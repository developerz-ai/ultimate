## 27.10.0 - 2026-10-12

### Added

Tier 2 — http. Tier 4 — ai.

- **`agent().run()` and `.continue()` — a finished run can be resumed with one more user turn.** `agent()` could only start: one user message, a fresh transcript, so correcting a finished answer was a whole new run that re-ran every tool. `agent()` now returns an `AgentAction` — the same `Action`, plus `.run(input, opts)` resolving to `{ output, transcript, turns, usage }` and `.continue(input, { transcript, user }, opts)`, which appends one user turn to that transcript and resumes the loop. The transcript is re-sent byte for byte, so the provider's prompt cache reads the prefix back and no tool runs twice. `maxTurns` and `budget.tokensPerRun` count the run and its continuations together; `deadlineMs` and `maxRepeatedToolCalls` are per call. `AgentTranscript` is JSON the app stores. It carries the run's own ceilings, so it is signed (HMAC-SHA256 with the framework's signing secret, `ULTIMATE_CURSOR_SECRET`, under its own label) and bound to the agent, the model, the declared tool names and the actor's `orgId`; on the way back it is checked for weight (2,000,000 characters, `MAX_TRANSCRIPT_CHARS`), signature, bindings and shape — message order, block kinds, every tool call answered and naming a declared tool — else `X_AGENT_TRANSCRIPT_INVALID` (422). In production a process still on the shipped development key refuses `.continue()`. A call that fails after a provider answered carries an updated signed handle (`transcriptOf(error)`) whose `turns` and `usage` include what it was billed: a job stores that one, because continuing from the handle it started with forgets the failed call's spend. A plain call is unchanged and keeps nothing. The session belongs to the agent it was opened for: an agent that runs underneath as a tool starts fresh. New names: `AgentAction`, `AgentRun`, `AgentContinuation`, `AgentTranscript`, `AgentTranscriptInvalidError`, `MAX_TRANSCRIPT_CHARS`, `TRANSCRIPT_VERSION`, `TRANSCRIPT_META`, `transcriptOf`; `@ultimat3/core` exports `currentSigningSecret`.

- **`inProcessTool()` — an agent tool that is not an MCP tool.** `agent()` refused any tool that was not `mcp: { expose: true }`, so a tool only the agent may call had to be an action that claims to be exposable — and was then served to every external MCP client. `inProcessTool({ name, description, input, execute })` is a tool that is this process's alone: `input` parses what the model sent (a failure reads back as `X_INPUT_INVALID`), `execute` runs as `ctx.actor` under the agent's own policy, and it appears in no MCP catalogue, route, `openapi.json` or manifest. An `action()` used as a tool is unchanged and must still be exposed; `X_AGENT_TOOL_UNEXPOSED`'s fix now names both ways out. New names: `inProcessTool`, `InProcessToolDef`.
- **An in-process tool's own refusal reaches the model.** A tool's failure is disclosed by the rule a problem document follows: a 5xx cause is hidden, and an app code with no `registerErrorStatus` row reads as a 500 — so an app's own typed refusal (`X_KB_DOC_NOT_FOUND`, its cause, its fix) reached the model as a fixed "details are withheld" sentence and the model repeated the call. A `ProjectableAction` may now say `inProcess: true`: an `UltimateError` it throws under a code nobody gave a status is sent as a structured error, `{"error":{"code","cause","fix"}}` (`callerFix` over `fix`). Everything else it throws keeps the general rule — an uncoded throw, a framework 5xx such as `X_DB_STATEMENT_FAILED`, a code the app registered as ≥ 500, an object that only looks like an error — and nothing but the three authored fields is ever sent. `discloseErrors: false` opts out. A tool projected from an exposed `action()` is unchanged. `@ultimat3/http` exports `declaredStatusFor` (the status somebody declared for a code, or `undefined`).
- **`temperature` and `seed` on `llm()` and `agent()`.** Neither could be stated. Both declarations (and `GenerateRequest`) take `temperature` (0 to 2) and `seed` (a whole number), screened at declaration (`X_AI_REQUEST_INVALID`). They are sent only to a model whose row takes them — `registerModel({ …, sampling: { temperature: true, seed: true } })` — and are left out for any other, because a reasoning model answers a sampling parameter with a 400; the `llm.sampling.ignored` span attribute names what was left out. `seed` is chat-completions only (the Messages API has none). A request that sets either gets its own response-cache entry; a request that sets neither keeps the key it had. No existing row or request changes. New type `Sampling`.
- **`forcedToolChoice: false` on a model row.** `llm()` offers one tool and the chat-completions wire forces it by name. A model whose thinking is always on rejects a forced choice — `anthropic/claude-sonnet-5.5` through OpenRouter answered 400 `tool_choice: type "tool" and "any" are not supported for this model` (2026-10-11), so every `llm()` call on it failed before a token was generated. A row that says `forcedToolChoice: false` is sent no `tool_choice`. Absent is forced, as before.
- **`llm()` takes `onCall` — usage and cost per provider call.** Only `agent()` had an observer. `onCall({ attempt, model, provider, stopReason, usage, cost, costExact, repairOf, run })` is called once per provider call an `llm()` invocation makes (the answer, and the repair turn when there is one; once for `.stream()`), awaited, and a throw from it fails the call. Not called on a semantic-cache hit. New type `LlmCall`.
- **A schema-repair turn says what it is repairing.** `onTurn`'s event (and `onCall`'s) carries `repairOf` on the turn that follows a rejected answer: the schema issues the model was told to fix. `X_LLM_OUTPUT_INVALID` carries the last answer's issues as a list on `meta.issues`, beside `prompt` and `attempts`.
- **Exact cost.** `exactCostOf(model, usage)` prices a call in micro-units of the currency's minor unit, in integers, as `Money` with a `scale` (`{ minor: 105_000, currency: 'USD', scale: 8 }` is 0.105 cents). `GenerateResult`, `AgentTurn`, `LlmCall` and `AgentRunUsage` carry it as `costExact` beside `cost`, and `BudgetLedger.report()` as `costExact`. Both built-in providers and `echoProvider()` state it; a `Provider` an app wrote may omit it. New names: `exactCostOf`, `roundUpCost`, `costScale`, `COST_SCALE_DIGITS`, `PRICE_SCALE_DIGITS`.
- **A price below one minor unit per million tokens can be stated.** A model's four prices accept `Money` with a `scale` up to six digits finer than the currency's minor unit: `inputPerMillion: { minor: 75, currency: 'USD', scale: 3 }` is $0.075 per million. Every existing row (no `scale`) means what it meant. A finer scale is refused by `registerModel`.

### Changed

Tier 4 — ai.

- **A call's cost is rounded up once, not once per half — `cost.minor` can be one unit lower than before.** `costOf` rounded the input side and the output side up separately, so a call worth 0.105 cents read 2. It now rounds the whole call once: 1. A call whose two halves each came to a whole minor unit is unchanged. The pre-flight estimate (`estimateCost`, what `budget.costPerCall` is checked against) moves the same way, never upward.
- **A ledger's cost is rounded once, when it is read.** `BudgetLedger` summed each call's rounded-up cost, so 14 turns of 0.45 cents reported 28 (two round-ups per turn); it now sums exact costs and `report().cost` — and `gateway.spent()` — say 7. A call recorded with no exact cost is summed from its rounded one, as before.
- **A `Provider` an app wrote may still report a fractional `cost.minor`; it is rounded up.** The exact ledger turned such a cost into a raw `RangeError` after the provider had been paid, losing the answer and leaving the reservation held. A fractional `minor` is rounded up; a `NaN`, an infinity or a negative is booked as zero (a negative would read as a credit); and a ledger that cannot record a paid call gives the reservation back, logs `ai.budget.record_failed`, and the answer is returned.
- **`budget.costPerCall` is compared as money.** A ceiling stated at a finer `scale` was compared by `minor` alone: `{ minor: 500, currency: 'USD', scale: 3 }` — fifty cents — accepted a $2.50 estimate, and `derive()` judged it looser than a $4.00 ceiling. Both now compare at a common scale (`compareMoney`). `billedOf(error).cost` carries its `scale`.
- **A cost stated finer than the ledger carries is rounded up, not thrown.** A provider result or a billed failure whose cost has more decimal places than the ledger's scale made the conversion throw after the provider was paid: a streamed answer was lost before it was yielded, and a billed failure was replaced by the conversion error. It is rounded up to the ledger's digit. `X_AI_BUDGET_EXCEEDED` for `costPerCall` states the estimate and the ceiling at one scale, named in the cause.
- **A stream whose provider throws after its `done` chunk is settled once.** `Gateway.stream` released the reservation again, crediting the ledger twice for one call.
- **Four deterministic failures are `terminal` for a job.** `X_LLM_TRUNCATED`, `X_LLM_OUTPUT_INVALID`, `X_LLM_TOOL_ARGUMENTS_INVALID` and `X_AGENT_TRANSCRIPT_INVALID` were unclassified, so a job with `attempts: 3` paid three times for the same answer: the ceiling does not move between attempts, and a schema two answers failed is a prompt to edit. They are now registered `terminal` (`AI_ERROR_RETRY`): `@ultimat3/jobs` dead-letters on the first attempt. **A job that relied on its retry policy to get past one of these no longer retries** — raise `maxTokens`, edit the prompt, or catch the code in the job and re-enqueue deliberately.
- **A truncated turn is refused even when its answer is complete, schema-valid JSON.** Stated once more because 27.9.0 returned it: a turn the provider labels cut off (`length`, `max_tokens`) is `X_LLM_TRUNCATED` whatever arrived, since content after the cut may be missing and nothing in the answer can show it.
- **An unknown chat-completions finish reason is no longer read as truncation.** Every reason this build did not list read as `max_tokens`, which — now that a truncated turn is refused before it is read — would have failed every call of an endpoint that spells "done" its own way. Synonyms are mapped, case-insensitively: `end_turn` / `eos` / `eos_token` / `STOP` are a stop, `stop_sequence` is one, `max_tokens` / `MAX_TOKENS` / `model_context_window_exceeded` are truncation, `tool_use` is a tool turn. A reason nobody knows is judged by the answer: a whole turn is a stop (or a tool turn when it carries calls), and a turn whose tool arguments do not parse — or whose reason is `error` — is the new `X_AI_PROVIDER_UNEXPECTED` (502), naming the reason and carrying `meta.billed`. The Messages API's reasons are a closed list and still fail closed. New name: `AiProviderUnexpectedError`.
- **A tool that itself calls a model is on the run's bill.** A nested `llm()` or `agent()` was recorded on the ledger but missing from the outer run's `meta.billed`, `onTurn`'s `run` and `AgentRun.usage` — and a nested failure reaches the model only as a tool error, so nothing else carried it. Nested runs now report upward call by call.
- **An in-process tool's refusal is bounded before it is serialised**: `cause` at 1,000 characters, `fix` at 500, so `maxToolResultChars` never cuts the JSON mid-string. `agent({ discloseToolErrors: false })` withholds every in-process tool's refusals for one agent, beside the per-tool `discloseErrors: false`.
- **`llm.sampling.ignored` names `seed` on a model only an Anthropic-format provider serves.** The Messages API has no seed; it was dropped without being listed. `Provider` gains an optional `wire`, `Gateway` an optional `samplingWires(model)`.
- **Streamed tool-call fragments with neither an `index` nor an `id`, naming a tool twice, are refused by name.** Two calls that cannot be told apart were merged into one; that is now `X_LLM_TOOL_ARGUMENTS_INVALID` saying so, and the merged arguments are never parsed or run, even when they happen to be JSON.
- **A model price that states a `scale` is priced at that scale.** `costOf` read `minor` and ignored `scale`, so a row written `{ minor: 75, currency: 'USD', scale: 3 }` was billed as 75 cents per million instead of 7.5. No row could usefully state one before, so an app is affected only if it had.

### Fixed

Tier 5 — cli.

- **`x g action --feature <slice>` into a hand-written slice writes only what an action needs, or refuses.** Pointed at a slice an author wrote (its own `policy.ts`, an `entity.ts`, a `repo.ts`), the generator behaved like a resource scaffold: it wrote `entity.test.ts`, `repo.test.ts` and `policy.test.ts` for modules it had not written, merged the entity's `admin.<slice>s.*` labels into every catalog, and emitted an action importing `can<Slice>Write` and `<slice>Tag` from a `policy.ts` that declared neither — a file that did not load, on which the generator itself then crashed (`X_CLI_UNEXPECTED`) with everything already on disk. Now: a module already on disk is its author's and gets no companion test and no admin labels; a `repo.ts` with no `byId` gets the lookup-free body; and a `policy.ts` that lacks the exports the generated file imports is refused **before anything is written** — `X_SLICE_POLICY_INCOMPLETE`, naming the file and the missing exports (`x g mutator` the same, for `can<Slice>Write`). The unit test it writes grants what the slice's own policy grants: the permission of a single literal `can('<perm>')`, or — when the grant cannot be read (`and`/`or`, a function, an unfollowed re-export) — no handler assertion at all, with a comment saying why; the contract test asserts no foreign-org denial against a policy it did not write. A fresh slice's generated files are unchanged byte for byte. The refusal's fix is the export lines to add, spelled for the slice. A nested destructuring pattern is "cannot tell", and a re-export that resolves to a directory without an `index.ts` is not followed (it was an uncoded `EISDIR`). A `policy.ts` that destructures its exports (`export const { a, b } = …`) or is a barrel is read properly: one level of relative `export * from` is followed, and a barrel that cannot be followed is "cannot tell" — the action is written, never refused on a guess. The line added to `apps/web/api/index.ts` is unchanged and correct: registration is what names an action. A slice with no `policy.ts` still gets the scaffolded one, with its test.

Tier 2 — http. Tier 4 — ai.

- **A cut-off answer is `X_LLM_TRUNCATED` before it is read, never an empty success.** `llm()` and `agent()` validated the answer first and looked at the stop reason only when validation failed. A `respond` call stopped at the output ceiling arrives with no arguments, which both wire formats read as `{}`, and `{}` satisfies any `output` whose keys are all optional: the run returned an empty object and was billed. A turn whose stop reason is `max_tokens` (chat-completions `length`, or a reason this build does not know) or `model_context_window_exceeded` now throws `X_LLM_TRUNCATED` before the schema runs, on both wires, streamed or not. **What changes for a caller:** a truncated answer that happened to validate used to be returned and is now refused; and an `agent()` turn cut off while it was asking for tools is refused too, where it used to run those tools on whatever arguments had arrived (`{}` for a call that never reached its first byte). The error's `fix` names `agent()` when an agent threw it, and its `meta` carries `prompt` and `maxTokens`.
- **A streamed tool call cut off mid-arguments is a truncated answer, not `X_AI_PROVIDER_UNAVAILABLE`.** Above a 16,000-token output ceiling `generate()` runs the streaming transport, and both wire readers threw a transport error the moment a tool call's arguments did not parse — before the stop reason (Anthropic) or the usage (chat-completions) had arrived. A long `respond` call that hit the ceiling therefore surfaced under the one code this package classifies `retryable`, the gateway moved on to the next provider, the reservation was released as if nothing had been spent, and a job ran the whole thing again. Now the fragment is dropped (a fragment is never a call), the result says `stopReason: 'max_tokens'` with the provider's real usage, and `llm()` / `agent()` raise `X_LLM_TRUNCATED`. The non-streamed chat-completions read makes the same call.
- **`X_LLM_TOOL_ARGUMENTS_INVALID` (502) — a FINISHED turn whose tool arguments are not JSON.** The other half of the same throw: the model completed its turn and wrote broken JSON. It is its own code, thrown by the provider once usage is known, carrying `meta.billed` (`usage`, `cost`, `calls`, `unsettled`; read it with `billedOf(error)`); the gateway records that bill on the ledger instead of releasing the reservation and does not retry or fall back. The cause never quotes the arguments. Registered `terminal` for jobs (below).
- **A failed run says what it was billed.** A failure after the provider answered was thrown with nothing about its cost, and for unparseable tool arguments the ledger was told nothing either. Every failure `llm()` (plain or `.stream()`) and `agent()` throw once a provider call has been started now carries `meta.billed` — `{ usage, cost, calls, unsettled }`, read with `billedOf(error)`: the usage of every call that answered, summed; its cost; and `unsettled`, the number of calls that were started and never reported usage (an abort, a deadline, a cut stream), **whose bill cannot be known** and is never estimated. That covers `X_LLM_TRUNCATED`, `X_LLM_REFUSED`, `X_LLM_OUTPUT_INVALID`, `X_LLM_TOOL_ARGUMENTS_INVALID`, `X_AGENT_MAX_TURNS`, `X_AGENT_TOOL_LOOP`, `X_AGENT_DEADLINE`, `X_ABORTED` and a budget or transport failure on a later turn. The ledger already held the settled calls; it now also holds a call that ended in `X_LLM_TOOL_ARGUMENTS_INVALID`. `meta` is operator-only and is not in a problem document.
- **Two streamed tool calls that share one `index` are two calls.** The chat-completions assembler merged fragments by `tool_calls[].index` alone. An endpoint that numbers every call of a turn `0` (or sends no index) and tells them apart by `id` had its calls concatenated into one argument string — `{…}{…}` — and one name (`readDocreadDoc`), which then failed to parse. A fragment whose `id` differs from the open call's now starts a new call; an id repeated on every fragment, or sent only on the first, is still one call.
- **A streamed call is read when the stream ends, not when the finish reason arrives.** Nothing in the format orders the finish reason against the last argument fragment, and an endpoint may send the reason twice (OpenRouter repeats it on the usage chunk). `ChatCompletionStream.end()` drains the calls at `[DONE]` or when the socket closes; tool-call chunks are yielded then.
