## 31.3.0 - 2026-11-11

### Highlights

- Read one row's recorded history in write order with `history(db.postsHistory, id)`: versions numbered from 1, scoped to the tenant.
- Islands used on exactly the same routes share one bundle: a multi-island page ships 31% less island JavaScript.
- `x dev` restarts in under 6 s on a 5,000-file app, down from 21 s.
- The reference app uses every new factory once, SAML sign-in included.
- Fixed: `partitionBy` migrations pass the drift step, rules on nullable columns accept `NULL` as Postgres does, and `@ultimat3/testing` ships a SAML test IdP.

### Added

- `@ultimat3/entity`: `history(table, id)` reads every recorded version of one row of an `entity({ history: true })`, oldest first, each numbered `version` from 1 (`HistoryVersion`, `HistoryRecord`). Rows are ordered by chaining each `before` onto the previous `after` across every version, with `at` only breaking ties: `at` is a transaction's START (`now()`), so a transaction that began first and committed last carries the earlier `at` and the later image. Delete-then-reinsert and A→B→A chain too, and a counted column is left out of the match. It reads the history table the app already declares (`database({ posts, postsHistory: posts.$history })`), so another tenant's row reads back `[]`. `version` counts the retained rows. `history(table, id, { limit: n })` reads the `n` versions with the latest `at` (every tie at the edge kept), oldest first, numbered as the whole history numbers them; `at` is a transaction's start, so a transaction that began before that window and committed inside it can fall outside. Same answer on memory, PGlite and a server; no schema change, no migration.
- `@ultimat3/entity`: `entity({ history: { ignore: ['likeCount', 'updatedAt'] } })` keeps columns that churn out of history: an update that changes only ignored columns records nothing, on Postgres (the trigger) and memory alike, and `history()` chains across them. Typed to the entity's own columns; another name is `X_INVARIANT_VIOLATED`. Declaring it is one `x db gen`, which reinstalls the trigger with the new list.
- `@ultimat3/testing`: `fakeSamlIdentityProvider({ audience, users, clock? })`, the SAML twin of `fakeIdentityProvider`: `metadataXml` for `samlIdentityProvider`, `answer(location)` returning the signed `{ SAMLResponse, RelayState }` for the AuthnRequest on an SP's redirect, `readAuthnRequest(location)`, `signInAs(nameId)` and `tamper({ wrongAudience?, expired?, unsigned?, wrongKey? })`. Each tamper is refused by the real verifier with an `X_SAML_*` code.
- `@ultimat3/auth`: `@ultimat3/auth/saml-test-idp`, the in-process SAML IdP and RSA signer auth's own suites sign with (`samlTestIdp()`, `readAuthnRequest()`, `encodeResponse()`, `testRsaSigner()`), now shipped. It was a `*-fixture.ts` the package excluded from npm. `TestResponseSpec.name` sets the `displayName` attribute.
- `@ultimat3/testing`: `entityDriverConformance` checks `history: true` + `history(table, id)` — five versions of one transaction in order, none from a failed one, none for another tenant — on a subject that declares `history: true` (new, optional on `EntityDriverSubject`). A `defineDriver` store declares none and skips it.

### Changed

- Reference app: `examples/dummy` uses each new factory once — `withLock`, the upload scanner (with a `hold`) and `variant()` on avatars; `partitionBy` and `smsChannel` on `quota_alerts`; `history()` in `postRevisions`; SAML SSO through `identityProviderRoutes`, mounted from deploy config and tested against `fakeSamlIdentityProvider`. Avatar and posts-import uploads go through `pending/` and promotion, because an installed scanner refuses targeted grants.
- `@ultimat3/cli`: on a 5,124-file app (the reference app plus 150 generated resources), an `x dev` restart reaches its first 200 in 5.7 s, down from 21.1 s. The island build runs alongside the app load, and each route group's build is cached. A fresh clone takes 29.3 s. A `web` pod booting from the prebuilt registry takes 2.4 s (3.3 s scanning). Measured by `scripts/bench/boot-large-app.bench.ts`, which boots the app whole; results are in `scripts/bench/results/boot-large-app.json`. The pod boot meets its 3 s target, every rung of `docs/idea/17-scale-ladder.md` cites a committed result, and wiki Deployment cites the pod boot.
- `@ultimat3/cli`: islands rendered on exactly the same set of routes are bundled in one split build and share their code. Every other island is still built alone, byte for byte (`island-groups.ts`). examples/dummy `/posts/:id`: 95,754 → 65,676 B of island JS; every other route of the three tracked apps is unchanged. `islands.sharedChunks` keeps its meaning: one group of every island.
- `@ultimat3/cli`: island builds reuse each route group's output from `.x/cache/islands/` while every file it read is unchanged, so bytes and URLs are identical. Each island stylesheet is compiled once per build rather than once per group. The cache tracks Sass partials, the directories imports resolve in, and the tsconfig/`package.json` environment; its entries verify their own bytes and are swept after 14 days. One failed island build stops the rest from starting, and `x dev` reads the realtime answer only after the app load settles.

### Fixed

- **Security** — `@ultimat3/auth`: `defineAuth` reads the installed limiters and TOTP replay guard where they are used, not when it is called. The boot installs them after `runtime.ts` loads, so an app whose `runtime.ts` imports reached `defineAuth` kept per-pod memory guards for life: account lockouts multiplied by the replica count, and a TOTP code or SAML assertion replayable once per pod. What `defineAuth` is passed still wins. A `rateLimit: { scope: 'shared' }` app with no shared limiter is now refused (`X_AUTH_LIMITER_NOT_SHARED`) where the limiter is first used, not at `defineAuth`, since the boot may still install one.
- **Security** — `@ultimat3/storage`: `ScanInput.revision` names which bytes under `pendingKey` a scanner is judging: the confirmed upload's etag, or `sha256:<hex>` on a disk with none. The upload URL stays valid after the sniff, so a held upload approved by `pendingKey` alone could be rewritten and confirmed again, attaching whatever was PUT there unscanned. Key a held decision by `(pendingKey, revision)`. `uploadScannerConformance` fails a scanner that clears a new revision of one upload on the old one's verdict. Optional on the type, always set by `promoteAttachment`.
- `@ultimat3/entity`: `history()` returns versions in write order when transactions interleave. A transaction that began first and committed last stamps the earlier `at`, so ordering by `at` put its version before the one it followed, and the row's latest image was not the last version.
- `@ultimat3/testing`: a seed pass whose rows no partition holds (`23514 no partition of relation`) is `X_SEED_GRAPH_UNSATISFIED` naming the app's `partitions()` job (`maintainPartitions.enqueue({})`) or `seedGraph({ now })`, not a factory to write.
- `@ultimat3/cli`: an app checked out under a directory named `node_modules` loads. The scan tested the absolute path for that segment and skipped every module.
- `@ultimat3/db`: a migration `x db gen` wrote for an `entity({ partitionBy })` or with `database.rowSecurity` no longer fails the app's own `drift` step with `X_MIGRATION_UNGENERATABLE`. The partition function's retired-signature drop, its `create or replace … returns jsonb`, the call that makes the first partitions, `enable`/`disable`/`force`/`no force row level security`, `create policy` and `drop policy if exists` are generatable forms. `ungeneratable.test.ts` now builds its corpus from a partitioned entity and row security too, so a form a generator adds and the list lacks fails there. A hand-written function call, policy or overload drop is still reported.
- `@ultimat3/testing`: `entitySeedWriter`'s snapshot binds and matches a `Date` key by its ISO instant, so a table keyed on a `timestamp()` — every `partitionBy` table — no longer fails `x exercise` with `X_DB_STATEMENT_FAILED` (`invalid input syntax for type timestamp with time zone: "… GMT-0500 (…)"`), under any session time zone.
- `@ultimat3/testing`: `seedGraph` gives a `partitionBy` column values inside the partition the migration made first — the UTC bucket holding `now`, read off `$describe().partition` — where it seeded `2026-01-…` and every insert into a partitioned table failed with `no partition of relation … found for row` (`x exercise`, the seed graph). `SeedGraphOptions.now` names that instant; default `systemClock.now()`, and under a frozen test clock pass the database's `now()`.
- `@ultimat3/entity`: an invariant over a nullable column passes `NULL` in the app as its CHECK does. `c.slug.matches(/…/)`, `minLength`, `contains`, `atLeast`, `eq`, `isTrue` and a column-to-column `eq` refused a `NULL` the database stored, so the memory driver and `$assert` rejected rows Postgres accepted. A rule now answers SQL's unknown for a `NULL` operand, `iff` composes unknowns, and a rule holds unless it is false. `isNull()`/`isNotNull()` stay total. To refuse `NULL`, declare the column NOT NULL or add `.isNotNull()`.
- Repo tooling: every repo script that runs a published or scaffolded app hands it an allowlisted env (`scripts/lib/stranger-env.ts`), never the repo's `.env` (`NPM_TOKEN`, `NPM_PASSWORD`, the TOTP seed): the first-hour bench, `scaffold-gate`, `scaffold-first-run`, `scaffold-admin`, `scaffold-agent` and `tutorial-run`. `scaffold-first-run` follows each generator's `data.next` but `x verify`, in place of a hard-coded `x db gen "generated"`.
- Repo tooling: the first-hour bench runs the commands `x g resource --json` names in `data.next` before its second gate. It skipped the migration, so the gate was red on `unit`, `exercise` and `drift` (bench run 42879568783).
