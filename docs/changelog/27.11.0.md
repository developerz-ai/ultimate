## 27.11.0 - 2026-10-17

### Fixed

- **A database blip no longer turns every request into a 500.** `postgresRateLimitStore`'s `take`
  and `peek` rethrew `X_DB_UNAVAILABLE`, so while Postgres was unreachable every request a web pod
  served, a prerendered `GET /` included, failed on the limiter. On a connection-class failure only
  (`X_DB_UNAVAILABLE`, `X_DB_POOL_EXHAUSTED`, or SQLSTATE class `08`, `57P01`–`57P03`, `53300`)
  the decision is now taken from a per-process memory bucket, for every method and every route
  (auth routes included): the limit still applies, per pod instead of fleet-wide, until the
  database answers again. The fallback is a separate budget that starts full on each pod, so a key
  may spend up to its capacity again per pod at the transition, on top of what it spent in Postgres.
  `reset(key)` clears the fallback bucket as well as the shared row.
  `http.rate_limit.degraded` is logged at warn at most once a minute.
  Any other failure (bad SQL, a missing table, an executor bug) still refuses as before. The
  credential limiter (`x_auth_lockouts`) is unchanged and still fails closed.
- **A pod stopped while it is still booting exits 0.** A rollout that superseded a pod mid-boot
  began the drain, and the boot then reached `markReady()`: `X_LIFECYCLE_DRAINED` with a stack trace
  and a non-zero exit. `runRole` now treats a boot that fails while a drain is under way as
  interrupted: it finishes the drain, logs `ultimate boot interrupted by shutdown` at info with the
  error's code, and exits 0. A boot failure with no drain under way is rethrown as before.
- **No warning for the bus's first dial.** The cache's boot subscribe races the transport's first
  connection and lost it on nearly every pod, warning `cache.broadcast.subscribe-failed` on attempts
  1 and 2 before landing within about a second. Refusals in the first 10 s (`FIRST_DIAL_GRACE_MS`)
  are now silent, and so is the landing after them. A bus still refusing after that warns as
  before, then logs `recovered` at info.
- **`x db backfill`, `x jobs` and `x auth` boot as a runtime role with DML only.** Every CLI
  command re-ran the framework DDL at boot, and Postgres checks ownership before existence: as a
  role that owns no framework table, `create index if not exists` on `x_job_counters` is
  `42501 must be owner` even when the index is there. A production backfill Job running as the
  runtime role failed with `X_FRAMEWORK_SCHEMA_FAILED` on every deploy and enqueued no sweep.
  These commands now read the stamp `ROLE=migrate` leaves and run no DDL when this build's stamp is
  there; with no stamp they apply it as before (a fresh dev database needs no other step).
  `ROLE=migrate`, `x db migrate`, `x dev` and `x mcp serve` still apply unconditionally, and a
  serving role still only verifies.
- **Finished jobs no longer live forever.** The hourly `x.purge` swept seven framework tables and
  none of the job tables, so `x_jobs` and `x_job_steps` kept every job ever run, and a `mail.send`
  row kept its recipient address and rendered body indefinitely. A new target, `x_jobs`
  (`jobsPurgeTarget` in `@ultimat3/jobs`), deletes `done` rows after `jobs.doneRetentionMs`
  (default 14 days) and `dead`, `failed` and `cancelled` rows after `jobs.deadRetentionMs`
  (default 90 days), each with its step records once no row of the run still stands. Live rows
  are never deleted, and neither is a row that an unpublished outbox row or a running backfill
  still names. A pass runs at most 50 batches (`maxBatches`) of 1,000 rows (`batchSize`) with
  `skip locked`; a batch is one statement, plus a follow-up after it commits when a concurrent sweep
  split a run, and the pass ends with one statement removing up to 1,000 step records whose run has
  no row left (a sweep that died before its follow-up). All three find a run's rows through the
  new index `x_jobs_run_idx`. The new partial index
  `x_jobs_finished_idx` serves the sweep, so the framework schema hash changes and
  `ROLE=migrate` must run before serving roles, as on every release.
- **Published outbox rows no longer live forever.** `x_outbox` kept every row a transaction ever
  staged, with the job input (`mail.send`'s address and body). Another new `x.purge` target, `x_outbox`
  (`outboxPurgeTarget`), deletes PUBLISHED rows after `jobs.outboxRetentionMs` (default 7 days),
  batched like `x_jobs`, measured against the job's clock as the relay stamps `published_at`. An
  unpublished row is never deleted. New partial index `x_outbox_published_idx`.
- **The Jobs wiki states the real idempotency-key window.** It said "`retentionpolicy` per queue;
  default 24h after terminal state", which nothing implements: a key is unique only while a row
  holding it is live, and the same key enqueues again as soon as that row is terminal.
- **`X_FRAMEWORK_SCHEMA_FAILED`'s fix names the migrate step's role.** It said to grant `create`
  on `public` to the role in `DATABASE_URL`, which cannot cure `must be owner` and widens a runtime
  role. It now says to run `x db migrate` with `DATABASE_URL` naming the role that owns the schema.
