## 29.0.0 - 2026-10-28

### Added

Tier 1 — seo.

- **`RouteMeta.socialCard?: boolean` — a page that may not be indexed can still carry a social
  card.** A document whose `meta` says `robots: { index: false }` carries no `og:*`, `article:*` or
  `twitter:*` tag, declared or derived; a route that declares `socialCard: true` asks for one
  anyway, and the card is emitted exactly as it is for an indexable document — declared values win,
  and the derived ones come with it (`og:type`, `og:title`/`og:description` from the page's own
  title and description, `og:url` from the canonical, `og:locale`, the `twitter:card` default). The
  opt-in is the route's own declaration, and it applies wherever the route's document is
  unindexable: a declared `robots.index: false`, or a 4xx/5xx, which `@ultimat3/render` marks
  `noindex` by construction. What does not change: the robots directives (`noindex,follow` stays
  `noindex,follow`), every indexable route, and every noindex route that declares no flag. One
  optional property on `RouteMeta`, no new export, and no other package's runtime or type changes.

  It supersedes the 23.0.0 entry `BREAKING — (#48)` — a `robots: { index: false }` document
  carries no `og:*`, `article:*` or `twitter:*` tag, and there was no switch — with
  `socialCard: true`, the switch that entry said did not exist. The 23.0.0 section is left as it
  shipped.

Tier 0 — core. Tier 3 — jobs. Tier 5 — cli.

- **`jobWorker({ maxInFlight })` and `jobs.maxInFlight` — one cap on the runs a worker PROCESS holds
  across every queue (Sidekiq's `concurrency`).** `concurrency` was per-queue pools only, so a
  worker serving many queues held the SUM of their slots, and an app that needed "at most 10 runs
  in this pod, whichever queues they come from" had nowhere to say it; `LimitConfig.global` sheds a
  job already claimed. The cap is read before every claim: a worker at it asks the queue for
  nothing, a run that ends frees one claim and kicks a pass at once, and the per-queue slots still
  bound each queue under it. **Fairness:** a pass splits its room over the queues it has not yet
  asked (`ceil(room / queues left)`), a queue with less work leaves the rest to the next ones (no
  idle slot while any served queue has ready work), and the queue order is rotated to start after
  the last queue given a job — so each freed slot goes to the next queue in turn and no backlog
  monopolises the cap, including while the loop idles at the cap (an idle pass there takes the
  rotated asks, not the one-statement claim that hands out the oldest row of any queue). Drain, lease heartbeat and fleet slots are unchanged. Unset is no cap, the
  worker as it was. `0`, negative, fractional, `NaN` or `Infinity` is `X_INVARIANT` at `jobWorker()`
  and `X_CONFIG_INVALID` naming `jobs.maxInFlight` at boot. For a scaler: `worker.stats()` gains
  `maxInFlight` (`null` when uncapped), the registry row's `concurrency` is the tighter of the cap
  and the slot sum, and two new gauges, `job_worker_in_flight` and `job_worker_capacity`, summed over the live workers
  in the process.

### Changed

Every package; tier 5 — cli.

- **BREAKING — (#1) Bun 1.4.4 is the floor.** `engines.bun` is `>=1.4.4` in every `@ultimat3/*`
  manifest and in `create-ultimate`, and `x` / `x doctor` (`REQUIRED_BUN`) refuse Bun 1.4.0–1.4.3
  with `X_BUN_VERSION`. CI, `release.yml`, the framework image (`oven/bun:1.4.4-slim`) and the image
  `x new` scaffolds (`oven/bun:1.4.4-alpine`, by digest) all run 1.4.4, so the floor names the one
  patch this release was tested on (`scripts/bun-pin.test.ts` holds every site to CI's patch).
  `@types/bun` is `1.4.4`. No shipped runtime code changed for it. What 1.4.4 moved, and what
  this repository did about each: (a) `--coverage` counts fewer functions while the uncovered ones
  stay, so a function ratio falls with no test or source changed (`packages/jobs` 95.46% →
  94.59%) — `jobs` is pinned, `scripts`' pin and both tracked apps' floors re-measured, each with
  the numbers in its `why`; (b) a `file:` folder dependency is now copied rather than symlinked
  file by file under the hoisted linker, so a graph that reaches `@ultimat3/core` through several
  `file:` packages loads several cores and `x` fails on `X_REGISTRAR_MISSING` — the scaffold smoke
  no longer forces the hoisted linker and installs with the default isolated one, which keeps one
  core; (c) `Bun.SQL` binds a JS array parameter itself, and `array-parameter.live.test.ts`
  asserts that instead of the refusal; (d) two `@ultimat3/ai` suites relied on a fixture module's
  import-time hook, which only reaches the first suite that imports it — each suite registers
  its fixture models itself. 1.4.4 resolves peer dependencies pnpm-style, so `bun.lock` drops the
  `@babel/helper-module-transforms` subtree nothing installed.

Tier 5 — cli.

- **BREAKING — (#2) A `WORKER_QUEUES` entry the app does not know refuses the worker's boot.**
  Each entry must be a queue in `jobs.queues` or the queue a registered `job()` is enqueued on —
  the union an unset `WORKER_QUEUES` serves. Any other entry (a typo, an unexpanded pattern such as
  `banks-*`, a bare `*`) is `X_WORKER_QUEUE_UNKNOWN` at worker start: the cause names the entry and
  every queue the app knows, says a pattern is never expanded, and the `fix:` is the
  `WORKER_QUEUES=` line to set — a pattern's expansion over the known queues. Before, the worker
  booted claiming a queue nothing is enqueued on, said so at `info`
  (`jobs.worker.queue-unregistered`), and stayed Ready: on 2026-10-27 an app's
  `WORKER_QUEUES=banks-*,banks,default` rolled out healthy and left every run on its real queues
  waiting ~15 minutes until a revert. Refused, the new pods crash and a rolling update stalls on
  the old ones. What does not change: unset or blank is still the union; a registered queue an
  exact worker does not list is still the `jobs.worker.queue-unserved` warning, not a refusal; an
  empty entry is still `X_CONFIG_INVALID`. A queue that only `enqueue({ queue })` reaches must now
  be in `jobs.queues` before a worker may name it (`packages/cli/src/runtime-jobs.ts`).

### Fixed

Tier 2 — entity.

- **A refused filtered update leaves every matched row as it was.** The in-memory driver's
  `updateWhere` wrote row by row, so a rule only the app can judge (`X_INVARIANT_VIOLATED`)
  refused the second matched row and left the first one stored — a half-written state the Postgres
  driver never had: it sends one statement and judges the rows that statement returned in the same
  transaction (`packages/entity/src/judged-write.ts`), so a refusal there rolls the write back. The
  memory driver now judges the whole result of the update before it writes any of it — the app's
  rule and the tenant for every merged row, the primary key and the unique constraints against the
  rows the filter did not match and against the results the same batch has already judged
  (`packages/entity/src/memory-update.ts`) — so a refusal leaves every matched row holding the
  values it held before the call, the answer the Postgres driver gives. What does not change: a
  filtered update that holds still writes every matched row and answers the count
  (`packages/entity/src/invariant-parity.test.ts`).
