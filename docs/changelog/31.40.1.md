## 31.40.1 - 2026-11-17

### Highlights

- **Audit round 3 (plan 101b, slice 20), its security half:** the realtime channel tenant leak (P0) and two P1s, each with a test that failed first. The round's P2s follow in the next release.

### Security

- realtime: a channel param that names a records entity's tenant column must be the subscribing actor's own org, checked by the hub before the channel's policy. A topic keyed by that column (`org-feed.<orgId>`) is one org's stream of records, events and presence; before, the policy alone decided the seat, so a permission-only rule (`can('post:read')`, the shape the missing-policy refusal suggested) let a member of org A subscribe with org B's id and receive org B's rows, events and presence. Refused as `X_TOPIC_FORBIDDEN` naming `X_TENANCY_ACTOR_MISMATCH` or `X_TENANCY_ACTOR_ORG_REQUIRED`; a proven `crossTenant()` scope passes.
- ai: an unbound vector store (no `.scoped({ tenant })`, no `scope: UNSCOPED`) is refused with `X_VECTOR_UNSCOPED` inside any request, whoever the actor. 31.40.0 refused it only for an actor acting for an org, so an anonymous visitor, an org-less user or a `tenant: 'none'` job still read and wrote every org's rows.

### Fixed

- `x new --force` writes only into free paths: a directory where any planned file already exists is refused before anything is written, naming the colliding paths. Before, `--force` silently overwrote an existing repository's `package.json`, `README.md`, `tsconfig.json`, `CLAUDE.md` and CI workflow, while its own message said it wrote "beside" them.
- The release workflow's scaffold-from-npm check greps the exact pin `x new` writes since 31.40.0; 31.40.0's run went red there after a clean publish.
