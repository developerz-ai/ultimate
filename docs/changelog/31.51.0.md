## 31.51.0 - 2026-11-25

### Highlights

- **Sign-in by mailed link:** an app can sign a user in from a link issued under a purpose it declared for that.
- **A boot failure names your file:** when an installed package fails to import, `X_APP_IMPORT_UNRESOLVED` points at the app module that reached it, with a fix that fits and, when static imports lead there, the chain.
- **Test code in a role is flagged:** `x verify` warns `X_BOUNDARY_DEV_IMPORT` when a module loaded at boot reaches the CLI barrel, `@ultimat3/testing` or `bun:test` through static imports of the app's own files.
- **Page tests through the real pipeline:** `pageRoute` lets a unit test GET a registered page and read the `Response`.

### Added

- `@ultimat3/auth`: sign-in by mailed link is exported. `signInWithLink(auth, { purpose, identifier, token, ip?, userAgent?, signUp? })` (with `LinkSignInInput` and `LinkSignUp`) consumes a link issued under a purpose the app declared a sign-in credential, `defineVerificationPurpose({ …, signIn: true })`, and answers what `login()` answers; with TOTP enrolled it answers `X_MFA_REQUIRED` with the sealed challenge and writes no session, and `completeMfa` finishes it. A declared purpose without `signIn` or with its own `identifier`, and the built-in `email-verify` and `password-reset`, are `X_CONFIG_INVALID` before the link is spent, and an undeclared name is `X_VERIFICATION_PURPOSE_UNKNOWN`; the fix names a dedicated sign-in purpose and a freshly issued link, so an email-change or deletion link is never promoted to a session. An account that never verified its address is refused (`X_UNAUTHENTICATED`): the registrant's password, second factor, passkeys, API keys and sessions survive a bare stamp, so recovery needs an app-owned flow that proves the inbox, clears all credentials while disabled, and atomically checks ownership before reopening, coordinated with administrative disables. A sign-up account is created verified in one write on an adapter that stores the new optional `CreateUserInput.emailVerifiedAt` (both built-in adapters do); an app adapter that drops it gets a second `updateUser` stamp, whose failure leaves the account unverified (`X_AUTH_WRITE_FAILED`).
- `pageRoute(path, { headers?, cookies?, buildId? })` in `@ultimat3/cli`: a unit test GETs a registered page through the real `httpPipeline` and gets the `Response`. See [Testing](https://github.com/developerz-ai/ultimate/wiki/Testing#a-pages-own-get).
- `@ultimat3/cli`: the `boundaries` step of `x verify` warns `X_BOUNDARY_DEV_IMPORT` for a module the boot scan imports that reaches `@ultimat3/cli` (the barrel), `@ultimat3/testing` or `bun:test` through static imports of the app's own files, one line per import to cut, with the chain. A warning on `main` (`warnings` in `--json`, the step stays green); the refusal is planned for `next`. Shared test support lives in `apps/<app>/test/`, outside the scan ([Testing](https://github.com/developerz-ai/ultimate/wiki/Testing)).

### Fixed

- `X_APP_IMPORT_UNRESOLVED` for an import that failed inside an installed package names the app module that reached it, with the chain (`meta.chain`) when static imports spell it (a computed `import()` has none), in `x doctor`, `x manifest` and the boot log, and `X_APP_MODULE_LOAD_FAILED` lists that module. One deployed app pruned `@ultimat3/testing` from its image and every role refused to boot over a finding that named `@ultimat3/cli/src/test-shards.ts` and said `bun add @ultimat3/testing`; the cause was its own test helper under `app/`, a `.fixture.ts`, importing `@ultimat3/cli`. The fix is the edit to that module, `bun install --frozen-lockfile` for a dependency the package declares, `bun install --force` for a damaged copy, `bun add` for a peer, and for a linked package its own import or install, in its checkout.
