## 27.13.0 - 2026-10-20

### Added

- **`agent()` runs pick inside their declaration: `offerTools()`, `model` as a function,
  `limits()`.** Every run read its tools, model and ceilings off the declaration alone, so an app
  storing per-tenant agent overrides (a permission rule, a model tier, a cheaper plan) declared one
  agent per combination, or offered every tool and refused inside each policy — still showing the
  model a tool it could never call. Each is a function of `{ input, ctx }`, called once per call
  before `vars()`, and each only NARROWS: `offerTools()` returns a subset of the declared tool
  names (another name is the new `X_AGENT_TOOL_UNDECLARED`, 500, `terminal` for a job); `model`
  answers a registered id (`X_AI_MODEL_UNKNOWN` otherwise) or `undefined` for the prompt's model,
  then `defaultModel`; `limits()` returns `{ maxTurns, maxTokens, maxToolResultChars,
  maxRepeatedToolCalls, deadlineMs, budget }`, screened like the declared bounds and held at or
  under each (a higher value is `X_AI_REQUEST_INVALID`). The transcript handle binds the run's model
  and the tool names it was OFFERED. `describeAgents()` reports a per-run model as
  `model: null, modelFrom: 'run'`. New types: `AgentModel`, `AgentRunLimits`; new class
  `AgentToolUndeclaredError`.
- **`budget.costPerRun` on `agent()` — a money ceiling for the whole run.** `costPerCall` bounded
  one call and nothing bounded their sum. Before each turn, the run's cost so far (every turn,
  every continuation, every nested call billed) plus that turn's worst-case estimate must fit, or
  the turn is refused pre-flight as `X_AI_BUDGET_EXCEEDED` with scope `costPerRun`. Published in
  `describeAgents()`'s `budget`; `limits()` may set or lower it. `Gateway` gains an optional
  `marksPromptCache(model)` so the estimate prices a turn as the gateway's reservation does.

### Fixed

- **A navigation the service worker has no rule for is answered from its preload, not sent
  twice.** The worker turns navigation preload on for every navigation, but returned without
  `respondWith` for a path with no route rule or under `offline.neverCache` (an app's own plain
  routes, e.g. an OAuth start and callback). The browser then cancelled the preload — which the
  server had already processed — and requested the URL again, so a one-time OAuth callback
  exchanged its code twice: the first exchange signed the person in on a response the browser
  dropped, the second failed with "code missing or expired" (`X_OAUTH_EXCHANGE_FAILED`, then
  `X_OAUTH_STATE_INVALID` on retry). Such a navigation is now answered from
  `event.preloadResponse`; an empty or failed preload is the one network fetch.
- **`x verify` and `bun run verify` write progress on stderr in the human render too**, not only
  under `--json`: a line per finished step, and a `still running: <steps> (<elapsed>)` heartbeat
  every `HEARTBEAT_MS` (60 s) while a step runs. A harness that kills a process after 30 silent
  minutes killed green gates that finished seconds past the window, and one step on a 2-core box
  can outlast it alone. The timer is unref'd and stopped however the run ends; stdout under
  `--json` is still the one document.
- **`page.gotoStreamed()` returns the whole first flush, not the first network chunk.** One server
  flush (the head and the shell) can reach the page as several chunks, and the read took only the
  first. `examples/dummy`'s streamed-feed e2e then failed on a header the server really sent, with
  the shell cut mid-tag (#807, CI). The reader now joins chunks until the first hole is revealed
  (and cuts there) or the stream pauses for 250 ms, then cancels it as before.
- **`delete_resource` accepts `live` and `confirmed_by_user` inside `params`, as documented**
  (#798). Its input schema required `confirmed_by_user` at the top level, so a call carrying both
  flags only in `params` was `X_INPUT_INVALID` before the dispatcher read them. The schema now
  requires neither; a live call without `confirmed_by_user: true` anywhere is still
  `X_MCP_USER_CONFIRMATION_REQUIRED`, and nested still wins.
- **`x verify` holds a slow machine to the same deadlines as a fast one.** Every declared number —
  each step class's 5 / 8 minutes, Bun's 5 s per test, a test's own `{ timeoutMs }` — was set on a
  4-core CI runner, and on a 2-core 1.8 GHz box the same work runs five to seven times longer: the
  framework's own gate went red there on `errors`, `unit`, `live`, `manifest` and `lint` or `job`
  (2026-10-19, five of twenty steps) with no defect in the code. Each entry point (`x verify`, `x build`'s preflight, the MCP host) now
  measures the machine's pace once, before any step — its cores against 4 and a short
  single-threaded probe against the runner's, each held at 1 from below — and multiplies the
  declared deadlines by it: a step's, `--timeout` on every test run, and `ULTIMATE_TEST_PACE` for a
  test's own, read by `@ultimat3/testing`'s new `paced(ms)` and by the typed helpers'
  `timeoutMs`. A number in `x.verify.json` is taken as written. `--json` carries `data.pace`, and
  an `X_VERIFY_STEP_TIMEOUT` past a stretched deadline says by how much. An unparseable
  `ULTIMATE_TEST_PACE` is `X_TEST_PACE_INVALID`.
