# Developer experience

## The first 60 seconds

```
bunx create-ultimate myapp && cd myapp && bun run setup && bun run dev
```

Four commands. `bun run setup` is the scaffold's own script, seven steps — `bun install`,
`x merge-driver install`, an `.env.development.local` touch, `x db gen "initial"` when `packages/db/migrations` holds no `.sql`,
`x db migrate`, `x db seed`, `x manifest` — and it is **not optional**: `x new` installs nothing, so
`x dev` straight after `cd` stops on `X_BUILD_FAILED` naming `bun install`. Measured
`As of 2026-09-11` on a warm Bun cache: 6,802ms for the six steps it then had, and 12.0s when the install is
cold. This page wrote the three-command form until 2026-08-23.

```
$ x dev
  roles web, sync, worker, scheduler
  panels routes, timeline, live, jobs, db, mail, cache, policy, manifest, services, boundaries
  manifest /path/to/myapp/x.manifest.json
  introspect http://localhost:3000/_x
✓ dev ready on http://localhost:3000 — /_x mounted (11 panels), db=embedded events=embedded storage=embedded mail=embedded cdn=none
```

`replicator` is the fifth role and is opt-in — it takes a replication slot, so `x dev` does not start
one. MCP is not a role either, and it is two things. The **app's** endpoint is mounted by the web
role, so `x dev` serves it: every `apps/<app>/mcp.ts` at its own `defineAppMcp({ path })` — `POST /mcp`
for the scaffold's `apps/web/mcp.ts`, `POST /admin/mcp` for an admin surface's — each logged at boot
as `app mcp mounted`, and each a 401 without a token (`packages/cli/src/app-mcp.ts`). The **dev**
server — routes, schema, tests, logs, read-only SQL — is `x mcp serve`, its own command and never a
path on the dev server. `As of 2026-11-19`.

**No Docker. No env scavenger hunt.**

| Dependency | In dev | In prod |
|---|---|---|
| Postgres | embedded PGlite, in-process, data in `.x/pgdata` | real Postgres |
| NATS | in-process, same API | NATS / JetStream |
| S3 | `./.x/storage`, real S3 API surface | `Bun.s3` against any S3 |
| Mail | captured in the `/_x` inbox, never sent | SMTP / provider |
| Redis (cache tier 3) | in-process map behind the same interface | `Bun.redis` |
| Secrets | generated dev values with a loud "dev only" prefix | env / mounted file |

`x new` writes `.env.development` complete and valid — committed non-secret defaults, with per-box secrets in `.env.development.local`, which wins. No "ask a teammate for the keys" step, and no service you must install first. The dev drivers implement the same interfaces as production, so switching to `docker/docker-compose.dev.yml` for a parity check is a one-line change ([`12-build-deploy.md`](./12-build-deploy.md)).

An `.env.example` is never hand-maintained either: `renderEnvExample()` projects one out of the `defineEnv` declaration, and `x verify`'s `manifest` step fails when the committed file is not byte-for-byte that projection (`X_ENV_EXAMPLE_DRIFT`, fixed by `x env example` — [`packages/cli/src/app-env.ts`](../../packages/cli/src/app-env.ts)). One declaration, both files — [axiom 2](./00-thesis.md).

## `x dev` runs all roles in one process

One Bun process, every role, **isolation simulated rather than skipped**:

| Simulated | How | Catches |
|---|---|---|
| Separate role contexts | each role gets its own ALS context, DB pool, and logger tag | code accidentally sharing in-memory state across roles |
| Surface imports are checked | `site/` → `app/`, `shared/` → a surface, `app/` → `api/` at runtime, a route touching `db`, a service importing `http` — five rules, five codes ([`../architecture/02-boundaries.md`](../architecture/02-boundaries.md)). There is **no** role-based rule: nothing refuses a `worker`-only module imported from a `web` handler | "works in dev, missing in prod" |
| Queue is real | the Postgres queue with real claiming and leases | jobs that only work when awaited inline |
| Replication is real | logical replication against the embedded Postgres | live queries that only work via optimistic local writes |
| Drain is real | Ctrl-C runs the same three phases production runs — `holdUntilShutdown` installs core's signal handlers and waits on the drain's first phase, then releases the embedded Postgres, the worker and the watcher. There is no `x dev restart` subcommand | reconnect bugs, unfinished steps |
| Role logs are prefixed and filterable | `x dev --role worker` isolates output | log soup |

Prod runs the same code with `ROLE` set per container. Nothing in the framework has a `if (dev)` behavioral branch — only different drivers behind the same interfaces.

## HMR that keeps state

Sub-second, and your app state survives the edit.

| Change | Reload behavior |
|---|---|
| Solid component | swapped in place; **signals keep their values** — form input, scroll, open modal all survive |
| SCSS module | stylesheet replaced, no JS reload at all |
| `action` / `query` | server module hot-swapped; the typed client re-derives its types; open subscriptions re-run their `sql` |
| `entity` / migration | nothing is generated or applied unasked. A saved entity ahead of the migrations turns the generation red with `X_DB_DRIFT`, whose fix is `x db gen "describe the change" && x db migrate`; run beside a live `x dev`, `x db migrate` is applied **by that dev server** (`POST /_x/db/migrate` — the embedded database takes one writer, and it is the process holding it), with no stop and no restart. Where that process cannot take the pass, the fix it prints is the stop form instead: `x stop --json && x db migrate && x dev`. `As of 2026-11-19` (`packages/cli/src/dev-rebuild-schema.ts`, `dev-db-migrate.ts`) |
| `app.config.ts` | full restart (config is validated at boot) |
| `route` config | route table rebuilt, `sw.js` regenerated (the second half is designed, not shipped — [#362](https://github.com/developerz-ai/ultimate/issues/362)) |

Why it works: Solid has no VDOM and no component-level re-execution. A component is a one-time setup function that wires signals to DOM nodes, so replacing a component's *body* does not require replaying a render tree or reconciling children. Contrast frameworks where fast-refresh remounts a subtree and drops its state — the fine-grained model makes state preservation the default rather than a best-effort heuristic.

## The error contract

Stable code + cause + exact fix command + `--json`. Same string in terminal, browser overlay, and MCP response.

```ts
throw new UltimateError({
  code: 'X_DB_DRIFT',
  cause: 'table "posts" has column "publish_at" not present in any migration',
  fix: 'x db gen "add publish_at"',
});
```

```
X_DB_DRIFT: schema differs from migrations
  cause: table "posts" has column "publish_at" not present in any migration
  fix:   x db gen "add publish_at"
```

| Rule | Reason |
|---|---|
| Codes are `SCREAMING_SNAKE`, prefixed `X_` | greppable, stable across versions, linkable to docs |
| Every package declares its codes in `src/errors.ts` | no anonymous failures |
| **Never throw a bare `Error`** | Biome fails the build on it |
| `fix` must be a runnable command or a one-line edit instruction | "check your configuration" is not a fix |
| Identical rendering in terminal / overlay / `--json` / MCP | an agent and a human debug the same string |

## One inferred type chain

Write the schema once. Nothing downstream is hand-typed and nothing needs a codegen step you can forget.

```text
entity + invariants           entity('posts', { columns, invariants })   apps/web/app/posts/entity.ts
  ↓ derived, no ORM
row type                      type Post = typeof posts.$row
  ↓ inferred
action input/output           action({ input: t.object({...}), output: PostView })
  ↓ inferred
typed client + MCP tool       await publishPost({ postId })    /    tool "publishPost"
  ↓ inferred
Solid component props         <PostCard post={post} />
```

| Break the chain | What fails, immediately |
|---|---|
| Rename a column | the entity type changes → the action's output no longer matches → the component prop errors — all at typecheck, before any test runs |
| Drop a column still used in a query | `X_DB_DRIFT` from `x verify`'s `drift` step + a type error at the query |
| Change an action's input shape | typed client callers error; `contract diff` flags it as breaking if the action is published |
| Add a required field | every call site errors, including generated MCP schema tests |

One rename, N errors, all pointing at real work. No runtime surprises and no "regenerate types" step — the manifest and OpenAPI are emitted from the same inference during `x dev` and `x build`.

## Typed env, validated at boot

`defineEnv` (from `@ultimat3/core`) takes a plain `EnvSchema` — a record of declarations, not a
`@ultimat3/schema` object — because env vars are always strings on the wire and need type
coercion (`number`/`port`/`boolean`/`enum`), a `role` gate, and `secret` redaction that a generic
object schema has no vocabulary for:

```ts
// app.config.ts — module scope, so importing the config is what parses the environment. The
// declaration is the `envSchema` export: `defineEnv` returns values, and every `x env` command
// reads the record back by that name.
import type { EnvSchema } from '@ultimat3/core';
import { defineEnv } from '@ultimat3/core';

export const envSchema = {
  DATABASE_URL: { type: 'url' },
  NATS_URL:     { type: 'url', role: 'worker' },
  S3_BUCKET:    { type: 'string' },
  VAPID:        { type: 'string', required: false },
  STRIPE_KEY:   { type: 'string', pattern: /^sk_/, secret: true },
} satisfies EnvSchema;
export const env = defineEnv(envSchema);
```

```text
X_ENV_MISSING: required environment variables are missing or invalid
  cause: STRIPE_KEY is missing (expected a non-empty string); NATS_URL is not an absolute URL (received a string of 4 characters)
  fix:   echo 'STRIPE_KEY=<value>' >> .env.development.local   # STRIPE_KEY: a non-empty string; also malformed, where grep -n -e '^NATS_URL=' .env* finds them: NATS_URL (an absolute URL)
```

The fix is the line to add and the file this environment loads: `.env.development.local` in
development (`.env.test.local` under test), `.env.production` for a deploy — never `x env check`,
which prints this same error, and never `.env`, which the scaffold does not write. A rejected value
is described by its shape, never printed.

| Property | Value |
|---|---|
| When | first thing at boot, before any listener binds |
| Cost of failure | ~40ms and exit 1 — **not a 3am `undefined` in a payment handler** |
| Access | `env.STRIPE_KEY` is typed, and the declaration is the only place its type is written |
| Per-role | `role: 'worker'` requires the key for that role only, so a `web` replica does not fail on `NATS_URL` |
| Where | `app.config.ts`, at module scope. There is no `env.ts` convention — one config file is also one root marker |

`x env check` **ships** `As of 2026-08` — `checkProcessEnv` parses the process's environment against
the app's declared schema, and it is the bare `x env`'s default subcommand. Which environment it
answers for, `As of 2026-11-19`: the one named (`ULTIMATE_ENV`, else `NODE_ENV`) — always; with
neither set, **development**, exactly as `x dev` in the same directory declares it, and the summary
says so and names `ULTIMATE_ENV=production x env check` for the deploy's answer; with neither set
under `CI`, production, because the boot fails closed and CI is where a deploy's table is checked. `x env example` writes the
`.env.example` the schema implies, and `x verify`'s `manifest` step refuses a committed one that has
drifted from it. What `x verify` has no step for is the **process** environment: that gate is the
boot parse above, which is why it runs before the first listener binds.

`X_ENV_MISSING` is the one code for the whole env gate — every offending key (missing or
malformed) is reported in one throw, not one exception per key. `X_CONFIG_INVALID` is a
different failure entirely: it is `app.config.ts` itself failing its own schema (bad
`defaultLocale`, `db.pool < 1`, a non-IANA `timeZone`), not an environment variable — see
[Configuration](../../wiki/Configuration.md).
