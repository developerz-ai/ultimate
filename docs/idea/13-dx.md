# Developer experience

## The first 60 seconds

```
bunx create-ultimate myapp && cd myapp && x dev
```

```
✓ postgres    embedded, migrated, seeded         420ms
✓ nats        in-process                           2ms
✓ storage     ./.x/storage (S3 API)                1ms
✓ roles       web sync worker scheduler replicator (one process, isolated)
✓ site/       12 routes   static   0kb js
✓ app/        3 routes    stream
✓ mcp         ws://localhost:9229
  http://localhost:3000        →  landing page (site/)
  http://localhost:3000/app    →  dashboard (app/)
  http://localhost:3000/_x     →  dev dashboard
  ready in 1.1s
```

**No Docker. No env scavenger hunt.**

| Dependency | In dev | In prod |
|---|---|---|
| Postgres | embedded, downloaded once, data in `.x/pg` | real Postgres |
| NATS | in-process, same API | NATS / JetStream |
| S3 | `./.x/storage`, real S3 API surface | `Bun.s3` against any S3 |
| Mail | captured in the `/_x` inbox, never sent | SMTP / provider |
| Redis (cache tier 3) | in-process map behind the same interface | `Bun.redis` |
| Secrets | generated dev values with a loud "dev only" prefix | env / mounted file |

`x new` writes `.env` complete and valid. There is no `.env.example` to diff, no "ask a teammate for the keys" step, and no service you must install first. The dev drivers implement the same interfaces as production, so switching to `docker/compose.dev.yml` for a parity check is a one-line change ([`12-build-deploy.md`](./12-build-deploy.md)).

## `x dev` runs all roles in one process

One Bun process, every role, **isolation simulated rather than skipped**:

| Simulated | How | Catches |
|---|---|---|
| Separate role contexts | each role gets its own ALS context, DB pool, and logger tag | code accidentally sharing in-memory state across roles |
| No cross-role imports | a `worker`-only module imported from a `web` handler is a build error | "works in dev, missing in prod" |
| Queue is real | the Postgres queue with real claiming and leases | jobs that only work when awaited inline |
| Replication is real | logical replication against the embedded Postgres | live queries that only work via optimistic local writes |
| Drain is real | `x dev restart` runs the SIGTERM sequence | reconnect bugs, unfinished steps |
| Role logs are prefixed and filterable | `x dev --role worker` isolates output | log soup |

Prod runs the same code with `ROLE` set per container. Nothing in the framework has a `if (dev)` behavioral branch — only different drivers behind the same interfaces.

## HMR that keeps state

Sub-second, and your app state survives the edit.

| Change | Reload behavior |
|---|---|
| Solid component | swapped in place; **signals keep their values** — form input, scroll, open modal all survive |
| SCSS module | stylesheet replaced, no JS reload at all |
| `action` / `query` | server module hot-swapped; the typed client re-derives its types; open subscriptions re-run their `sql` |
| `entity` / migration | `x db gen` prompt, then apply to the dev DB; live queries resubscribe |
| `app.config.ts` | full restart (config is validated at boot) |
| `route` config | route table rebuilt, `sw.js` regenerated |

Why it works: Solid has no VDOM and no component-level re-execution. A component is a one-time setup function that wires signals to DOM nodes, so replacing a component's *body* does not require replaying a render tree or reconciling children. Contrast frameworks where fast-refresh remounts a subtree and drops its state — the fine-grained model makes state preservation the default rather than a best-effort heuristic.

## The error contract

Stable code + cause + exact fix command + `--json`. Same string in terminal, browser overlay, and MCP response.

```ts
throw new UltimateError({
  code: 'X_DB_DRIFT',
  cause: 'table "posts" has column "publish_at" not present in any migration',
  fix: 'x db gen "add publish_at"',
  docs: 'https://ultimate.dev/errors/X_DB_DRIFT',
});
```

```
X_DB_DRIFT: schema differs from migrations
  cause: table "posts" has column "publish_at" not present in any migration
  fix:   x db gen "add publish_at"
```

| Rule | Reason |
|---|---|
| Codes are `SCREAMING_SNAKE`, prefixed `X_` | greppable, stable across versions, linkable to docs |
| Every package declares its codes in `src/errors.ts` | no anonymous failures |
| **Never throw a bare `Error`** | Biome fails the build on it |
| `fix` must be a runnable command or a one-line edit instruction | "check your configuration" is not a fix |
| Identical rendering in terminal / overlay / `--json` / MCP | an agent and a human debug the same string |

## One inferred type chain

Write the schema once. Nothing downstream is hand-typed and nothing needs a codegen step you can forget.

```text
entity + invariants           entity('posts', { columns, invariants })   packages/db/src/schema/posts.ts
  ↓ derived, no ORM
row type                      type Post = typeof posts.$row
  ↓ inferred
action input/output           action({ input: t.object({...}), output: PostView })
  ↓ inferred
typed client + MCP tool       await publishPost({ postId })    /    tool "publishPost"
  ↓ inferred
Solid component props         <PostCard post={post} />
```

| Break the chain | What fails, immediately |
|---|---|
| Rename a column | the entity type changes → the action's output no longer matches → the component prop errors — all at typecheck, before any test runs |
| Drop a column still used in a query | `x db drift` + a type error at the query |
| Change an action's input shape | typed client callers error; `contract diff` flags it as breaking if the action is published |
| Add a required field | every call site errors, including generated MCP schema tests |

One rename, N errors, all pointing at real work. No runtime surprises and no "regenerate types" step — the manifest and OpenAPI are emitted from the same inference during `x dev` and `x build`.

## Typed env, validated at boot

`defineEnv` (from `@ultimat3/core`) takes a plain `EnvSchema` — a record of declarations, not a
`@ultimat3/schema` object — because env vars are always strings on the wire and need type
coercion (`number`/`port`/`boolean`/`enum`), a `role` gate, and `secret` redaction that a generic
object schema has no vocabulary for:

```ts
// app.config.ts — module scope, so importing the config is what parses the environment
import { defineEnv } from '@ultimat3/core';

const env = defineEnv({
  DATABASE_URL: { type: 'url' },
  NATS_URL:     { type: 'url', role: 'worker' },
  S3_BUCKET:    { type: 'string' },
  VAPID:        { type: 'string', required: false },
  STRIPE_KEY:   { type: 'string', pattern: /^sk_/, secret: true },
});
```

```text
X_ENV_MISSING: required environment variables are missing or invalid
  cause: STRIPE_KEY is missing (expected a string matching /^sk_/); NATS_URL="nats:4222" is not a url
  fix:   add STRIPE_KEY NATS_URL to .env (copy .env.example), then run: x env check
```

| Property | Value |
|---|---|
| When | first thing at boot, before any listener binds |
| Cost of failure | ~40ms and exit 1 — **not a 3am `undefined` in a payment handler** |
| Access | `env.STRIPE_KEY` is typed, and the declaration is the only place its type is written |
| Per-role | `role: 'worker'` requires the key for that role only, so a `web` replica does not fail on `NATS_URL` |
| Where | `app.config.ts`, at module scope. There is no `env.ts` convention — one config file is also one root marker |

`x env check` is **planned**, `As of 2026-08`: it exits `X_NOT_IMPLEMENTED` with `fix: x doctor --json`,
and `x verify` has no environment step. The gate that exists today is the boot parse above, which is
why it runs before the first listener binds rather than in CI.

`X_ENV_MISSING` is the one code for the whole env gate — every offending key (missing or
malformed) is reported in one throw, not one exception per key. `X_CONFIG_INVALID` is a
different failure entirely: it is `app.config.ts` itself failing its own schema (bad
`defaultLocale`, `db.pool < 1`, a non-IANA `timeZone`), not an environment variable — see
[Configuration](../../wiki/Configuration.md).
