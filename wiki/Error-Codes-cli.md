# Error codes: `@ultimat3/cli`

Part of [Error codes](Error-Codes): every code `@ultimat3/cli` registers. `x errors explain <CODE> --json` prints the same row.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_ADMIN_RESOURCE_UNWIRED` | an admin override x g wrote is not in the app's defineAdmin() call | x g resource --admin writes the override and lists it under resources: in apps/admin/app/admin/admin.ts; that file is missing or holds no defineAdmin({ … }) call the generator can add to | `x g resource widget --admin --dry-run --json` — lists the files; the finding names the two lines to add to apps/admin/app/admin/admin.ts |
| `X_ADMIN_UNSCANNED` | a defineAdmin() declaration sits outside the app scan, so the admin is never mounted | the admin lives under apps/<app>/src/, which no boot imports — the app scan reads apps/*/{site,app,api,shared}/** only | `git mv apps/admin/src/index.ts apps/admin/app/admin/admin.ts` — then repoint its relative imports and x verify --only manifest --json |
| `X_ADVISORY_FLOOR_UNMET` | a resolved dependency is below its advisory floor | bun.lock resolves a package below the first release past its published advisories | `bun update source-map-js immutable` |
| `X_APP_EMPTY` | an app with an app.config.ts registered no primitive | the loader imported nothing — an app whose absolute path contained `.test.` read every module as a test — so manifest, `x db gen`, policy and i18n all checked nothing | `x doctor --json` |
| `X_APP_IMPORT_UNRESOLVED` | an app module imports what does not resolve | A module under the app globs imports a package nobody installed, or a relative path with no file behind it. One finding per specifier, however many modules reach it | `bun add <pkg>` — a relative import: edit it in the file the finding names |
| `X_APP_MIGRATIONS_UNAPPLIED` | a serving role booted over a database missing migrations this build ships | this build ships migrations the database has not applied, so serving would fail on the first statement naming a column they add: the migrate step must run first | `x db migrate --json` |
| `X_APP_MODULE_LOAD_FAILED` | an app module failed to load, so the role refused to serve a partial app | a module under apps/* threw on import or on registration in the container boot; serving without it would drop its routes, actions, policies or jobs | `x manifest --json` — names each module that does not load and why; fix it, then restart the role |
| `X_APP_NAME_EMPTY` | the app name has no letters or digits | a name that slugifies to nothing (`!!!`) names no directory, so `x new` scaffolded into the current one — and `--force` then committed the files already there | `x new my-app --json` — a name with letters or digits; it becomes the directory |
| `X_APP_PACKAGE_INVALID` | the app's `package.json` has no usable `name`/`version` — the manifest never fabricates `app@0.0.0`, because its version is the compatibility gate | a malformed or hand-trimmed `package.json` | `bun pm pkg set name=<app> version=0.1.0` |
| `X_APP_ROOT_NESTED` | a second app.config.ts inside the app | An app.config.ts under apps/ or packages/ makes that workspace a second app root — its own registry, its own migrations, its own image. One repository is one app: every apps/* workspace boots in the one image, ROLE picks the process, and packages/db/migrations is the one migration owner | `x verify --only drift --json` — after deleting the nested app.config.ts and moving what it configured into the root app.config.ts |
| `X_APP_URL_PORT_MISMATCH` | APP_URL names a loopback port x dev does not serve | APP_URL is a localhost origin whose port is not the one x dev binds (--port, then PORT, then 3000), so OAuth redirects, absolute links and the sync origin point at a server that is not this one | `export APP_URL=http://localhost:3000` |
| `X_ASSET_RETAIN_FAILED` | Build assets were not retained | publishing this build to the retained-asset disk failed | `x doctor --json` |
| `X_ASSET_RETAIN_UNDECLARED` | A served build keeps no earlier build's assets | a web role booted outside development and test with no assets.retain in app.config.ts: across a rolling deploy, or after one, a page can name a stylesheet or island chunk the answering replica 404s | `edit app.config.ts: add assets: { retain: { disk: 'assets', builds: 3 } }, naming a disk your defineStorage({ disks }) declares that every web pod reads` |
| `X_ASSET_VARIANT_UNDECLARED` | an /assets image variant responsiveImage() never mints | ?w=, ?f= or ?q= on a hashed /assets URL names a width, format or quality outside the declared set for that source (usableWidths over DEFAULT_WIDTHS, DEFAULT_FORMATS, no quality), or the file is not a raster the pipeline decodes | `responsiveImage({ src: asset('assets/hero.png'), width, height, alt })` — no widths/formats override for a site asset; an upload under /media answers any width |
| `X_BACKFILL_SLICE_ENTITY` | the slice holds no entity a generated backfill can sweep | x g backfill --feature <slice> writes a sweep over the slice's own scaffolded table (db.<plural>, its title column); the slice exists and its entity.ts declares other tables, so the generated files would not compile | `x g job <name> --feature <slice>` — then wrap its body in backfill({ source: db.<your table>, … }) from @ultimat3/jobs |
| `X_BOUNDARY_ADAPTER_IMPORT` | an app module imports an adapter installer | a site/app/api/shared module imports @ultimat3/<pkg>/adapter at runtime | `export const runtime = { jobs: yourDriver } satisfies RuntimeOverrides;   # in apps/web/runtime.ts — name the port your import installed` |
| `X_BOUNDARY_APP_TO_API` | `app/` imported `api/` at runtime | a value import instead of `import type` | use `import type`, and call the typed client |
| `X_BOUNDARY_LOADER_IMPORT` | an app module imports a registration loader | a site/app/api/shared module imports @ultimat3/action/loader or @ultimat3/query/loader — registerAction(s)/registerQuery(ies) are the boot's, and calling one is a second registration path beside defineApi | `export const api = defineApi({ actions: [yourActions], queries: [yourQueries] });` — in apps/web/api/index.ts — list the module there, then delete the loader import |
| `X_BOUNDARY_PACKAGE_TO_APP` | packages/ imported apps/ at runtime | A file under packages/ imports a module of an app: a shared package that depends on one app is no longer shared, and the import graph has a cycle no tier names | `x verify --only boundaries --json` — after moving the shared code into the package, or importing in the opposite direction |
| `X_BOUNDARY_ROUTE_TO_DB` | a route touched the database | SQL in a page file | `x g query <route-name> --feature <slice>` when the import resolves into a slice, `x g resource <name>` when none; then call it from the route |
| `X_BOUNDARY_SERVICE_TO_HTTP` | a service imported HTTP | request awareness inside business logic | take the values as arguments so a job can reuse the service |
| `X_BOUNDARY_SHARED_LEAF` | `shared/` imported a surface | `shared/` is a leaf | invert the dependency |
| `X_BOUNDARY_SITE_TO_APP` | `site/` imported `app/` | the classic transitive import | the chain is printed in `cause`; break it at the named hop |
| `X_BOUNDARY_SURFACE_IMPORT` | a surface imports one SURFACE_SPECS does not allow | an import between surfaces the table does not list | move the imported code into shared/ and import it from there — then x verify --only boundaries --json |
| `X_BROWSER_SERVER_BARREL` | browser-reachable code imports a package's server barrel where the package publishes a browser entry | an island's import closure reaches, for example, `@ultimat3/entity`, whose barrel retains ~1 MB of SQL rendering and `@ultimat3/db`, while `@ultimat3/entity/record` is the entry published for a browser (`@ultimat3/query` → `@ultimat3/query/client`). The browser entries are derived from each installed manifest's `exports` (a `record`, `browser` or `client` subpath, `packages/cli/src/server-barrels.ts`), never listed. Reported by `x verify`'s `boundaries` step in every app, `As of 2026-10` | `x verify --only boundaries --json` — each finding opens with its edit: the import swapped to the browser entry it names (`@ultimat3/query/client` for `@ultimat3/query`), or the cut where the island first reaches the barrel |
| `X_BROWSER_TRANSPORT_BYPASS` | browser-reachable code opens its own connection instead of using the one seam | a `fetch(` call, `new WebSocket(`, `new XMLHttpRequest(` or `new EventSource(` — or the global `fetch` handed on as a value (`rpc({ fetch })`, `fetch: fetch`, `const f = window.fetch`, `make(globalThis.fetch)`; a property named `fetch`, a local binding and a type position are not) — in an island or a module one reaches (its import closure, followed name by name through barrels, into the app's own `packages/*`). Such a request skips the page's record store, the idempotency header and the principal fence. Reported by `x verify`'s `boundaries` step in **every app** (`As of 2026-10`; built in, not a `guards/` file, so an app cannot delete it) — there no file may hold one: the three seams are the framework's, inside `node_modules`, and the walk stops at that boundary. In this repository `bun run browser-transport` runs the same rule with the seams as files: `packages/core/src/client-dispatch.ts` for `fetch`, `packages/realtime/src/browser-socket.ts` for sockets, `packages/storage/src/upload-client.ts` for XHR, nothing for `EventSource`; the service worker's files are exempt. **Blind spots, stated:** a browser module that is no island, names no seam and is imported by neither; a request made inside an installed package; a computed member (`globalThis['fetch']`); a bare `fetch(` in a file that binds a local `fetch`. A `route.ts`, a job and a test are server code and never reported | `x verify --only boundaries --json` after replacing the call the finding names: an action → `await browserClient.<action>(input)` (`rpc<Api['actions']>` in `apps/web/shared/browser-client.ts`); a read → `useQuery(<QUERY_REF>, input)`; a socket or SSE → `useQuery` / `useChannel`; a file → `uploadFile({ file, grant })` from `@ultimat3/storage`; anything else → `clientTransport({ method, url })` from `@ultimat3/core/page`; a `fetch` passed as a value → delete it (`rpc()` and `queryClient()` send through `clientTransport` when given none) and move the module that took it onto one of the above |
| `X_BUDGET_PARAMS_UNDECLARED` | a dynamic route with a budget declares no prerender() paths to weigh it by | The budgets step: the build renders an app/ route only to weigh it, and a route with params needs one real path to render | add prerender: () => [{ <param>: '<a real value>' }] to the route's defineRoute, then x build --target static |
| `X_BUDGET_UNMEASURED` | a route declares a budget the build never measured | the route is absent from `.x/build-stats.json`, or the file was written by an earlier measurement rule than this gate's (its `measuredBy` is not `BUILD_STATS_RULES`), so its numbers are not this gate's to read. `.x/` survives framework upgrades. `x verify`'s `budgets` step builds when the stats are missing or stale, so inside the gate this means a static build ran and wrote no stats (`apps/web/prerender.ts` must call `prerenderSite()`) | `x build --target static --json && x verify --json` |
| `X_BUILD_ENTRY_MISSING` | the build target's entry file is not in the app | an app scaffolded before `x new` wrote `apps/web/server.ts` and `apps/web/prerender.ts`, or one whose `docker/Dockerfile` was deleted — refused before the builder is spawned, because `bun build`'s own "module not found" names no owner | the `fix` names the file; `x new <name> --dry-run --json` lists every entry a build needs |
| `X_BUILD_FAILED` | `x build` failed | a static check or the bundler. For a browser entry the framework builds, the cause names which: an island file, the `sync worker` or the `page boot` | read `cause`; the failing step is named. For a framework script: `bun build --target browser --format iife <entry>` |
| `X_BUILD_OUT_UNSAFE` | the static export directory is not one a build may empty | every static build empties its export directory first, and this one is the app root, an ancestor of it, or an existing non-empty directory that carries no `.x-export` marker a previous build wrote (the default `.x/static` is exempt) — `--out apps`, `--out .x` (the dev database), a home directory. Nothing is removed | `x build --target static --out .x/static --json` |
| `X_BUN_VERSION` | Bun is older than the framework floor | the runtime is below the floor — `x doctor` checks the CONSUMER floor (`packages/cli/src/app-root.ts`), `scripts/setup.ts` checks the CONTRIBUTOR floor, which tracks CI's pinned series and is higher | `bun upgrade` |
| `X_CATALOG_SLOT_MISMATCH` | two locales define one key with different interpolation slots | a translation added or dropped a slot: the two values interpolate different sets of names, so one locale renders a placeholder the other never had. The sets are compared by name, and their order does not matter | `x i18n check --json` — the finding names the locale, the key and the slots that differ |
| `X_CATALOG_UNTRANSLATED` | a locale still carries the reference locale's value | a value copied from the reference catalog and never translated. A value of 24 characters or less is legitimate — Postly, Free and Blog read the same in every language — and is not reported | `x i18n check --json` — the finding names the locale and the key still carrying the reference value |
| `X_CHART_MISSING` | x g chart-alerts found no Helm chart to write into | the app has no docker/helm/Chart.yaml with a name: it deploys with Compose or outside Kubernetes, or its chart lives elsewhere — and a rule loader outside Kubernetes takes the plain rule groups instead | `x g chart-alerts --print --json` |
| `X_CI_RUN_NOT_FOUND` | no workflow run for this branch | `x ci` on a branch that has never been pushed, whose runs have aged out, or whose `--workflow`/`--event` filter matched nothing (the cause names the filter given) | `x ci --branch main --json` |
| `X_CLIENT_EDITED` | a generated client file was changed by hand | a file x client wrote no longer hashes to the value in its own header, so the next regeneration would silently discard the edit | `x verify --only drift --json` — regenerate with the command the finding names, and keep custom code in a file of your own that wraps the client |
| `X_CLIENT_SPEC_INVALID` | x client was handed a document that is not OpenAPI 3.0 or 3.1 | the file or URL given to --from is not JSON, or is JSON without an openapi field of 3.0.x or 3.1.x | `x help client --json` — then point --from at the OpenAPI 3.0 or 3.1 document itself |
| `X_CLIENT_SPEC_UNSUPPORTED` | x client met an OpenAPI construct its compiler refuses | the source document uses a construct the compiler does not read (the cause names its JSON pointer): not, if/then/else, patternProperties, a non-JSON body, a cookie parameter | `x help client --json` — then rerun with --only naming the tags around the pointer the cause names, or pin a corrected source.json |
| `X_CLIENT_STALE` | a generated client is older than the document it was compiled from | the source document (a vendor's source.json, or the app's openapi.json) changed and the client was not regenerated, so it still calls the old contract | `x verify --only drift --json` — each finding names the line that regenerates its client |
| `X_CLI_BAD_FLAG` | flag or positional rejected | unknown flag, a bad value (`--port abc`, `--workers 4.9` — refused, never coerced), a required positional left out, or a mandatory-subcommand command called bare. A missing positional says so and names it, rather than inventing a flag that does not exist. A **well-formed** argv whose answer is still no is not this code — a `dev`-tier seed refused against production is `X_SEED_ENVIRONMENT`, because a flag code says "you typed it wrong" and sends the reader to `x help`, which is the wrong instruction there | `x help <command>`. **Use that form and not `--help` on `db` and `mcp`** — they declare no default subcommand, and the subcommand is resolved *before* the flag loop, so `x db --help` raises this same error again. Its `fix:` said exactly that until 2026-08 |
| `X_CLI_FLAG_UNREAD` | a command declares a flag no code reads | the CLI's own declarations held to each other: a `FlagSpec` the parser accepts and no file under `packages/cli/src` reads is a promise `x help` makes with nothing behind it. `x deploy --critical` said *"forces clients to reload"* and reached no reader outside the plan JSON. The four global flags are excluded — the parser owns them — and any bare `'name'` literal outside a `name:`/`short:` spec field counts as a read, so a flag echoed into `--json` still counts | `bun test packages/cli/src/flag-reads.test.ts` — the finding names the flag and the file to read it in |
| `X_CLI_UNEXPECTED` | the CLI itself failed | a bug, or a broken environment | `x doctor --json` and attach it to an issue |
| `X_CLI_UNKNOWN_COMMAND` | not a command | a typo | `x help` — the suggestion is in `fix` |
| `X_COVERAGE_BELOW_FLOOR` | the unit suite covers less of the app than x.verify.json states | Line or function coverage of the app's own source — every `.ts`/`.tsx` under `apps/` and `packages/`, a file no unit test loads counted at 0% — is under the `coverage` floor in `x.verify.json`. A test was deleted, or source landed without one. The finding names the measured and required numbers and the ten files that lose the most lines | `x verify --only unit --json` — names the ten files losing the most lines; cover the worst with a test beside it |
| `X_COVERAGE_FLOOR_STALE` | the app now covers more than the floor in x.verify.json states | A floor under 95 is more than 1.5 points below what the unit suite measures. The floor only rises: left alone it would let the next regression fall back to a number the app left behind | `x verify --only unit --json` — the finding carries the measured numbers; raise "coverage" in x.verify.json to them |
| `X_COVERAGE_FLOOR_UNSTATED` | x.verify.json states no coverage floor, or one under 95 with no reason | `x.verify.json` has no `coverage: { lines, funcs }`, so the gate has no floor to hold the unit suite to — an app is never held to a default it did not write. Also raised for a stated floor under 95 on either number that carries no `why` | `x verify --only unit --json` — the finding carries the measured numbers and the exact "coverage" line to add to x.verify.json |
| `X_DB_BRANCH_FAILED` | `x db branch` refused, or failed for a reason no framework error claimed | **two shapes under one code.** A deliberate refusal: `delete` aimed at a name `x db branch list` does not show, whose `cause` names the exact database or data directory it *would* have touched, so the refusal is checkable rather than assertable. Or an unclaimed failure of any of the three verbs — the clone connection refused, the data directory unwritable. `X_BRANCH_EXISTS` (the name is taken) and `X_SQL_UNSAFE` (the name is not `[a-z0-9_-]+`) reach you as themselves | for the refusal, `x db branch list --json` — the name is not in the set, and only what that lists can be deleted. Otherwise read `cause`, then `x doctor --json` |
| `X_DB_GEN_FAILED` / `X_DB_MIGRATE_FAILED` | the `x db` step failed for a reason no framework error claimed | a write the filesystem refused, the database unreachable. A failure the engine itself names — `X_MIGRATION_CONFLICT`, `X_MIGRATION_IRREVERSIBLE`, `X_DB_UNAVAILABLE` — reaches you as that code, with its own fix, never wrapped in these | read `cause` — it carries the underlying error verbatim — then `x doctor --json` |
| `X_DB_HANDLE_UNREGISTERED` | an entity x g wrote is not in the app's typed database handle | The generated repo.ts reads db.<table>, and packages/db/src/client.ts has no entity set the generator can add to, or packages/db/src/index.ts does not export the handle | `x g entity widget --dry-run --json` — lists the files; the finding names the two lines to add to packages/db/src/client.ts |
| `X_DB_INDEX_UNDECLARED` | Schema dump holds an index nothing declares | an index in packages/db/schema/05_indexes is in neither the newest migration snapshot nor any entity declaration; every write maintains it | `x verify --only drift --json   # each X_DB_INDEX_UNDECLARED warning names the index: its DROP INDEX CONCURRENTLY IF EXISTS "<name>"; goes in a new hand-written migration (-- transaction: false), or declare it in the entity's indexes: [...] and x db gen "<change>"` |
| `X_DB_ROW_SECURITY_OFF` | Raw sql reaches tenant tables while database.rowSecurity is off | database.rowSecurity is off and a raw sql statement in the app's source names a tenant table; the repository's tenant scope does not reach a raw statement, so one missing tenant predicate reads every tenant's rows | `database: { rowSecurity: true }` — in defineConfig, app.config.ts; then: x db gen "row security" --json && x db migrate --json && x doctor --json |
| `X_DB_SCHEMA_UNDECLARED` | a migration records schema no entity declares | the other direction, and a different repair: the database carries a constraint, column or index the entities no longer ask for. Reported separately from `X_DB_SCHEMA_UNMIGRATED` because "your database is missing this" and "your last generation lost something" are not one finding | delete the stale declaration, or `bun run x -- db gen "drop what the entities no longer declare"` if the removal is intended |
| `X_DB_SCHEMA_UNMIGRATED` | an entity declaration no migration recorded | the half `X_DB_DRIFT` cannot see: that check compares a schema-source **hash** and never reads the SQL, so a committed migration smaller than its declaration passes. Measured on `dummy/social-media-clone`, whose `drift` was GREEN while nine declared CHECK constraints had never reached any database — a comment body could be whitespace, a like count could go negative, an email needed no `@`. Compares `snapshotOf(describeEntities())` against the newest `.snapshot.json`, so it needs no database connection. Also names a table a channel with params or a live query's `subscribes:` needs `REPLICA IDENTITY FULL` on when no migration recorded it (`As of 2026-10-02`): that need is a realtime declaration, so no entity hash moves when the channel is added | `bun run x -- db gen "describe the change"` — the generated migration is additive, one `add constraint` per finding |
| `X_DB_STUDIO_FAILED` | reserved, not thrown — `studio` left `x db` `As of 2026-11-15` ([Known gaps](Known-Gaps#open-by-decision)). It shelled out to `bunx drizzle-kit studio`, a second schema engine for one subcommand | — | `x dev`, then the db panel at `/_x` |
| `X_DECLARATION_UNKNOWN` | no declaration with this name is registered | a typo, or a module that never imported. `x db seed <name>` answers with it too — a seed is a declaration, and the cause lists every seed the app does declare | `x actions list --json` (or `queries` / `entities`); `x db seed --dry-run --json` for a seed, which lists them and writes nothing |
| `X_DEPLOY_BUILD_MISMATCH` | production never served this build | no /readyz sample carried the build before --timeout passed | `x deploy verify --url https://app.example.com --build "$BUILD_ID" --json` — the id CI stamped; meta.byBuild names what answered |
| `X_DEPLOY_BUILD_UNSTAMPED` | the deployment answers with no build header | /readyz answered 2xx with no x-ultimate-build, so no sample can name a build | `x build --target docker --json` — stamps BUILD_ID into the image; or set BUILD_ID in the image's environment |
| `X_DEPLOY_ENV_MISSING` | x deploy --method compose found no complete .env.production | the app has no `.env.production`, or it leaves a `${VAR:?}` the compose file requires unset or empty, so every compose step would refuse | `x env init --production --json` |
| `X_DEPLOY_FAILED` | a deploy step failed | the compose/helm command exited non-zero | run the printed command directly for full output |
| `X_DEPLOY_QUEUE_UNSERVED` | a registered queue has no serving worker of this build | no worker row that is not draining and runs this build claims the queue | `x jobs list --json   # then WORKER_QUEUES=<queue> on a worker Deployment, or --idle-ok <queue> on the deploy verify subcommand for a scale-to-zero pool` |
| `X_DEPLOY_UNSTABLE` | the build answered but did not hold | the build answered, but the --window of consecutive good samples never closed before --timeout | `x deploy verify --url https://app.example.com --json` — samples.byStatus and samples.byBuild name what interrupted it |
| `X_DEV_ALREADY_RUNNING` | another x dev already owns this checkout | a live `x dev` holds `.x/` — embedded Postgres is a single-writer data directory, so a second one cannot open it | use the one already running, or stop it: `x stop --json` |
| `X_DEV_DATA_UNOPENABLE` | x dev set aside an embedded data directory that would not open | the embedded PGlite directory under .x/ failed to open — a crash mid-write, a PGlite upgrade or a copied directory — so x dev renamed it to <dir>.unopenable-<UTC> and booted an empty database; the old rows are in the moved directory | `x db migrate --json` — the fresh database has no tables yet; then x db seed --json if the app declares a seed. The moved directory (meta.aside) is kept: delete it once its rows are not needed |
| `X_DEV_HOST_REFUSED` | a /_x request named a host that is not this machine | the request reached x dev with a Host header that is not localhost, a *.localhost name or a loopback address, which is how a DNS-rebinding page reads the dev dashboard and its database cross-origin | `curl -sS -H 'accept: application/json' http://localhost:3000/_x` |
| `X_DEV_LOCK_UNREADABLE` | the dev lock file cannot be read or removed | `.x/dev.lock` parses as no lock and `unlink` refused it — a directory left at that path, or a file this user may not delete. Its own code because the alternative was `X_DEV_ALREADY_RUNNING` naming the READER's own pid as the holder, whose `fix:` was `kill <self>` | `rm .x/dev.lock`, then re-run `x dev` |
| `X_DEV_LOG_ABSENT` | the dev log does not exist yet | logs.tail or x logs tail found no <stateDir>/dev.log; x dev writes it | `x dev --json   # the dev server writes the dev log as it boots; then: x logs tail --json` |
| `X_DEV_PEER_REFUSED` | a /_x request came from a non-loopback peer | x dev is bound beyond loopback (--host) and a request for the dev dashboard came from another machine | `x doctor --json   # /_x answers a loopback peer only: open it on the machine the dev server runs on, or forward the port with ssh -L` |
| `X_DEV_RESTART_REQUIRED` | a save reached a module that defines a primitive; only a new process serves it | a slice service, a view under defineAdmin, or an action/query/entity/job file itself was saved, and the module that defines the primitive still holds the old code | restart `x dev` — the supervised `x dev` restarts itself; an embedded `startDev()` passes `onRestart` |
| `X_DEV_ROOT_GONE` | the app root x dev serves was deleted or moved | the directory x dev was started in was removed or renamed while it ran (a test fixture torn down, a re-clone, mv of the checkout) | x dev   # from the app root, once it exists again (restored, re-cloned or moved back) |
| `X_DEV_STATE_UNWRITABLE` | x dev cannot claim its state directory | the state directory could not be created, written, or hard-linked into, so x dev cannot take its lock — a read-only checkout, a .x/ this user may not write, or a filesystem without hard links | `ls -ld .x` — make it writable by this user, on a filesystem that supports hard links, then re-run x dev |
| `X_DEV_STOP_DENIED` | x stop may not signal the x dev the lock names | the pid in .x/dev.lock belongs to another user, so SIGTERM is refused with EPERM | `ps -o user= -p <pid>, then run x stop --json as that user` |
| `X_DEV_STOP_TIMEOUT` | x stop sent SIGTERM and x dev did not exit in time | the x dev the checkout lock names is still running when the wait ends: a drain past its deadline, or a process that ignores SIGTERM | `x stop --timeout 2m --json`; still running: `kill -9` the pid its cause names, then `x dev --json` (a hard kill leaves the lock, which the next boot clears) |

| `X_VERIFY_STEP_UNFLOORED` | A gate step applies to this app but x.verify.json does not floor it | the step has suite files or committed input here, and x.verify.json "steps" does not hold it, so a deleted suite reads as skipped and the gate stays green | `x doctor --json` — its X_VERIFY_STEP_UNFLOORED fix names the steps: run that x verify --only, then add each step that passed, not skipped, to "steps" in x.verify.json |
| `X_VERIFY_STRICT_UNRUN` | x.verify.json is strict and a step ran no check with no written why | x.verify.json sets strict: true and a step ran no check (it did not apply, or its suite skipped every test) with no skip entry giving the reason | `x verify --json   # data.skipReasons names each step that ran no check: give it a suite, or write "skip": { "<step>": "<why>" } in x.verify.json` |
| `X_VERIFY_SUITE_VANISHED` | a step the committed floor requires had nothing left to check | `x.verify.json` names a step this repo already ran and the step found nothing — either its suite was deleted (the step reports as skipped) or every test in the files it did find skipped itself, which `applies` cannot see and only `bun test`'s own summary reports. Both are a green gate over an unrun suite | restore the suite or set what it skips without (`TEST_DATABASE_URL` for `live`), or delete that name from `x.verify.json` in the commit that says why — then `x verify --json` |
| `X_WORKER_QUEUE_UNKNOWN` | WORKER_QUEUES names a queue no job and no jobs.queues entry declares | a typo, or a pattern (banks-*) the app meant to expand before the worker read it — the worker would claim a queue nothing is ever enqueued on and leave the real ones waiting | `x jobs list --json   # set WORKER_QUEUES to queues it lists, or add the queue to jobs.queues in app.config.ts` |
| `X_WORKSPACE_DEP_UNDECLARED` | a workspace imports another workspace its own `package.json` does not declare | an import added long after the scaffold, or a generator that emitted the import and not the edge. The graph then exists only inside `tsc` — affected-package detection, `bun --filter` ordering and blast radius all read manifests, and a missing edge makes each of them silently answer too small a set. Shipped source only: a test file's import is not judged, because `packages/*` here declares no `devDependencies` by design and the root's hoist is what resolves them | add the dependency the finding names — it carries the manifest path and the exact line, e.g. `"@demo/web": "0.0.0"` |
| `X_WORKSPACE_EXTERNAL_DEP_UNDECLARED` | a workspace imports a registry package that neither it nor the app root declares | a workspace imports a package only a sibling workspace declares; it resolves through the hoisted node_modules until a clean or filtered install stops hoisting it | `bun add <package> --cwd <workspace>` — the package-shape finding names both |
| `X_WORKSPACE_NAME_TAKEN` | x g app or x g package was given a name the other workspace kind already holds | apps/<name> and packages/<name> are both named @<scope>/<name>, so a second workspace under one name is two packages bun install cannot tell apart | `x g app admin-app --dry-run --json` |

## Notes

### Encrypted secrets

One committed file, `secrets.enc.json`, sealed with AES-256-GCM under a 32-byte master key read from `ULTIMATE_SECRETS_KEY` first and the gitignored `.secrets.key` second. Values are decrypted into the process environment by `installSecrets()` and read back through the app's own `envSchema` — a secret is an env var, so it has one declaration, one mask and one reader. See [CLI reference](CLI-Reference) for `x secrets`.

The envelope carries a **key id**: a domain-separated, truncated SHA-256 of the master key, safe to commit. It is what makes "you used the wrong key" and "this file was edited after it was sealed" two different codes instead of one unexplained decryption failure.
