# Error codes

Every framework failure is an `UltimateError` carrying a stable `X_*` code, a concrete cause, and the exact command or edit that fixes it. Same content in the terminal, the dev overlay, the HTTP body, the MCP tool result and `--json`.

```text
X_DB_DRIFT: schema differs from migrations
  cause: table "posts" has column "publish_at" not present in any migration
  fix:   x db gen "add publish_at"
```

```json
{"code":"X_DB_DRIFT","title":"schema differs from migrations","cause":"table \"posts\" has column \"publish_at\" not present in any migration","fix":"x db gen \"add publish_at\"","docs":"https://github.com/developerz-ai/ultimate/wiki/Error-Codes"}
```

| Rule | Detail |
|---|---|
| Lookup | `x errors explain <CODE> --json`, or the MCP `errors.explain` tool — same content as this page |
| Uniqueness | one code is owned by exactly one package; a collision throws `X_ERROR_CODE_DUPLICATE` at registration |
| Stability | codes never change meaning. A renamed concept gets a new code and the old one stays documented |
| `fix` | always runnable or editable as written. If a fix reads "do the right thing", that is a bug — [file it](https://github.com/developerz-ai/ultimate/issues) |
| Bare `Error` | never thrown by the framework. Anything caught is normalised through `toUltimateError()` |
| Registration | a code exists when its owning package calls `registerErrorCodes()`. That one call is what makes it explainable, unique and documented-or-fail — a code emitted as a `Finding` rather than thrown is registered the same way |
| Enforcement | the `errors` step of `x verify` fails on an empty or advice-only `fix` (`X_ERROR_FIX_INVALID`), on a `fix` citing a file the repo does not have (`X_ERROR_FIX_PATH_MISSING`), on a declared code with no row on this page (`X_ERROR_CODE_UNDOCUMENTED`), on a row this page presents as live that no package registers (`X_ERROR_CODE_UNREGISTERED`), and on a `code:` reached through a name nothing in its own file declares (`X_ERROR_CODE_UNRESOLVED`) |

## Core and runtime

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_ABORTED` | operation aborted | the `AbortSignal` on `ctx` fired: client disconnected, or a deadline passed — including a job past its `timeout`, whose steps are refused from that point on | add `throwIfAborted(ctx)` before expensive work, or pass `fetch(url, { signal: ctx.signal })` — unwind at the deadline instead of running past it |
| `X_TIMEOUT` | operation exceeded its deadline | a request that ran past the configured `requestTimeoutMs` (30s), or past the shorter budget its caller sent as `x-request-timeout-ms`. The abort fires first for cooperative code, so this is what the socket gets when the handler never looked at `ctx.signal`. Core owns the code and classifies it `retryable`; `@ultimat3/http` throws it and maps it to 504 | pass `ctx.signal` to every outbound call — `fetch(url, { signal: ctx.signal })` — and call `throwIfAborted(ctx)` before expensive work, or call `configureHttp({ requestTimeoutMs: 60_000 })` at module scope in a file under `apps/*/` |
| `X_INTERNAL` | unexpected internal framework error | a non-Ultimate error escaped into framework code | fix the failure named in `cause`, then re-run |
| `X_INVARIANT` | invariant violated | framework state that "cannot happen" happened | report it with `x doctor --json` output attached |
| `X_UNREACHABLE` | unreachable branch was reached | an exhaustive `switch` met a value the type says cannot exist | narrow the union at the call site |
| `X_NOT_IMPLEMENTED` | this driver does not implement the requested feature | an interface-complete driver whose remote half is unwritten | use the default driver, or implement the named method |
| `X_ASYNC_CONTEXT_UNAVAILABLE` | async context unavailable | `node:async_hooks` is stubbed to `{}` in this runtime, so nothing can be made ambient — a browser bundle | the scope is server-only: open it in `apps/web/server.ts` or a route handler, and keep every module that opens one out of the import graph of a client island entry |
| `X_NO_CONTEXT` | no request context is active | framework code called outside the ALS context | `runWithContext(createContext({ … }), fn)` |
| `X_SERVICE_MISSING` | service is not registered on the request context | `ctx.<service>` used without providing it | pass it in `createContext({ services: { … } })` |
| `X_SERVICE_DUPLICATE` | a service name is registered twice | two `defineService('name', ...)` calls used the same name | rename one of the two declarations |
| `X_ROLE_INVALID` | `ROLE` is not a known runtime role | typo or an old role name in the env | set `ROLE` to `web`, `sync`, `worker`, `scheduler`, `migrate` or `replicator` |
| `X_DRAINING` | process is draining and refuses new work | work arrived after SIGTERM | retry against another replica; the LB should already have removed this one |
| `X_SHUTDOWN_TIMEOUT` | graceful shutdown exceeded its deadline | an in-flight handler outlived `DRAIN_TIMEOUT` | raise `configureLifecycle({ deadlineMs })` or shorten the slow handler |
| `X_FLIGHT_GATE_OVERLOADED` | a concurrency gate is at its ceiling and its queue is full | more callers asked for a bounded resource than `createFlightGate({ maxConcurrent, maxQueued })` admits — argon2 hashes, a browser pool, any work whose cost is memory rather than CPU time. Past the queue bound the answer is a refusal and never a longer queue: an unbounded queue turns a load spike into a memory fault and answers it minutes late. `meta` carries `active`, `queued`, both bounds and `retryAfterSeconds`, so it is classified `retry-after` and `@ultimat3/http` renders the header from it | retry after the `Retry-After` header, or widen the ceiling at the `createFlightGate({ maxConcurrent, maxQueued })` call site — only if the box has the capacity the extra slots buy |
| `X_SUPERSEDED` | a later generation superseded this work | an answer came back for a generation the fence has already moved past — a reload, a resubscribe or a re-render whose predecessor finished late. Classified `terminal`, and declared rather than defaulted: re-running superseded work produces this same refusal by construction, so an unclassified reading would spend a job's whole retry policy proving that the world has still moved on | discard this answer and re-issue the work against `fence.generation()` — whoever called `bump()` has already started the replacement |
| `X_READINESS_CHECK_DUPLICATE` | a readiness check name is registered twice | two `registerReadinessCheck('<name>', check)` calls under one name. A silent replacement leaves the probe an operator believes is running unreachable, and `/readyz` green on the strength of the one that replaced it — the `cause` lists every name already registered | name the second check for what it actually probes, e.g. `registerReadinessCheck('<name>-replica', check)` — or hold the unregister the first registration returned and call it first |
| `X_LIFECYCLE_DRAINED` | a drained process cannot become ready again | a role called `markReady()` in a process whose lifecycle has already drained — a second `createServer().start()`, or a boot that started a role after SIGTERM arrived. `state` never leaves `stopped` and `drain()` memoizes, so the socket such a role binds answers 503 to every request and nothing is left to close it: measured, still accepting connections after its own `stop()` returned | start every role BEFORE the first drain — a drained process is on its way out and is replaced, never reused. In a test, call `resetLifecycle()` from `@ultimat3/core` between the drain and the next `start()` |
| `X_ERROR_RETRY_INVALID` | error retry classification is unknown or already claimed | `registerErrorRetry()` given a kind that is not `terminal`, `retryable` or `retry-after`, or a second, different classification for one code. Core's own codes are closed to reclassification: an app that could call `X_DRAINING` terminal would stop the retry a rolling restart depends on | `x errors list --json` — then `registerErrorRetry({ <CODE>: 'retryable' })` with one of `terminal`, `retryable`, `retry-after` |
| `X_ID_INVALID` | value is not a valid id | a hand-built string passed where a typed id is required | generate ids with `uuid()` / `typedId<'post'>()` from `@ultimat3/core` |
| `X_CURSOR_INVALID` | pagination cursor is malformed, tampered with or from another query | signature mismatch — an edited cursor, or `ULTIMATE_CURSOR_SECRET` rotated — or a cursor built for a different query, filter or sort order | drop the cursor and request the first page (`after: null`) |
| `X_CURSOR_SECRET_DEV` | cursors are signed with the shipped development key | `ULTIMATE_CURSOR_SECRET` is unset in a production environment, so the signing key is the constant published in `@ultimat3/core` and a client can forge a page position. Reported by `x doctor`, never thrown | `export ULTIMATE_CURSOR_SECRET="$(openssl rand -hex 32)"` |
| `X_ERROR_CODE_DUPLICATE` | error code registered twice | two packages declared the same code | rename the colliding code in the registering package's `src/errors.ts` |
| `X_ERROR_REPORTER_DSN_INVALID` | the error monitor DSN is malformed | `SENTRY_DSN` is not a URL, carries no public key, names no project, or uses a scheme that is not `http`/`https`. Thrown at boot rather than at the first failure, because a monitor that was never connected looks exactly like an app that never failed | set `SENTRY_DSN=https://<publicKey>@<host>/<projectId>` in `.env`, then run `x env check` |
| `X_REGISTRAR_MISSING` | no registrar is loaded for a primitive kind | the owning package is absent from the graph, so nothing announced a registrar — `defineApi({ queries })` without `@ultimat3/query`. `meta.kind` names the kind, and the owner is `@ultimat3/<kind>`; importing it is what announces | `bun add @ultimat3/<kind>` |
| `X_REGISTRAR_CONFLICT` | two different registrars are loaded for one primitive kind | two copies of `@ultimat3/<kind>` in the dependency tree, each with its own registry, so half the primitives register where nothing reads them. `bun pm why @ultimat3/<kind>` names the dependents when ranges genuinely disagree | `bun update @ultimat3/<kind>` |

## Metrics

Counter, gauge and histogram live in `@ultimat3/core` (`metrics.ts`), aggregate in process, and are read through one `collectMetrics()`. The wire format is a **driver**: `MetricExporter` is the seam, the default is a no-op, and `metricsText()` renders the Prometheus/OpenMetrics scrape body behind `METRICS_PATH`. An OTLP client ships `As of 2026-08`: `otlpMetricExporter()` and `otlpSpanExporter()` speak OTLP/HTTP JSON and read `OTEL_EXPORTER_OTLP_ENDPOINT`, with no new dependency. gRPC on `:4317` is refused by design; scraping `/metrics` with an agent stays equally supported.

The three series `docker/helm` autoscales on are `http_requests_total` (the counter `rps` is derived from), `connections` and `queue_depth` — `SCALING_METRICS` in `runtime-metrics.ts` maps each `ScalingSignal` to its series, so the role table and the chart cannot drift apart.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_METRIC_NAME_INVALID` | metric name is malformed, or redeclared with a different kind, bounds or observer | a name that is not lowercase `snake_case` — dotted OTel names survive OTLP but not a Prometheus scrape, and the autoscaler reads the scrape — or one name declared as both a counter and a gauge, or a second `histogram('x', { bounds })` / `gauge('x', { observe })` whose stated option differs from the first. An **omitted** option is still a handle-fetch, so `gauge(name)` keeps working | rename the instrument: `counter('http_requests_total')`, one metric name to one kind; or make the second declaration state the same `bounds`/`observe` as the first |
| `X_METRIC_VALUE_INVALID` | metric value is not recordable | a `NaN`/`Infinity` observation, or a counter decremented — a counter is a cumulative total and only goes up | pass a finite value, and use `gauge(name)` for a number that can fall |
| `X_METRIC_CARDINALITY` | a metric exceeded its series ceiling and is folding into one overflow series | an unbounded label at the call site — a user id, a path, an email — so every distinct value mints a series and the scrape grows without limit. Past `maxSeries` every further label set folds into one `otel_metric_overflow="true"` series, reported once per instrument rather than once per observation. Also raised at declaration for a `maxSeries` that is not a positive integer | drop the unbounded label from the call site, or raise it deliberately: `counter('orders_total', { maxSeries: 4000 })` |
| `X_OTLP_ENDPOINT_INVALID` | the OTLP collector endpoint is missing or malformed | `OTEL_EXPORTER_OTLP_ENDPOINT` unset with none passed, a value that is not a URL, a scheme that is not `http`/`https`, or the collector's gRPC receiver on `:4317` — OTLP/HTTP JSON is served on `:4318`, and an exporter pointed at the wrong port drops every batch with a transport error and no metrics | `set OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318`, or skip the exporter when `tryOtlpEndpoint('<signal>')` is undefined |
| `X_OTLP_HEADERS_INVALID` | `OTEL_EXPORTER_OTLP_HEADERS` is malformed | a percent-escape in one header **value** that `decodeURIComponent` cannot decode — a stray `%` meant literally (`api-key=100%`), or a truncated escape (`%zz`). Refused rather than kept raw: an operator-set variable with a bad escape is a misconfiguration, and sending the undecoded bytes would authenticate against nothing while looking like a collector outage. The header **key** is named in the `cause` and the `fix`; the value never is, because a header value is a credential | `set OTEL_EXPORTER_OTLP_HEADERS=<key>=<encoded>`, where `<encoded>` is what `bun -e 'console.log(encodeURIComponent(process.argv[1]))' <value>` prints — or drop the stray `%` if it was meant literally |
| `X_OTLP_PROTOCOL_UNSUPPORTED` | the OTLP protocol requested is not OTLP/HTTP JSON | `OTEL_EXPORTER_OTLP_PROTOCOL` asking for `grpc` or `http/protobuf`. This exporter speaks one wire format and no dependency ships a second — refused at construction rather than negotiated down | unset `OTEL_EXPORTER_OTLP_PROTOCOL` (or set it to `http/json`) and point `OTEL_EXPORTER_OTLP_ENDPOINT` at the collector's HTTP receiver, e.g. `http://otel-collector:4318` |
| `X_TELEMETRY_SAMPLER_ARG_INVALID` | the trace sampling ratio is not a number between 0 and 1 | `OTEL_TRACES_SAMPLER_ARG` holding a value outside `[0, 1]`, or one that is not a number. Read at the first span, not at boot — so it warns through the logger and samples **every** trace rather than killing a process mid-request over a sampling typo. Losing the traces silently is the worse failure; the bill is the loud one | `set OTEL_TRACES_SAMPLER_ARG=0.05` — the `cause` names the spelling it read |

## Images

One pipeline in `@ultimat3/core` serves `storage`, `seo` and `pwa`. It **decodes and encodes PNG and JPEG only**; WebP, AVIF, GIF and SVG are identified and measured — enough to inline `width`/`height` and keep CLS at 0 — but never synthesised. A variant in one of those formats comes from a CDN or an `ImageTransformDriver`, never from a silent passthrough.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_IMAGE_UNSUPPORTED` | the built-in image pipeline cannot read or write this format | a request for an AVIF or HEIC variant (both need an OS codec the pinned `backend: 'bun'` never uses), an SVG or TIFF source, or a colour that is not hex or `transparent` | `await transformImageBytes(bytes, { format: 'png' })` (or `'jpeg'`, or `'webp'`), or pass an `ImageTransformDriver` that produces the format — `meta.format` names the one refused |
| `X_IMAGE_DECODE_FAILED` | image bytes are malformed, truncated or internally inconsistent | a partial upload, a corrupted file, or a header that disagrees with the data that follows | `file <path>` to confirm the type, then re-export the image and retry |
| `X_IMAGE_TOO_LARGE` | image exceeds the pipeline pixel ceiling | a header declaring more than 64 megapixels — usually a decompression bomb, occasionally a real scan | `await transformImageBytes(bytes, { width: 4000 })` before it reaches the pipeline, or raise `MAX_IMAGE_PIXELS` deliberately |

## Config and environment

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_CONFIG_INVALID` | a configuration this process cannot boot on — env **or** `app.config.ts` | a field failed its schema, a required field is missing, or two keys that each parse contradict each other (`selectMailDriver`, `selectPurgeDriver`), or a declaration whose guarantee this build cannot enforce (`defineAuth({ mfa: { required: true } })` — nothing reads it, so believing it would be a false security claim) | `x doctor --json` and fix the named key; see [Configuration](Configuration) |
| `X_ENV_MISSING` | required environment variables are missing or invalid | a key absent at boot; validation runs before the server listens | `x env check --json`, then set the keys it names. There is no `--fix`: `x env` declares `check` and `example` and no flags of its own ([`packages/cli/src/cmd-env.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/cli/src/cmd-env.ts)), so the flagged form dies at the parser with `X_CLI_BAD_FLAG` |
| `X_ENVIRONMENT_INVALID` | `ULTIMATE_ENV` is not a known environment | a spelling the framework does not use (`prod`, `dev`, `preview`). `NODE_ENV` is only a fallback and is never policed — CI images legitimately set it to anything | `export ULTIMATE_ENV=production` — one of `development`, `test`, `staging`, `production` |
| `X_ENV_EXAMPLE_DRIFT` | `.env.example` does not declare every variable the schema requires | a key added to `defineEnv()` and not to the committed example, so the next clone boots into `X_ENV_MISSING` for a variable nobody documented | `x env example` — the example is a projection of the schema, never a second list |
| `X_BUN_VERSION` | Bun is older than the framework floor | the runtime is below the floor — `x doctor` checks the CONSUMER floor (`packages/cli/src/app-root.ts`), `scripts/setup.ts` checks the CONTRIBUTOR floor, which tracks CI's pinned series and is higher | `bun upgrade` |
| `X_NOT_IN_APP` | command must run inside an Ultimate app | no `app.config.ts` at or above the cwd | `x new myapp && cd myapp` |
| `X_PORT_IN_USE` | the dev port is taken | an unrelated process holds it — usually another project's dev server; the pid and command are named when the OS will say | `x dev --port 3001`, or kill the named pid if it is yours |
| `X_DEV_ALREADY_RUNNING` | another x dev already owns this checkout | a live `x dev` holds `.x/` — embedded Postgres is a single-writer data directory, so a second one cannot open it | use the one already running, or `kill <pid>` |
| `X_DEV_LOCK_UNREADABLE` | the dev lock file cannot be read or removed | `.x/dev.lock` parses as no lock and `unlink` refused it — a directory left at that path, or a file this user may not delete. | `X_PORT_INVALID` | `PORT` is not a TCP port number | a platform-injected `PORT` that is empty, non-numeric or out of range — never defaulted past, because a web role that quietly bound 3000 fails the platform's health probe with nothing in the log that names the cause | `docker run -e PORT=3000 <image>` |
| `X_ROLE_UNKNOWN` | `ROLE` names something that is not a role | a typo in a compose file, a Helm value or a `docker run` — one image runs every role, so the typo would otherwise start a process that serves nothing and reports healthy | `docker run -e ROLE=web <image>` — one of `web`, `sync`, `worker`, `scheduler`, `replicator`, `migrate` |

## Encrypted secrets

One committed file, `secrets.enc.json`, sealed with AES-256-GCM under a 32-byte master key read from `ULTIMATE_SECRETS_KEY` first and the gitignored `.secrets.key` second. Values are decrypted into the process environment by `installSecrets()` and read back through the app's own `envSchema` — a secret is an env var, so it has one declaration, one mask and one reader. See [CLI reference](CLI-Reference) for `x secrets`.

The envelope carries a **key id**: a domain-separated, truncated SHA-256 of the master key, safe to commit. It is what makes "you used the wrong key" and "this file was edited after it was sealed" two different codes instead of one unexplained decryption failure.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_SECRETS_KEY_MISSING` | no master key for the encrypted secrets file | `ULTIMATE_SECRETS_KEY` is unset and `.secrets.key` does not exist, while a sealed file does. Fatal at boot on purpose — an app that started without its secrets authenticates against nothing and still reports healthy | `export ULTIMATE_SECRETS_KEY="$(cat .secrets.key)"`, or `x secrets init` in a repo that has no key yet |
| `X_SECRETS_KEY_INVALID` | the master key is not 32 bytes of hex | a truncated paste, or a platform secret that carried quotes. An AES-256 key is exactly 64 lowercase hex characters | `export ULTIMATE_SECRETS_KEY="$(cat .secrets.key)"` |
| `X_SECRETS_KEY_MISMATCH` | the secrets file was sealed with a different master key | a key from another environment, or a `x secrets rotate` interrupted between its two writes. Both key ids are named in the cause | `git checkout -- secrets.enc.json`, or point `ULTIMATE_SECRETS_KEY` at the key whose id the file names |
| `X_SECRETS_FILE_MISSING` | the encrypted secrets file does not exist | `x secrets show/edit/set/rotate` in a repo that never ran `init`. Never an empty listing — "no secrets" and "no file" are different facts | `x secrets init` |
| `X_SECRETS_FILE_INVALID` | the encrypted secrets file is not a readable envelope | a merge conflict marker, a truncated write, an unknown `v` or `alg`, or a header field that is not base64. Nothing reached authentication, so this is not tampering | `git checkout -- secrets.enc.json` — the file is written only by `x secrets`, never by hand |
| `X_SECRETS_TAMPERED` | the secrets file failed its authentication tag | under a key whose id already matched, the ciphertext or the header bound into it as AAD changed after sealing. GCM refuses rather than returning garbage | `git checkout -- secrets.enc.json`, then `x secrets show --json` |
| `X_SECRETS_PLAINTEXT_INVALID` | the decrypted secrets are not a flat map of env values | an `x secrets edit` buffer saved as something other than one flat JSON object, a key that is not an environment variable name, or an empty value. Refused before sealing, so a file that opens always installs | `x secrets edit` — the buffer is `{"SESSION_SECRET": "s3cr3t"}` |
| `X_SECRETS_EDITOR_MISSING` | no `$EDITOR` to open the decrypted secrets in | neither `VISUAL` nor `EDITOR` is set. No editor is guessed — opening a decrypted file in a surprise program is the last place a default belongs | `EDITOR=nano x secrets edit`, or write one value without an editor: `printf %s "$TOKEN" \| x secrets set STRIPE_KEY` |
| `X_SECRETS_EDIT_FAILED` | the editor exited non-zero, so nothing was resealed | a crash or a deliberate abort. The buffer is discarded and the committed file is untouched | `x secrets edit` |
| `X_WORKSPACE_DEP_UNDECLARED` | a workspace imports another workspace its own `package.json` does not declare | an import added long after the scaffold, or a generator that emitted the import and not the edge. The graph then exists only inside `tsc` — affected-package detection, `bun --filter` ordering and blast radius all read manifests, and a missing edge makes each of them silently answer too small a set. Shipped source only: a test file's import is not judged, because `packages/*` here declares no `devDependencies` by design and the root's hoist is what resolves them | add the dependency the finding names — it carries the manifest path and the exact line, e.g. `"@demo/web": "0.0.0"` |
| `X_SHOT_BROWSER_MISSING` | `x shot` found no browser library in the app | `puppeteer-core` does not resolve from the app root, or resolves to a module exporting no `launch()`. The framework ships **no** browser and takes no such dependency: `@ultimat3/scraping` declares the CDP library's shape structurally (`cdp-port.ts`) and the app passes its own in, the same way `s3Driver({ client })` takes an SDK. Playwright is not an alternative — its `connectOverCDP` cannot perform the WebSocket upgrade under Bun | `bun add -d puppeteer-core` |
| `X_GH_UNAVAILABLE` | the GitHub CLI is not runnable from here | `gh` is not installed or not on `PATH`. `x pr` and `x ci` shell out to it rather than embedding an HTTP client — no new dependency, and the user's existing auth | `gh auth login` — install first from https://cli.github.com |
| `X_GH_NOT_AUTHENTICATED` | `gh` holds no credentials for this host | a fresh machine, an expired token, or a GitHub Enterprise host `gh` was never logged into. Detected from `gh`'s own refusal text, so it is never confused with a network failure | `gh auth login` |
| `X_GH_COMMAND_FAILED` | a `gh` invocation exited non-zero | the invocation and its exit code are in the cause. `gh` exits non-zero whenever a GraphQL response carries `errors`, so a partial answer never reaches the parser | the finding carries the exact `gh` invocation that failed — run it yourself to see why |
| `X_GH_RESPONSE_INVALID` | `gh`'s output is not the shape the command reads | GitHub changed a field, or a query was edited without its schema. The response is **parsed**, never cast: a `null` where an id was expected would otherwise become a resolve call against `undefined` | the finding names the field that did not parse; `x pr review --json` |
| `X_PR_NOT_FOUND` | no pull request for this checkout | `x pr` with no `--pr`, on a branch GitHub has no PR for | `x pr review --pr <n> --json`, or open one first: `gh pr create` |
| `X_CI_RUN_NOT_FOUND` | no workflow run for this branch | `x ci` on a branch that has never been pushed, or whose runs have aged out | `x ci --branch main --json` |

## Schema and validation

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_VALIDATION_FAILED` | value did not match its schema | a parse boundary rejected input | read `cause` for the failing path; correct the value or widen the schema deliberately |
| `X_SCHEMA_UNSUPPORTED` | the active schema provider cannot do this | a Standard Schema implementation without JSON Schema export | drop the `configureSchemaProvider()` call and use `t`, the shipped dependency-free builtin provider |
| `X_SCHEMA_DISCRIMINANT_INVALID` | a discriminated union member can never be dispatched to | a member of `t.discriminatedUnion('<key>', […])` that declares no literal at the discriminant, or one whose tag an earlier member already claims. Thrown where the union is **built**, not where a value is parsed: a member no tag routes to is wrong for every input, so the first import of the authoring file is the earliest honest place to say so | give the member named in `cause` a literal discriminant — `t.object({ <key>: t.literal('…'), … })` — its own value at that key, or merge the two members into one; `t.union(...)` if the members share no key |
| `X_SCHEMA_DEFAULT_UNSHAREABLE` | a schema default cannot be copied per parse | `.default(value)` where `value` holds a function, a symbol or anything else `structuredClone` refuses. Every parse that omits the field must receive its OWN copy — one shared object meant a handler's mutation became the next request's starting value — so a default that cannot be copied is refused where it is WRITTEN, at the first import of the authoring file, rather than shared and bled | pass a JSON-shaped default (plain object, array, `Date`, `Map`, `Set`), or drop `.default()` and answer the absent value in the handler |

## HTTP

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_ROUTE_NOT_FOUND` | no route matches this request | path typo, or the route was never generated | `x routes --json`, then `x g route <path>` |
| `X_METHOD_NOT_ALLOWED` | route exists but not for this method | GET against an action endpoint | call it with the method in `cause`, or add that method |
| `X_PATH_INVALID` | a path segment is not valid percent-encoding | a hand-built URL, or a value concatenated into a path instead of run through `encodeURIComponent` — `%ZZ`, a lone `%`, a truncated `%A`. Answers 400: the client wrote the path, so the client is who can fix it, and the request never reaches a handler | send the segment percent-encoded — `encodeURIComponent(value)`; a literal `%` is `%25` |
| `X_ROUTE_CONFLICT` | two routes claim the same path | a copied route file | `x routes --json`, then remove or rename one |
| `X_BODY_INVALID` | request body failed its schema | client sent the wrong shape | `x actions describe <name> --json`, then match the input schema |
| `X_UNAUTHENTICATED` | no authenticated actor for this request | the two things that produce an anonymous actor where one is needed: the request carried no `__Host-x_session` cookie, or it carried one nothing resolved. `authenticate()` answers the anonymous actor for a missing cookie rather than throwing, which is why the failure surfaces one layer later, at the surface that needed the actor. Also the code for an oauth identity a local account already holds — `@ultimat3/auth` owns it, `@ultimat3/http` only borrows it | send the `__Host-x_session` cookie with this request, and resolve it once at the boundary: `authenticate(auth, readSessionCookie(request, auth.sessions.policy))` |
| `X_FORBIDDEN` | policy denied this actor | the actor exists but the policy said no | `x policy explain <path> --json` |
| `X_RATE_LIMITED` | rate limit exhausted for this key | bucket empty. One request spends a LIST of keys — the caller's, then the tenant's when `rateLimit.tenantBucket` is declared — and stops at the first refusal, so `meta.key` names which one | retry after `Retry-After`, or raise the bucket: `configureHttp({ rateLimit: { buckets } })` at module scope in a file under `apps/*/` |
| `X_RATE_LIMIT_NOT_SHARED` | the app declared a fleet-wide rate limit and the store keeps its counters per process | `rateLimit.scope: 'shared'` against `memoryRateLimitStore()`, whose `scope` is `'process'`. `assertRateLimitScope` compares the two inside `createPipeline`, **before the socket opens** — the outcome it PREVENTS is N replicas each enforcing the full bucket, so a declared `limit: 5` costs 5 × N, silently. Also raised when `enabled: false` sits under `scope: 'shared'`: a fleet-wide limit switched off is a claim with nothing behind it | install a shared store — `createServer({ routes, rateLimitStore: postgresRateLimitStore({ executor }) })` — or drop to `scope: 'process'` and terminate the limit at a shared proxy instead |
| `X_RATE_LIMIT_BUCKET_CONFLICT` | one bucket has two declarations that disagree | an action's `rateLimit` and a `rateLimit.buckets.<name>` entry passed to `configureHttp()` name different numbers, or two routes claim one bucket name. Refused at `createServer`/`createPipeline`, **before the socket opens** — picking a winner leaves the loser a number someone reads and nothing applies. An identical restatement passes | **one edit, not a choice**: delete `rateLimit.buckets.<name>` from the app's `configureHttp()` call. The route is authoritative because it sits beside the handler and is what the OpenAPI operation publishes, so a config entry duplicating it is the copy that goes stale — the cause says so, and says which numbers came from where |
| `X_RATE_LIMIT_BUCKET_UNBOUND` | the installed limiter does not hold a bucket a route declares | a limiter passed through `PipelineDeps.limiter` was built by the app from a config that never saw the routes, so every route-declared limit silently reverted to `default` — measured before the fix: 21 of 21 requests allowed against a route declaring 5, with `ratelimit-limit: 120` on the wire. Refused rather than rebound, because a `RateLimiter` is opaque and "binding" it would mean discarding the caller's limiter **and its store**. An absent bucket table is refused exactly as a wrong one is: what cannot be shown to hold is not assumed to hold | pass the **store** and let the pipeline build the limiter — `createServer({ routes, rateLimitStore })` — so the bucket table is the one the routes registered |
| `X_RATE_LIMIT_SCOPE_UNSET` | the deployment has not said where the rate limiter keeps its counters | an enabled `rateLimit` with no `scope`, at `defineHttpConfig`. Reachable only from an embedder that builds its own config: `scope` is boot-owned, so `configureHttp()` type-refuses it and a process booted by `x dev` or `apps/web/server.ts` DERIVES it from the store it installed. `scope` used to **default** to `'process'`, so `login: { limit: 5 }` against the 3 `web` replicas this repo's own chart ships enforced 15 per window, with a green `x verify` and nothing anywhere to read. `assertRateLimitScope` only ever fired for an app that said `'shared'`, so the silent case was exactly the one nobody declared. One process is still a legal answer; it is no longer an assumed one | `defineHttpConfig({ rateLimit: { scope: 'process' } })` if this app runs as ONE replica, or `scope: 'shared'` plus `createServer({ routes, rateLimitStore: postgresRateLimitStore({ executor }) })` for a fleet-wide limit |
| `X_RATE_LIMIT_TENANT_BUCKET_UNKNOWN` | the tenant allowance names a bucket nothing declares | `rateLimit.tenantBucket: 'tenant'` with no `rateLimit.buckets.tenant` beside it. Refused at `defineHttpConfig`, **before the socket opens**, and not on the first request: `bucketFor` resolves an unknown name to `default`, so a whole tenant's cap written as 5,000 would silently be the 120-burst `default` — looser than the declaration and visible nowhere. The cause lists every bucket name that IS declared | declare the bucket beside the name — `configureHttp({ rateLimit: { tenantBucket: '<name>', buckets: { '<name>': { capacity: 5000, refillPerSecond: 100 } } } })` — or drop `tenantBucket` to leave this app with no per-tenant allowance |
| `X_RATE_LIMIT_INVALID` | a declared rate limit computes to numbers the limiter cannot run on | a `{ limit, windowMs }` pair `toBucket` cannot convert: `limit` below 1 refuses the first caller, which is a policy's job and never a rate limit's, and `windowMs: 0` or `{ limit: MAX_VALUE, windowMs: 1 }` compute an infinite refill — a bucket that never empties. Raised in `@ultimat3/http`, which owns `Bucket` and the maths, so an action's and a query's `rateLimit:` are refused by one check and not two | edit the `rateLimit:` on the declaration `cause` names to a whole allowance over a real window — `{ limit: 5, windowMs: 600_000 }` for five per ten minutes — or delete it to keep the `default` bucket |
| `X_RATE_LIMIT_STORE_UNAVAILABLE` | the shared rate-limit store did not answer, so nothing decided | the `PgExecutor` handed to `postgresRateLimitStore` returned no row for a statement whose `returning` clause always produces one — a swallowed driver error, a pooler that dropped the statement, or an executor that maps `returning` away. Raised rather than defaulted: a limiter that cannot read its bucket has no safe assumption, and guessing `allowed` hands out the fleet-wide budget to every replica at once | `psql "$DATABASE_URL" -c "select * from x_rate_limit limit 1"` — then confirm the `PgExecutor` passed to `postgresRateLimitStore` returns the rows of `returning` |
| `X_TRUST_PROXY_UNSET` | proxy headers are trusted without saying how many proxies are in front | `trustProxy: true` with no `trustedProxyHops`. The leftmost `x-forwarded-for` entry is whatever the client typed, so without a hop count there is no way to tell the proxy's entry from the caller's — and every per-ip limit and lockout is then keyed on an address the caller chooses. Asked at `defineHttpConfig` in the same shape as `X_RATE_LIMIT_NOT_SHARED`, because only the app knows its own topology. Both keys are **boot-owned** and `configureHttp()` type-refuses them: a framework-booted process reads the hop count from the ENVIRONMENT, because one image runs behind an ingress in one cluster and behind nothing on a laptop | set `TRUSTED_PROXY_HOPS` in the deployment environment to the number of proxies that append to `x-forwarded-for` — 1 for a single ingress or ALB, 2 for a CDN in front of one — and leave it unset for a process reached directly (`trustedHopsFromEnv`, [`packages/cli/src/dev-roles.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/cli/src/dev-roles.ts)). An embedder calling `defineHttpConfig` itself passes `{ trustProxy: true, trustedProxyHops: 1 }` |
| `X_OVERLOADED` | in-flight requests are at the configured ceiling | more concurrent requests than `maxInflight` (1,000). Shed **before** any work — no route match, no auth, no body, no query — because the alternative is not "serve everyone" but "serve nobody": every request queues behind the same pool, p99 walks off the chart and client retries multiply the load. `@ultimat3/realtime`'s `AcceptBudget` is the same decision for sockets. Classified `retry-after`, and the response carries the header; also thrown by `@ultimat3/auth`'s KDF gate, which refuses a password hash when 8 are running and 64 are queued — each argon2id arena is ~19 MiB, so the caps bound memory the per-IP limiters cannot | retry after the `Retry-After` header; to serve more at once call `configureHttp({ maxInflight: 2000 })` at module scope in a file under `apps/*/`, and add replicas to match. For the KDF half, `configureKdfGate({ maxConcurrent, maxQueued })` |
| `X_CSRF_BLOCKED` | a credentialed write arrived from an origin that is not allowed to make it | a state-changing request carrying the browser's ambient session cookie whose `Origin` is not one this app allows. Never a 401: the caller **is** signed in, which is precisely the problem | call it with an `Authorization` header instead of the session cookie, add the calling origin to `configureHttp({ cors: { origins } })`, or `configureHttp({ csrf: { mode: 'off' } })` if this app has no cookie session at all |
| `X_WEBHOOK_SIGNATURE_INVALID` | the inbound webhook is not signed by the holder of this secret | four conditions, one code: no readable `x-ultimate-webhook-signature`, an id or topic header outside 1–200 characters or carrying a `:` or a control character, a mac that does not match the bytes that arrived, or a secret the two sides disagree about. The header check is refused **before** the mac is taken — the signed string is `v1:<t>:<id>:<topic>:<body>`, so id `evt:01HZ` with topic `orders.paid` and id `evt` with topic `01HZ:orders.paid` build the SAME bytes, one mac authenticating two differently-labelled deliveries. **401 and never 400**: the request is well formed and carried a CREDENTIAL, so what failed is authentication. Never 403 either, which means an authenticated caller was refused, and there is none here. Does not trigger `signInRedirect`, which keys on `X_UNAUTHENTICATED` alone — a sender is not a browser and has no session to go get. `cause` names only what the framework chose: never the signature, never the secret, never the body | sign the delivery with the secret this endpoint was registered under, or re-read the secret from your sender dashboard and pass it as `verifyWebhookSignature(request, { secret })` |
| `X_WEBHOOK_SIGNATURE_STALE` | the inbound webhook is signed correctly and is too old to accept | the mac verified and the timestamp sits further than `toleranceMs` (default 300,000 ms) from this clock — a sender's clock, or a delivery replayed off a capture. The mac is checked **before** the window, deliberately, so this code always means "authentic and old" and never "unreadable and old". Both directions of skew count: a sender running ahead is the same replay window pointed the other way, and accepting the future half doubles it. Same 401 as above — the credential is a timestamped one and this is its expiry half | sync the sending host clock with NTP, or widen the window with `verifyWebhookSignature(request, { secret, toleranceMs: 600_000 })` if the sender queues deliveries for longer than that |
| `X_BUILD_SKEW` | client build id does not match the server build id | a tab open across an incompatible deploy | reload; the SW fetches the new build manifest. See [PWA and offline](PWA-And-Offline) |
| `X_SERVER_NOT_STARTED` | server handle used before `start()` | reading `url()` too early in a test | `await createServer({ … }).start()` first |
| `X_PIPELINE_NO_RESPONSE` | a pipeline stage produced no response | a middleware returned `undefined` | return a `Response` from the stage or from the handler |
| `X_PIPELINE_FINALIZE_FAILED` | a finalize stage threw instead of finishing the response | the response cannot take the headers the pipeline puts on it — a `Response.redirect()`, or a frozen or proxied `Response` a handler returned. `handle()` answers this 500 rather than rejecting, and the `cause` names the stage | return a Response built here — `json()`, `text()`, `html()` or `redirect()` from `@ultimat3/http` |
| `X_NO_REQUEST` | the inbound request is not in scope here | `useRequestCookie()` / `setRedirect()` called from a job, a task or a module body | read it inside a route handler, an action or a page; a job gets the value from its payload |
| `X_ERROR_STATUS_INVALID` | an error code cannot be mapped to that status | `registerErrorStatus()` given a framework-owned code, a status outside 100–599, or a second, different status for one code | `x errors list --json`, then map a code this app owns to a status the framework does not already hold |
| `X_CORS_CONFIG_INVALID` | the cors config can never produce a working response | `cors.origins` contains `'*'` while `cors.credentials` is true — a pair no browser accepts, which used to resolve to no CORS headers at all rather than an error | call `configureHttp({ cors: { credentials: false } })` at module scope in a file under `apps/*/`, or replace `origins: ['*']` with the exact origins allowed to call this app |
| `X_CSP_DIRECTIVE_INVALID` | a csp extension would emit something other than the directive it names | a `security.csp.extend` key that is not a CSP directive token, or a source carrying one of the header's own separators — `{ 'x; script-src *': [] }` is not one badly named directive, it is a second directive nobody declared, widening the one the framework locks down hardest. Refused at `defineHttpConfig`, because there is no encoding for a CSP directive and escaping it at emission time is not a repair | in the `configureHttp({ security: { csp: { extend } } })` call write one entry per directive, each source its own array element — a directive name is `[a-z][a-z0-9-]*`, and no source may contain a space, a comma or a semicolon |

## Policy and authz

A denial is `X_FORBIDDEN`, above — `@ultimat3/policy` owns it and every surface adapter throws it, so there is one code for "the policy said no" wherever it was decided.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_POLICY_MISSING` | an action was declared without a policy | a new action shipped with no `policy:` | add `policy: can('<resource>:<verb>')`, or `allow('public')` to say so explicitly |
| `X_POLICY_CLAUSE_EMPTY` | a policy combinator was built with no clauses | `and()` answered **allowed** and `admitsAnonymous(and())` agreed, so `policy: and(...caps.map(can))` over a list that filtered to empty admitted an anonymous caller on all four surfaces — and because `meta.auth` derives from `admitsAnonymous`, http did not 401 first. The label rendered as `and()`, so there was no diagnostic. `or()` fails closed but denies with `no clause allowed this actor`, a reason naming no clause. Both are refused where they are written, the `allowHosts: []` precedent | `allow('public')` is the spelling for "no clauses required"; `deny('<reason>')` is the one that carries a reason |
| `X_PERMISSION_UNKNOWN` | permission string is not in the permission set | typo, or a permission never declared | add it to `definePermissions([…])` |
| `X_POLICY_SURFACE_UNKNOWN` | enforce() was handed a surface no adapter answers to | `enforce(surface, policy, args)` called with a value outside `'http' \| 'live' \| 'job' \| 'mcp'` — a config-driven table, a surface name off the wire, or a JS host, none of which the type reached. Refused rather than dispatched because the adapter table is an object literal and so inherits `Object.prototype`: `adapters['valueOf']` answered a FUNCTION, `enforce('valueOf', …)` called it with the table as its receiver, and the truthy return was the adapter table typed as a `SurfaceDenial` — an authz dispatch that failed CLOSED with a denial carrying no code and no reason | pass one of `http`, `live`, `job`, `mcp` — `enforce('http', policy, args)` — or add the adapter for the new surface in `packages/policy/src/surfaces.ts`, the one place a fifth may be declared |
| `X_ROLE_REDEFINED` | two modules define the same role differently | one role name declared twice with different grants — a merged feature branch, or a role copied into a second module. Whichever module imported last would otherwise decide what the role can do, and the losing definition is still on disk for the next reader to trust. Both declaration sites are named, because which two is the only thing the author does not already know | `x policy list --json` — then keep ONE definition of the role `cause` names: rename the second, or fold its grants into the first |
| `X_TENANCY_UNSCOPED` | a tenant-scoped query has no org predicate | a repo call outside any request context, so there is no actor to derive the tenant from; a plan handed to the verify-only `assertScoped()` while an actor *is* present; or an `upsertAll(rows, { onMatch: 'update' })` whose `onConflict` omits the tenant column — a collision there lands on another tenant's row | the cause says which of the two it is. No context: `runWithContext(createContext({ actor }), fn)` from the script or seed. Actor present: build the plan through `scopedPlan()`, or `orgScoped(plan, ctx.actor.orgId)`. For the upsert: put the tenant column in `onConflict` |
| `X_TENANCY_ACTOR_MISMATCH` | a call named a tenant other than the actor's — as a query predicate, or as the tenant column of a row being written | an `orgId` that arrived as action input, a query string or a path parameter, passed into a repo call; or an `insert`/`upsertAll` row, or an `update` patch, naming another tenant — the cause names both tenants | drop the `orgId` argument, the actor's tenant scopes the plan; or act as that tenant with `withChildContext({ actor })`; a read that must span tenants is `crossTenant('<why>', fn)` |
| `X_TENANCY_ACTOR_ORG_REQUIRED` | the acting actor carries no tenant | anonymous, or a service actor minted without an `orgId`, reading a tenant-scoped entity | mint the actor with its tenant at the request boundary — `userActor({ id, orgId })` — or `crossTenant('<why>', fn)` |
| `X_TENANCY_CROSS_DENIED` | a cross-tenant read was entered without the capability | `crossTenant()` called by an actor lacking `tenancy:cross`, or outside every request context — the capability is re-checked on every plan built inside the scope, so an actor swapped in by `withChildContext()` does not inherit the reach | mint the actor with the scope — `serviceActor({ id: 'reconciler', scopes: ['tenancy:cross'] })` — run inside `runWithContext(createContext({ actor }), fn)`, and wrap the reads in `crossTenant('<why this spans tenants>', fn)`; the reason is required and non-blank, because it is what the next reader greps for |
| `X_ACTION_POLICY_MISSING` | an action was registered without a policy | build-time check on the action registry | add `policy: can('<name>')` to the declaration |
| `X_QUERY_POLICY_MISSING` | a query was registered without a policy | same, for reads | add `policy: can('<name>')` to the query |
| `X_QUERY_NOT_PAGEABLE` | a read returned rows with no id, so a cursor cannot name a position | a projection or aggregate that drops the primary key — the id is the tiebreak that makes the sort order total | return the key from the query's `sql:`, e.g. `db.posts.select({ id: true, … })` |
| `X_CURSOR_VALUE_UNSUPPORTED` | a sort value cannot be carried in a cursor | a read ordered by a column whose values are objects, or by a number that is `NaN`/`±Infinity` — a cursor is JSON, and `Date` and `bigint` are the only non-JSON types it tags and revives. Raised where the cursor is MINTED, not where one arrives: the mistake is the read's own `orderBy`, so no retry and no fresh first page repairs it | order by a scalar column — `.orderBy('createdAt')` or `.orderBy('id')` — and project the composite value into the row instead |
| `X_AGGREGATE_UNSUPPORTED` | that column has no aggregate both drivers can answer alike | three conditions, one code, and the `cause` names which. A `text` column has no `min`/`max` the two drivers agree on — ordering is the database's collation in one and JS code-unit order in the other. `avg` over money is refused outright: the mean of an integer number of minor units is not one, so every answer would be a silent rounding. And a money `sum` past ±2^53 minor units has no JS number to hold it, and `MoneyValue.minor` is one | the fix names the exact call. For a wrong column, `<entity>.<fn>('<candidate>')` — the cause lists the columns that fn accepts, or says the entity declares none. For `avg` over money, `<entity>.sum(col)` and `<entity>.count()`, dividing at the call site where the rounding is a decision somebody made. For the overflow, narrow the rows with `.andWhere(…)` |
| `X_AGGREGATE_MIXED_CURRENCY` | an amount was aggregated across currencies | 100 JPY and 100 EUR have no common unit, so a `sum`, `min` or `max` over them answers a number in no currency at all. **Both** drivers count the distinct currencies of the rows they are about to aggregate and refuse past one, rather than answering in whichever came first; the cause lists every currency it found | `<entity>.andWhere('<col>.currency', 'eq', '<CUR>').<fn>('<col>')` — one currency per call — or `countBy('<col>.currency')` first to see the split |
| `X_APPROXIMATE_COUNT_FILTERED` | an estimate was asked of a filtered chain | `approximateCount()` reads `reltuples` out of `pg_class`, which knows nothing about a predicate, so `posts.where({ orgId }).approximateCount()` would answer for the whole TABLE while reading as "roughly how many of mine". Refused rather than answered, because the wrong answer is plausible and unbounded | `<entity>.count()` — the exact answer for a filtered chain. `approximateCount()` answers for the whole table only |
| `X_QUERY_CACHE_TTL_INVALID` | a query declares a cache `ttlMs` no tier can hold | `cache: { ttlMs: Infinity }`, `0`, a negative value or `NaN`. Judged at `query()`, in the file that declared it, rather than on the first read: the tiers already refuse the value with `X_CACHE_TTL_INVALID`, so before this the mistake compiled, passed review, and made **every** read of that query fail permanently in production. The cause echoes the value rather than the query name — `query()` runs before `registerQueries()` stamps a name, exactly as `X_QUERY_INPUT_UNENCODABLE` does | pass a positive, finite `ttlMs`, or drop the `cache` block — "do not cache" is expressed by not declaring one |
| `X_QUERY_INPUT_UNENCODABLE` | a query input cannot be carried in a query string | a read declaring a nested `t.object`/`t.record`/`t.money` member, an array or union of one, a REQUIRED `t.nullable(...)` member, or a top-level input that is not an object. A read is served as `GET /_x/query/<name>`, so its input is characters: the typed client would encode a structure as JSON text and skip a `null`, and `coerceQuery` has no inverse for either. Raised at `query()`, in the file that declared it | flatten the key into scalar arguments (`status: t.string, limit: t.number`), spell an absent value as `.optional()` rather than `t.nullable(...)`, or declare it as an `action()` if it really needs a JSON body |
| `X_QUERY_SUBSCRIBES_INVALID` | a query declares subscribed relations no live read can use | `subscribes: []`, or a `subscribes:` on a read that is not `live: true`. Judged at `query()`, in the file that declared it, like `X_QUERY_CACHE_TTL_INVALID` one field over — an empty list names no table to grant `REPLICA IDENTITY FULL` to, and a non-live read never reaches the cross-check at all, so an accepted one would be a declaration nothing verifies and nothing emits | name the relation the read selects from — `subscribes: ['posts']` — or delete the field; on a read that should be subscribable, add `live: true` beside it |
| `X_QUERY_SUBSCRIBES_DRIFT` | a live query subscribes to a relation its own sql never reads | the declaration and the read disagree: `subscribes: ['post']` while `sql:` returns `from('posts', …)`. Thrown at the first subscribe, where the resolved `QueryShape` is the first thing that can say which relation the read really names — the string lives inside a callback nothing can invoke without valid input. A refusal and not a warning, for `assertMatchable`'s reason one line above it: `x db gen` keys the migration on this list, so a stale name has already granted `REPLICA IDENTITY FULL` to the wrong table and left this one unable to produce an old row on `UPDATE`, which is a subscription that silently stops updating | add the relation the `cause` names to that query's `subscribes:`, then `x db gen` |
| `X_QUERY_SUBSCRIBES_UNKNOWN` | a live query subscribes to a table no entity declares | `subscribes:` on a `live: true` query names a relation this app has no entity for — a typo, or a table that was renamed. Raised by `x db gen`, the one tier holding both the manifest and the entity registry: `@ultimat3/query` has no table catalog and cannot see it, and `@ultimat3/db` DROPS a name no entity table matches, so without this the identity would have been granted to nothing while the declaration read as granted | edit `subscribes:` on the query the cause names to a table the app declares, or drop the name, then `x db gen "retry after fixing subscribes" --json` |

## Auth and sessions

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_SESSION_EXPIRED` | session passed its idle or absolute expiry | `cause` names which of the two clocks ran out | sign in again, or raise `session.absoluteTtlMs` / `session.idleTtlMs` in `defineAuth({ session })`. The wiki used to name `POST /auth/sign-in` here; the framework mounts no such route, and the password half is the app's until it ships one |
| `X_MFA_REQUIRED` | password proven, second factor outstanding | the user has TOTP enrolled, and `login()` / `completeOAuthLogin()` throw before any session is written | **the framework mounts no second-factor route and ships no `completeMfa()`** — this page named `POST /auth/mfa/verify` for a release while nothing served it. Until it exists the second leg is the app's: catch `X_MFA_REQUIRED` in your sign-in handler, check the code with `verifyTotp({ secret: user.mfaSecret, code, at })`, then mint the session with `createSession(auth.sessions, { userId, mfaSatisfied: true })`. The user id is in `meta.userId`, never in `cause` — both public surfaces publish `cause` and drop `meta`. The framework's own leg needs a sealed pending-MFA credential first (`packages/auth/CLAUDE.md`), or `POST /auth/mfa/verify { userId, code }` is unauthenticated by construction and MFA becomes the only factor |
| `X_MFA_SECRET_INVALID` | a TOTP secret that is not RFC 4648 base32, so it decodes to zero bytes | `enrolTotp` is handed an imported secret outside the alphabet, or `totpCode` is called with one. `verifyTotp` does **not** throw it — an unreadable stored secret reads as a non-verdict there, the same rule `verifyAgainst` follows for a password hash Bun cannot read, so a login checking a broken row gets a credential refusal rather than a 500 | issue a fresh one and store it: `const { secret } = enrolTotp(auth, { account: user.email })`. An imported secret must be base32 (`A-Z` and `2-7`; padding, spaces and dashes are ignored) and must decode to at least one byte. Zero bytes is not a decode that failed closed: an HMAC keyed with zero bytes is a valid HMAC, so every unreadable secret in the table used to verify against one shared code stream that needed no secret to compute |
| `X_OAUTH_STATE_INVALID` | state, nonce or PKCE verifier did not match | a replayed callback URL, a handshake that expired, or a token minted for another browser | restart the flow at `GET /auth/oauth/<provider>` — a callback URL is single-use |
| `X_OAUTH_EXCHANGE_FAILED` | the provider refused the exchange or returned no usable identity | wrong client secret, an unregistered `redirect_uri`, a spent code, or a missing scope. **Not** the user pressing Cancel — that is `X_OAUTH_DENIED` | `meta.stage` is `token` or `userinfo`: for `token`, match `<PROVIDER>_CLIENT_SECRET` and the registered `redirect_uri`, then `x doctor --json`; for `userinfo`, restart at `GET /auth/oauth/<provider>` |
| `X_OAUTH_TOKEN_INVALID` | the id token failed its signature, issuer, audience or expiry check | `As of 2026-08` the signature is verified too, against the issuer's published key set through a JWKS client — until this cycle the token was decoded and its claims read, so a token minted by whoever posted it to the callback passed every check it faced. Also: a token that is not a three-segment JWT, a payload with no `iss`/`sub`/`exp`/`aud`, a client id in `.env` that is not the one the authorize URL was built with, or a skewed host clock | the `fix` branches on which check failed — for a signature, confirm the token came from the provider's token URL and was not minted by the caller; for the rest, match `<PROVIDER>_CLIENT_ID` to the id `beginOAuth()` used, then restart at `GET /auth/oauth/<provider>` |
| `X_OAUTH_PROVIDER_DUPLICATE` | two oauth providers were registered under one id | two `registerOAuthProvider` calls claiming one id. Refused at boot rather than replacing silently, because the winner would be whichever module imported second — and it decides where every login for that id goes, **including which `issuers` an id token may claim** | give one of them a different id, or delete the duplicate `registerOAuthProvider({ id: '<id>' })` call |
| `X_OAUTH_PROVIDER_UNKNOWN` | the URL named a provider this app has not enabled | the `:provider` segment is not a known provider, **or** is one but was left out of `defineAuth({ providers })`; also `providerFor()` reaching for an id nothing registered. One refusal for all of them: distinguishing them would describe the app's configuration to an anonymous caller | `registerOAuthProvider({ id: '<id>' })` if it is not built in, then add that id to `defineAuth({ providers: [...] })` — the registration comes **first** because a segment nothing registered cannot be added to `providers` at all, so "add it" alone was an instruction that could not be followed. The list the `fix` prints is what is **known here**, never the subset this app enabled, and `meta` carries only `{ provider }` |
| `X_OAUTH_DENIED` | the user or the provider declined the authorization | `error=` on the callback redirect — nearly always the consent screen's Cancel. Split out of `X_OAUTH_EXCHANGE_FAILED` so the commonest non-success outcome of a login stops paging on-call as a 502 provider outage | restart at `GET /auth/oauth/<provider>` and approve the consent screen; nothing is wrong with the app |
| `X_PASSWORD_WEAK` | strength check rejected the password | too short, or a known-common password | choose a longer, uncommon password — or relax `defineAuth({ password: { minLength } })` |
| `X_ACCOUNT_LOCKED` | per-ip or per-account bucket is inside its lockout | repeated failed attempts; `cause` names the key and the seconds left. The wiki used to name `x auth unlock <key>`, a command that has never existed | wait out the seconds `cause` names — or clear this one bucket: `auth.limiter.recordSuccess('<key>')`, `auth.orgLimiter` for an `org:` key — or raise `defineAuth({ rateLimit })`. Never `reset()`: it drops every bucket in the table, including the spray this lockout is holding |
| `X_AUTH_LIMITER_NOT_SHARED` | the app declared a fleet-wide credential throttle and the limiter keeps its counters per process | `defineAuth({ rateLimit: { scope: 'shared' } })` against the built-in limiter, whose `scope` is `'process'` — account lockout would be `maxAttempts × replicas`, and a lockout on one replica invisible to the others. Refused at `defineAuth`, never at a request | pass a shared `AuthLimiter` to `defineAuth({ limiter })`, or drop to `scope: 'process'` |
| `X_AUTH_LIMITER_POLICY_MISMATCH` | a custom credential limiter enforces different numbers than the app declared | `defineAuth({ limiter })` where the limiter's own `policy` disagrees with the declared `rateLimit` on `maxAttempts`, `windowMs` or `lockoutMs`. `Auth.rateLimit` is what an operator reads as "what this deployment enforces", and an injected limiter could leave nothing behind it. The `cause` names both numbers and says which half is likely wrong; `maxKeys` is deliberately **not** compared, since it bounds one process' table and a shared limiter has no opinion on it | construct the limiter with the declared number — the declaration is what `Auth.rateLimit` reports, so it is the half that stays. If the limiter's number is the one this deployment means, change the declaration instead; `meta` carries `{ field, declared, enforced }` |
| `X_API_KEY_INVALID` | key unknown, revoked, expired or wrong | one shape for all four — a precise message is an enumeration oracle, so which of the four it was is not named here and never will be. The wiki used to name `x auth keys list --json`, a command that has never existed | issue a replacement: `const { plaintext, record } = issueApiKey({ env, scopes }); await auth.adapter.putApiKey(record)` — `auth.adapter.listApiKeys(ownerId)` through `describeApiKey()` shows which keys are still live |
| `X_AUTH_WRITE_FAILED` | an adapter write returned no row, so it cannot be confirmed | an `insert … returning *` wrote nothing — the table is missing its migration, or a trigger or RLS policy swallowed the row. This page printed `x db query` until 1.2.0; the `db` subcommands are `gen`, `migrate`, `reset`, `studio`, `branch` and `backfill` | `x db migrate`, then confirm the table with `psql "$DATABASE_URL" -c "select 1 from x_users limit 1"` |

`GET /auth/oauth/<provider>` is the app's route to mount, not one the framework serves. Every OAuth fix above is reachable only where the host routes matching requests to `oauthLogin(auth).start.handle`; `oauthLogin()` supplies the descriptors and nothing else mounts them. The thrown `fix:` and the descriptor's `path` both read the one declaration in `oauth-paths.ts`, so the string cannot go stale — but `As of 2026-08` `serve.ts` composes a fixed set of route tables with no seam for a raw `Route`, so nothing `x new` scaffolds mounts the pair and an app that has not mounted it itself answers that path with a 404.

## Entity and database

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_DB_DRIFT` | schema differs from migrations | a column exists in code but in no migration — or, on an app that declares an entity and has generated no migration yet, `packages/db has a schema but no migration recorded it`. An app declaring **no** entity is not drifting: zero declared against zero recorded is agreement | `x db gen "<describe the change>"` then `x db migrate`; on a fresh scaffold that is `x db gen "initial"`. The one difference this does **not** fix is `unknown-schema` — see `X_MIGRATION_SNAPSHOT_MISSING` below, whose two remedies it shares |
| `X_DB_SCHEMA_UNMIGRATED` | an entity declaration no migration recorded | the half `X_DB_DRIFT` cannot see: that check compares a schema-source **hash** and never reads the SQL, so a committed migration smaller than its declaration passes. Measured on `dummy/social-media-clone`, whose `drift` was GREEN while nine declared CHECK constraints had never reached any database — a comment body could be whitespace, a like count could go negative, an email needed no `@`. Compares `snapshotOf(describeEntities())` against the newest `.snapshot.json`, so it needs no database connection | `bun run x -- db gen "describe the change"` — the generated migration is additive, one `add constraint` per finding |
| `X_DB_SCHEMA_UNDECLARED` | a migration records schema no entity declares | the other direction, and a different repair: the database carries a constraint, column or index the entities no longer ask for. Reported separately from `X_DB_SCHEMA_UNMIGRATED` because "your database is missing this" and "your last generation lost something" are not one finding | delete the stale declaration, or `bun run x -- db gen "drop what the entities no longer declare"` if the removal is intended |
| `X_ENTITY_DUPLICATE` | two entities claim the same name | copy-pasted `entity({ name })` | rename one; `x entities list --json` |
| `X_INVARIANT_VIOLATED` | a domain invariant rejected this row | a CHECK or a declared invariant failed. This page printed `x entity explain` until 1.2.0; the registry command is plural and its subcommands are `list` and `describe` | `x entities describe <entity> --json` — every invariant with its `kind`, `message`, `sql` and `where` |
| `X_NOT_FOUND` | no row for that id | stale id, wrong tenant, or already deleted | confirm with `psql "$DATABASE_URL" -c "select id from <table> limit 5"` — `x db` has no `query` subcommand |
| `X_WRITE_UNFILTERED` | `deleteWhere()` or `updateWhere()` named no filter columns | an empty filter, or one whose only value came back `undefined` — the two look identical at the call site, and either would reach every row | name the columns that bound it, e.g. `db.likes.deleteWhere({ postId, userId })`. A deliberate whole-table write is a migration: `x db gen "<name>"` |
| `X_PATCH_EMPTY` | `updateWhere()` named no columns to write | an empty patch, or one whose only value came back `undefined` — reporting "n rows updated" for a statement that set nothing is the silent no-op the count exists to prevent | name the columns to write, e.g. `db.participants.updateWhere({ conversationId, userId }, { lastReadAt })` |
| `X_PRELOAD_UNKNOWN_RELATION` | no relation of that name on this entity | a typo, or a relation the schema never declared — relations are derived from `references()` columns, so there is no list to read them off | the `fix` is a call on one that exists, e.g. `relationNamed('posts', 'author')   # or: org, likes`. No foreign key at all ⇒ `x entities list --json`, then add `.references(() => <target>.id)` to the column that points at one |
| `X_N_PLUS_ONE_QUERY` | a read repeated once per row | one lookup per row of a page — `members.findById` fifty times where one `in` statement would answer. Counted per request by the statement ledger `x dev` installs, and never counted in production. Reported on four surfaces at once: `x dev`'s findings, `/_x/timeline`'s `nPlusOne`, the browser overlay under the error, and one `logger.warn` per request per code. **Thrown in one place only** — a test that destructures `@ultimat3/testing`'s `statements` fixture, where the loop's fifth statement rejects and fails the test | the `fix` is the preload the schema already declares, e.g. `db.posts.preload('author')`. No relation points at the entity ⇒ the batched form of the same read, `db.members.andWhere('id', 'in', ids).all()`. A loop that is genuinely one statement per row is declared, not silenced: `expectedQueryLoop('<why>', fn)` |
| `X_N_PLUS_ONE_WRITE` | a write repeated once per row | one `insert`, `update` or `delete` per row of a set, where one statement writes all of them. Same four surfaces as the read above, same ledger, and the same throw inside the `statements` fixture | the bulk form of the same call: `db.posts.insertAll(rows)`, `db.posts.updateWhere(filter, patch)`, `db.posts.deleteWhere(filter)` — or `expectedQueryLoop('<why>', fn)` when the loop is deliberate |
| `X_SEARCH_UNDECLARED` | this entity has no searchable column | a `matches` predicate on an entity whose columns declare no `.searchable()`, so there is no tsvector to match against. Raised where the STATEMENT would be built and not where the chain was written, because both drivers reach it: a search vector is derived from the entity's own columns, so there is nothing else the predicate could name and no vector to guess at. 500 and not a 4xx — nothing the caller sends changes the answer, and the repair is an edit to the entity | `add .searchable() to a text() column of <entity>, then: x db gen "search <entity>"` |
| `X_SEARCH_IN_MEMORY` | the in-memory driver cannot answer a full-text match | a search run against `memoryDriver()`. REFUSED rather than emulated, and that is the whole decision: `to_tsvector` stems, drops stop words and applies a language's own rules, and `websearch_to_tsquery` parses quoted phrases and `-`negation — a JS token comparison is a DIFFERENT question with the same shape, so it would answer green in a unit test and differently in production, which is the one outcome the two-driver split exists to prevent. 500 for the same reason as the row above | move this read into a `<name>.live.test.ts` and run it with `TEST_DATABASE_URL` set — `bun test packages/entity/src/pg-search.live.test.ts` is the model |
| `X_STATE_UNDECLARED` | that column declares no state machine | `transition()` on a column with no `.transitions()` — a declaration bug and not a caller's, which is why `cause` lists the columns that DO declare one: the repair is naming a different column or writing the table, and both are edits to source. 500, the same shelf as `X_SEARCH_UNDECLARED` | `add .transitions(…) to <entity>.<column>` — it must be an `enumerated()` column, and every value that set declares needs an entry. When other columns already declare a machine, the `fix` lists those instead |
| `X_STATE_TRANSITION_ILLEGAL` | the machine has no such transition | three conditions and one code, because they share one repair — the move is not in the table — and `cause` states which. `"<from>"` is not a state the `enumerated()` set declares; the row is terminal in `"<from>"`, an empty move list being how a terminal state is written; or the move to `"<to>"` was never declared. The unknown-state branch is separate because an unknown state has no outgoing moves either, so a single "no legal moves" answer reported a typo as "the row is terminal in `<typo>`" — a sentence about a state that does not exist. **422 and not 400**: the request is well formed and its schema passed, which is `X_INVARIANT_VIOLATED`'s shape and takes its status. Refused before any statement opens a connection, so nothing was written | the `fix` is the same call with a legal target substituted — `orders.transition('status', id, { from: 'pending', to: 'paid' })` — or add `"<to>"` to the `"<from>"` entry of the `transitions()` table |
| `X_STATE_CONFLICT` | the row is no longer in the state this transition named | the lost update, caught: two callers both read `pending`, both found the move legal, and the second one's statement carried `status = 'pending'` in its predicate and matched nothing. The state in `cause` is read back AFTER the refusal, so it is a diagnosis and never the decision — the decision was the statement, and it was atomic. **409 and not 422**: nothing is wrong with the request, the identical one succeeds a moment later, and re-read-and-retry is precisely what a 409 tells a client to do | re-read the row and decide again against the state `cause` names: `orders.findById(id)` — a transition names the state it expects, so a stale read is refused rather than overwritten |
| `X_DB_UNAVAILABLE` | cannot reach the database | nothing listening on `DATABASE_URL`, a closed pool, or `@electric-sql/pglite` not installed for a `pglite://` url — every failure that **never reached a server**, and `As of 2026-09-05` only those: a failure carrying a SQLSTATE is proof the server answered and is one of the two rows below. The driver's own words ride in the cause (`ECONNREFUSED 127.0.0.1:5432`) | set `DATABASE_URL` to a reachable Postgres, or `x dev` for the embedded PGlite — `bun add @electric-sql/pglite` when the url is `pglite://` |
| `X_DB_SCHEMA_STALE` | the statement names a table or column the database does not have | SQLSTATE `42P01` / `42703` — an entity edited before the migration that adds its column ran, on either driver (PGlite under `x dev` included). The cause leads with `[SQLSTATE 42703] column "host_id" does not exist` and carries the statement after it, excerpted, so the column list can never push the message off the line | `x db gen "<what changed>" && x db migrate` — only the migrate half when the migration already exists |
| `X_DB_STATEMENT_FAILED` | the database refused the statement | any SQLSTATE the table does not classify — a syntax error, a data exception, a check or not-null violation. The server's verdict, so re-running it gives the same verdict, and the connection is not the problem | read the SQLSTATE and message in the cause; `psql "$DATABASE_URL" -c "<the statement>"` reproduces it by hand |
| `X_DB_UNIQUE_VIOLATION` | a unique constraint rejected the row | SQLSTATE `23505` — two clicks racing a signup, or an insert where an upsert was meant. One of six driver failures that used to reach the caller as `X_DB_UNAVAILABLE`, whose fix reads "set `DATABASE_URL` to a reachable Postgres": a raced signup paged on-call for an outage that never happened. `meta.constraint` names the index the server refused on | `upsertAll(rows, { onConflict: [...] })` over the columns the constraint `cause` names — or catch `X_DB_UNIQUE_VIOLATION` and answer 409, which is what a raced signup is |
| `X_DB_FOREIGN_KEY_VIOLATION` | a foreign key constraint rejected the row | SQLSTATE `23503` — the parent row is absent, or was deleted between the read and the write. `meta.constraint` names the key | insert the row the constraint `cause` names points at first, in the same `withTransaction(...)` — or drop the write, because the parent it names is gone |
| `X_DB_SERIALIZATION_FAILURE` | the transaction lost a serialization race | SQLSTATE `40001` or `40P01` — a serializable transaction whose read set another commit invalidated, or a deadlock the server broke. Retryable by definition, which is why it is its own code and not an outage | `withTransaction(fn, { retry: 3 })` — `fn` re-runs from the top, so it must be idempotent |
| `X_DB_STATEMENT_TIMEOUT` | the statement ran past its `statement_timeout` | SQLSTATE `57014` — a sequential scan where an index was assumed, or a plan that changed under a grown table | add the index this statement needs to the entity (`indexes: [...]`), then `x db gen "add index"` |
| `X_DB_LOCK_TIMEOUT` | the statement waited past its `lock_timeout` | SQLSTATE `55P03` — usually a DDL statement queued behind a long transaction holding the same table, which then blocks every reader behind *it* | `psql "$DATABASE_URL" -c "select pid, state, query from pg_stat_activity where state <> 'idle'"` — end the blocker, then re-run the statement |
| `X_DB_POOL_EXHAUSTED` | no connection was available | SQLSTATE `53300` from the server, or the local pool answering nothing inside `acquireTimeoutMs` — deliberately one code, because to a caller both mean "there was no connection for this unit of work" and a second code would split one runbook in two. Refused rather than queued forever: a hang makes `/readyz` join the queue, the kubelet kills the pod, and the next pod inherits the same saturated database | set `DATABASE_POOL_MAX` below `max_connections / replicas` (per-role default: `POOL_PROFILES`), or cut the replica count |
| `X_DB_DRAIN_TIMEOUT` | the pool did not drain inside its shutdown budget | `As of 2026-08-27`: `close()` gave up waiting for a role's pool to hand its connections back. `Bun.SQL`'s `end()` waits on an outstanding RESERVED connection and never stops — measured three runs per case on Bun 1.3.14 **and** 1.4.0, with the database perfectly healthy — so before `PoolProfile.drainTimeoutMs` a shutdown that met a pinned connection never finished, and the operator's only signal was a container that burned its whole termination grace period before SIGKILL. Raised on the elapsed time, because the driver RESOLVES when it gives up rather than rejecting: a drain that silently abandoned in-flight work looked exactly like a clean one. `migrate` and `replicator` are `0` and still wait forever, deliberately — a run-once role cutting off its own session mid-statement is worse than a slow exit | find the statement that will not finish — `psql "$DATABASE_URL" -c "select pid, state, query from pg_stat_activity where state <> 'idle'"` — or raise `drainTimeoutMs` in `createPostgresClient({ profile })` for the role `cause` names |
| `X_MIGRATION_CONFLICT` | the migration ledger disagrees with this build | a ledger row from an app version this build does not ship, an applied migration whose file was edited so its checksum moved, or a rollback aimed at a row whose `down` SQL exists only in the build that shipped it. The wiki used to name `x db status --json` here; that command has never existed — the `db` subcommands are `gen`, `migrate`, `reset`, `studio`, `branch` and `backfill` — and this is one of the two errors most likely to fire during a real deploy | the `fix` branches on which half disagreed. Foreign ledger row: deploy the app version `cause` names, or drop its row — `psql "$DATABASE_URL" -c "delete from x_migrations where id = '<id>'"`. Moved checksum: `x db gen "fix <migration>"`; never edit an applied migration. Unknown `down`: read the ledger with `psql "$DATABASE_URL" -c "select id, app_version from x_migrations order by id desc limit 5"` and roll back on the build that shipped it |
| `X_MIGRATE_CONCURRENT` | another migrator holds the migration lock | two overlapping deploys, or a migrator wedged on a partition — or OOM-killed with its backend still alive — still holding `pg_advisory_lock(<key>)` when the wait ran out. `pg_advisory_lock` blocks with no timeout, so that case left `helm upgrade --wait` sitting inside one statement, printing nothing, with the job never failing so `backoffLimit` never fired. `As of 2026-08` a bounded `pg_try_advisory_lock` poll turns it into an exit code | `psql "$DATABASE_URL" -c "select pid, application_name, state from pg_stat_activity join pg_locks using (pid) where locktype = 'advisory'"` — `pg_terminate_backend(pid)` the wedged migrator, then `x db migrate` |
| `X_MIGRATION_IRREVERSIBLE` | this migration cannot be reversed without data loss | a generated plan that drops a column or a table | `x db gen "<name>" --allow-destructive`, or keep the column and deprecate it |
| `X_MIGRATION_DESTRUCTIVE` | this migration destroys data and does not say so | `As of 2026-08`: a committed migration whose `up` drops a table, drops a column, truncates or retypes, with no `-- destructive: true` line in the file. Raised by `x verify`'s `drift` step over the files, never by the migrator — the rail fails in CI, before a release phase applies it. Only `up` is judged: reversing a `create table` is a `drop table`, and marking every `down` marks nothing | add the line `-- destructive: true` to the migration, or `x db gen "<name>" --allow-destructive` to regenerate it — the generator writes the marker itself. Add it **before** the migration is applied: the marker is SQL the checksum covers, so marking an applied file is an edit and answers `X_MIGRATION_CONFLICT` |
| `X_MIGRATION_UNGENERATABLE` | this migration holds SQL no declaration carries and does not say so | the third rail of the `drift` step, and the one a **squash** discards. `x db gen` can only write what an entity declares, so a hand-written `CREATE TYPE … AS ENUM`, `CREATE EXTENSION`, `GRANT`, `ALTER TABLE … REPLICA IDENTITY FULL` or a data backfill is lost the moment anyone regenerates — and no declaration-based check can see it, because a regenerated sidecar equals the declaration by construction. `examples/dummy`'s `0001_init.sql` holds **7**: five enum types and both replica identities. A count, not a boolean, so the first hand-written statement does not buy that file an unlimited allowance | add the header line `-- ungeneratable: <n>` to the file `packages/db/migrations/<id>.sql` that the finding names, so a squash carries these statements by hand — or re-declare what an entity *can* express (an enum is a text column plus a `check` invariant) and run `x db gen "<name>"`. Add the marker **before** the migration is applied: it is SQL the checksum covers, so marking an applied file answers `X_MIGRATION_CONFLICT` |
| `X_MIGRATION_VIEW_DEPENDS` | a view is compiled against a column this migration retypes | `As of 2026-08-25`: a **preflight**, run inside each migration's own transaction before its first statement, in both `x db migrate` and `x db rollback`. A view stores a compiled parse tree, not its text, so `alter table … alter column … type` under a dependent view is `0A000 cannot alter type of a column used by a view or rule` and rolls the WHOLE migration back. The generator cannot see this by construction — a view is on no `SchemaDescription`, `introspect()` excludes views, and no entity can declare one — so the check lives where a connection exists. Until this code, the failure reached an operator as `X_DB_UNAVAILABLE: cannot reach the database` on a database the migrator was mid-transaction on, with the server's own `rule _RETURN on view … depends on column` sitting unread in a `DETAIL` field | `cause` names the view, the table and the column; `fix` is a runnable pair of `psql "$DATABASE_URL" -c '…'` invocations — drop the view, then `x db migrate`, then re-create it from the `create view` the fix line carries verbatim, read out of `pg_get_viewdef` before the drop. Single-quoted deliberately: `identifier()` writes the view name in DOUBLE quotes, so the `-c "…"` form the sibling migration errors use would end the shell word at the name. A view whose name `identifier()` refuses (a quote, a space, a backslash — all legal inside a quoted Postgres name) gets a fix that names the view as JSON and asks you to quote it, rather than a `fix:` that throws |
| `X_MIGRATION_SNAPSHOT_MISSING` | the newest migration records no schema snapshot | `As of 2026-08`: `x db gen` found the newest migration on disk carrying no `<id>.snapshot.json` sidecar — deleted, or hand-written without one. Every generated migration writes the sidecar the *next* generation diffs against, so there is nothing to diff the entities against. Refused rather than defaulted to the empty schema, which would emit `create table` for every table the database already holds. A scaffold no longer starts in this state: `x new` writes no migration at all, and `x db gen` is the one writer of that directory. `x doctor` reports it too, `As of 2026-08`, so the condition is visible before a generate hits it | `git checkout -- packages/db/migrations/<id>.snapshot.json`, or, when it was never written, delete the whole migration first and regenerate: `rm packages/db/migrations/<id>.* && x db gen "<name>"`. That order is the fix — naming `x db gen` while the file is still there re-raises this code. The same condition reaches `x db migrate` as `X_DB_DRIFT` with an `unknown-schema` difference, whose `fix:` names the same two remedies in the same order |
| `X_BRANCH_EXISTS` | that branch database already exists | two conditions, one code: `x db branch create <name>` for a name already taken — refused rather than overwritten, because a silent re-clone discards whatever the branch already held — or a `dropBranch()` aimed at the database this session is itself connected to, which Postgres cannot drop from underneath its own connection | `x db branch drop <name>   # then re-create, or pick another name` — `x db branch ls --json` lists what exists. To drop the database you are connected to, reconnect elsewhere first: `DATABASE_URL=.../postgres` |
| `X_SQL_UNSAFE` | SQL was built by string interpolation | a non-scalar interpolated into a `sql` template, or an identifier or branch name that is not `[a-z0-9_-]+` | pass a scalar (it becomes `$n`), a nested `sql` fragment, or wrap audited SQL in `raw()` — `cause` numbers the interpolation |
| `X_REPO_CLIENT_PINNED` | a repository pinned to its own client cannot join the open transaction | a repository built through `postgresDriver({ client })` used inside `withTransaction`. Refused rather than resolved, because neither answer is available: the pinned client takes a different connection out of the pool, so the write commits immediately and survives the rollback while the read cannot see rows the transaction already wrote — both silently. Joining the transaction instead is the worse guess, since a `DbTx` does not name the client it was opened on, and on a sharded app "is this even the same database" has the answer no | `setDbClient(client)` at boot and build the repository with no `client:` — `postgresDriver()` then resolves the open transaction through `db()` — or run this call outside `withTransaction()` |
| `X_DB_GEN_FAILED` / `X_DB_MIGRATE_FAILED` | the `x db` step failed for a reason no framework error claimed | a write the filesystem refused, the database unreachable. A failure the engine itself names — `X_MIGRATION_CONFLICT`, `X_MIGRATION_IRREVERSIBLE`, `X_DB_UNAVAILABLE` — reaches you as that code, with its own fix, never wrapped in these | read `cause` — it carries the underlying error verbatim — then `x doctor --json` |
| `X_DB_BRANCH_FAILED` | `x db branch` refused, or failed for a reason no framework error claimed | **two shapes under one code.** A deliberate refusal: `drop` aimed at a name `x db branch ls` does not show, whose `cause` names the exact database or data directory it *would* have touched, so the refusal is checkable rather than assertable. Or an unclaimed failure of any of the three verbs — the clone connection refused, the data directory unwritable. `X_BRANCH_EXISTS` (the name is taken) and `X_SQL_UNSAFE` (the name is not `[a-z0-9_-]+`) reach you as themselves | for the refusal, `x db branch ls --json` — the name is not in the set, and only what that lists can be dropped. Otherwise read `cause`, then `x doctor --json` |
| `X_DB_STUDIO_FAILED` | reserved, not thrown — `x db studio` is **planned and unreleased**, and exits `X_NOT_IMPLEMENTED`. It shelled out to `bunx drizzle-kit studio`, a second schema engine for one subcommand | — | `x dev`, then the db panel at `/_x` |

## Actions

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_ACTION_DUPLICATE` | two actions registered under one name | duplicate export names across features | rename one; names are global. `x actions list --json` |
| `X_ACTION_PATH_DUPLICATE` | two actions derive one HTTP path | two distinct names that pluralize onto the same route — `archiveOrder` and `archiveOrders` both derive `POST /api/orders/archive`. | `X_INPUT_INVALID` | input failed the primitive's schema — an action's, and a query's too | wrong shape from a client or an agent; over HTTP it is a **400**, never a 500 | `x actions describe <name> --json` (`x queries describe <name> --json` for a read) |
| `X_OUTPUT_INVALID` | the handler returned a value its `output` schema rejects | the handler drifted from the declared output | `x actions describe <name> --json`, then fix the handler or the schema |
| `X_ACTION_FOREIGN` | a value that is not an action was projected as one | a hand-rolled object with `kind: 'action'`, or an action from a duplicated copy of `@ultimat3/action` | declare it as `export const name = action({ input, output, policy, handle })` |
| `X_ACTION_UNREGISTERED` | an action was projected before it was registered, so it has no name | `.tool()` / `.client()` / `.job()` / `.openapi()` on an action `registerActions()` never named | `registerActions(await import('./actions'))` at boot, before mounting routes |
| `X_IDEMPOTENCY_CONFLICT` | idempotency key reused with a different payload, or still in flight | a retried request mutated its body | send a fresh `Idempotency-Key` for a different payload; otherwise retry after the first settles |
| `X_IDEMPOTENCY_KEY_INVALID` | an `Idempotency-Key` header was sent that cannot identify one request | a blank value — `Headers.get()` answers `''` for `Idempotency-Key:` and never `null`, so a blank header used to become a live key every blank sender shared — or one past the 255 characters the OpenAPI operation publishes. A **400**, raised before the handler, so nothing was written | set the header to a fresh `crypto.randomUUID()` on the client, one per request — or omit it entirely to run this call without idempotency |
| `X_IDEMPOTENCY_NOT_SHARED` | idempotency is declared fleet-wide and the installed store is per-process | `configureIdempotency({ scope: 'shared' })` against a store whose scope is `'process'` — or one that declares no scope at all, refused identically: what cannot be shown to be shared is not assumed to be. Refused at registration, before a socket opens, because the failure it replaces is silent and expensive — under `replicas: 3` the retry that lands on another replica finds no record, re-runs the handler and **charges the card again**, with nothing anywhere saying it did | install a shared store at boot: `setIdempotencyStore(postgresIdempotencyStore({ executor: Bun.sql }))` from `@ultimat3/action`, or drop the declaration to `configureIdempotency({ scope: 'process' })` |
| `X_IDEMPOTENCY_STATUS_UNKNOWN` | an idempotency record holds a status this build cannot read | `x_idempotency.status` holds a word this build has no branch for. The record was written by whatever build was deployed when the first attempt ran, which on a rolling deploy is not this one. Refused rather than cast: an unknown status fell past every branch of `withIdempotency` and answered `{ value: null, replayed: true }` — "this already ran, here is its result" — for a record nobody could read | `psql "$DATABASE_URL" -c "select key, status from x_idempotency where status not in ('in-flight', 'settled', 'failed')"` — then drain the older processes |
| `X_IDEMPOTENCY_REPLAYED_FAILURE` | a retried `Idempotency-Key` replays a first attempt that failed after it may have committed | the first attempt under this key threw and the store kept no detail of it — so nothing ran here, and what the caller is being handed is a recorded outcome, not a second execution. When the store *did* keep the first attempt's code, that code is replayed instead of this one; `meta.replayed` is `true` either way | read the first attempt in the logs, then send a fresh `Idempotency-Key` once the cause is fixed |
| `X_CONTRACT_DRIFT` | the published contract changed | input/output shape moved without a version bump | give new inputs a `.default()`, or bump the package version |
| `X_ACTION_DEPRECATION_INVALID` | an action declares a deprecation whose dates cannot be rendered | a `deprecated: { since, sunset }` value that is not a date. Refused where the declaration is converted, so the route and the OpenAPI operation refuse the same value — a `Sunset` header rendering `Invalid Date` is a contract statement no client can act on | edit `deprecated: { <field>: … }` on the action to an ISO-8601 instant — e.g. `'2026-12-31T23:59:59Z'` |
| `X_AUDIT_SINK_MISSING` | an action declares `audit: true` and no sink is installed | `setAuditSink()` never ran at boot. Raised **before the input parse** — it is the one audit failure with nothing committed behind it, and there is deliberately no logger-backed default: a line nobody stores would satisfy the declaration while recording nothing | `setAuditSink(sink)` from `@ultimat3/action` at boot, before `registerActions()`. Two ship: `postgresAuditSink({ executor })` — append-only `x_audit`, one row per record, no purge — and `memoryAuditSink()`, which is a **bounded ring that drops** (1,000 records, oldest first, `dropped` counts them) and is the dev sink, not a system of record. Nothing applies `SQL_AUDIT_TABLE` at boot yet, so run that DDL once against the app's database before installing the Postgres sink |
| `X_AUDIT_SINK_FAILED` | an action ran and its sink refused the record, so the change is unrecorded | the sink threw on an `allowed` record — the handler had **already committed**, so this is not a rollback. A refused `denied`/`failed` record is logged instead and the original error still reaches the caller, because answering with an audit error there would hide the `X_FORBIDDEN` and turn the audit backend's health into an oracle | **the fix branches on whether this call is replayable**, and `meta.replayable` carries the same fact. Replayable (the call arrived with an `Idempotency-Key`): fix the sink, then retry with the **same** key — the replay re-records without re-running the handler. Not replayable (no key was in play, whether or not the action declares `idempotent`): fix the sink and **reconcile this one change by hand — do not retry**, because a second call runs the committed handler again |
| `X_RPC_FAILED` | the typed client could not reach the action or the query | gateway, network, a non-JSON response, or a body whose `code` is not a framework code in `X_` SCREAMING_SNAKE form — `""`, `error` and `x_input_invalid` are all refused, not just a missing prefix | check the gateway, then `x actions describe <name> --json` (`x queries describe <name> --json` for a read) |

A code the SERVER threw keeps its own code on the client — including one this table never
lists, because an app declares its own through `registerErrorStatus`. The typed client rebuilds
it as a `RemoteActionError` marked `meta.origin: 'remote'`, linked to the first of the server's
`docs` and RFC-9457 `type` that is an absolute `http(s)` URL — a `javascript:` in the preferred
slot costs nothing, it does not suppress the other — and otherwise to this page, which is the error
index. It never synthesizes a **per-code** URL for a code no row here documents: there is one docs
URL in the framework, `ERROR_DOCS_URL`, and a code lives here in a table row, which has no anchor to
link at. `As of 2026-08-23`.

## Jobs

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_IDEMPOTENCY_REQUIRED` | the job has no `idempotencyKey` | the field was omitted — normally a compile error, checked again at registration | add `idempotencyKey: (input) => '<stable>:' + input.id` |
| `X_JOB_TENANT_REQUIRED` | the job declares no tenant | the field was omitted — normally a compile error, checked again at declaration, and reached through `backfill()` too, which forwards its `tenant` to `job()` verbatim. A job body runs with no request behind it, and `@ultimat3/entity`'s tenant guard derives from the **ambient** context, so a job that declared nothing ran with no tenant at all: a row naming another org was refused over HTTP as `X_TENANCY_ACTOR_MISMATCH` and accepted through the queue. A boot-supplied service actor would close the same hole with one identity for every job, which is the cross-tenant read the declaration exists to prevent. `'none'` declares **no** org either way, but it reads differently on each side of the factory: on a `job()` it means the body touches no tenant-scoped table, because every scoped read then fails closed as `X_TENANCY_ACTOR_ORG_REQUIRED`; on a `backfill()` it is how a sweep says it spans every tenant, and the pass — never the author — opens the cross-tenant scope for it | add `tenant: (input) => input.orgId` to the job; use `tenant: 'none'` for a job that touches no tenant-scoped table, or for a `backfill()` that sweeps every tenant |
| `X_JOB_DUPLICATE` | a name or a live key already has a job | a second enqueue inside the dedupe window, or a second job/task registered under a name already taken | pass `onConflict: 'dedupe'` or make the key narrower; for a name clash, rename one export |
| `X_STEP_DUPLICATE` | two `step.run` calls share a name | copy-paste inside `run()` | rename one — step names are the replay key |
| `X_JOB_MAX_ATTEMPTS` | the job exhausted its retries | a step kept failing | `x jobs show <id> --json` for the step trace, then `x jobs retry <id>` |
| `X_JOB_TIMEOUT` | a job exceeded its wall-clock limit | one long step | raise `timeout`, or split the work into more `step.run()` calls |
| `X_JOB_ROW_STATUS_UNKNOWN` | a queue row carries a status this build does not know | a rolling deploy where a **newer** worker wrote a status this build has no name for. The decoders used to `as`-cast the column, which is worse than it sounds: `steps.ts:263` returns a step's memoized output only when the status is `completed`, so a laundered value turned "this step already ran" into **run it again** | drain the older workers, or roll forward — `x jobs show <id> --json` prints the row. The reverse direction cannot fire: a release that only adds a status still knows every older one |
| `X_JOB_CLAIM_QUEUES_EMPTY` | a driver was asked to claim with `queues: []` | an empty list names no queue, and the two shipped drivers had two meanings for it — every queue on the memory driver, the `default` queue on the Postgres one — while `ClaimOptions.queues` documented neither. Each meaning is silently wrong in the other's deployment: one takes work this worker was never configured for, the other drains nothing and reads as an idle queue. Reachable only by an embedder, since `createWorker` passes exactly one queue per pass | pass the queue by name — `driver.claim({ queues: ['default'], limit, visibilityTimeoutMs, workerId })` — or read the list from `jobs.queues`, which is what `createWorker` walks one queue at a time |
| `X_ACTION_JOB_UNBRIDGED` | an action projection was registered as a job | `registerJobs({ x: someAction.job() })`. `.job()` returns a **handle**, not a job — `action` and `jobs` are both tier 3 so neither may import the other. It used to be skipped in silence alongside the helpers and constants a module namespace carries, so the job simply never ran and nothing failed anywhere | register the real `job()`, or bridge it the way `agentJob()` in `@ultimat3/ai` does — it composes a job from the handle's `idempotencyKey` and `invoke` |
| `X_JOB_CONCURRENCY_UNENFORCEABLE` | `job.concurrency` is declared and cannot be enforced | a jobs driver with no lease store — the cap then holds per **process** and the fleet runs `concurrency × replicas`. `job.concurrency` was documented, in the manifest, and enforced by nothing; the worker now refuses to start rather than run with the wrong number, which is what axiom 3 means by a convention that is not a build error not existing | remove `concurrency` from the job `cause` names, or call `setJobDriver(createPgDriver({ executor }))` at boot |
| `X_JOB_LEASE_LOST` | the queue took this job back mid-run | `x jobs cancel` wrote a terminal state, or this worker's visibility lease lapsed and another worker re-claimed the row. Its own code and not `X_ABORTED` because the response differs: `X_ABORTED` is "your deadline passed, make the work smaller", this is "somebody else owns this run now, stop writing to it" | `x jobs show <id> --json` |
| `X_JOB_SLOT_LOST` | the fleet concurrency slot this run held was taken by another worker | this worker stalled past the slot TTL and a second worker renewed slot 0 for itself, so `job.concurrency` was about to be exceeded. Its own code and not `X_JOB_LEASE_LOST` because the queue may still consider this worker the owner of the *job* — the two are different rows on different clocks (`x_job_leases` vs `x_jobs.visible_at`), and only one of them was lost. The run is aborted rather than left to double up | `x jobs show <id> --json` — a run that keeps losing its slot is slower than its slot TTL, so raise the TTL or make the job shorter |
| `X_JOB_NOT_CANCELLABLE` | the job cannot be cancelled | `x jobs cancel` reached a job that already finished, or an id no queue holds — not a failure of the command, but never a silent success either: an operator cancelling a runaway pass has to know whether they stopped it or missed it. Also raised by a driver with no `introspect.cancel` (the redis and nats stubs, and any hand-rolled driver) | `x jobs ls --state running --json` — for a driver that cannot cancel one job, call `setJobDriver(createPgDriver({ executor }))` at boot, then `x jobs cancel <id> --json` |
| `X_OUTBOX_NO_TX` | enqueue outside a transaction | `<job>.enqueue` called with no ambient tx | wrap in `ctx.tx(async (tx) => …)`, or enqueue with `{ outbox: false }` deliberately |
| `X_DRIVER_UNAVAILABLE` | the queue driver is unreachable | Redis/NATS down, or the URL is wrong | `x doctor --json`; check the driver URL in `app.config.ts` |

### Outbound webhooks

`webhook()` is a job factory, so a delivery ends on one of these eight — every one thrown inside a worker, where `ROLE=worker` opens no HTTP port, so none of them ever answers a request. The INBOUND pair is `X_WEBHOOK_SIGNATURE_INVALID` and `X_WEBHOOK_SIGNATURE_STALE` under [HTTP](#http), and both are 401.

The retry classification is what the split is for, and all eight are **listed** in `registerErrorRetry` rather than left to the default: `classifyThrown` reads an unregistered code as UNCLASSIFIED, which spends a delivery's whole retry policy re-proving that a 404 endpoint is still a 404.

| Classification | Codes |
|---|---|
| `retryable` | `X_WEBHOOK_DELIVERY_FAILED` |
| `retry-after` | `X_WEBHOOK_DELIVERY_THROTTLED` |
| `terminal` | the other six |

No secret and no signature reaches a `cause`, a `fix` or a `meta`, and a URL is redacted to origin + path — several senders in the wild put a token in the query string, and all three fields reach the log store and the dead-letter row.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_WEBHOOK_ENDPOINT_UNKNOWN` | no endpoint carries this id | the `endpoint` seam answered nothing for an id a queued delivery names — usually an endpoint the app deleted between the enqueue and the attempt. Terminal: a queued delivery cannot invent a destination | return the endpoint row for the id `cause` names from `webhook("<name>").endpoint`, or stop enqueueing deliveries for endpoints your app has deleted |
| `X_WEBHOOK_ENDPOINT_INVALID` | the endpoint cannot be delivered to as declared | three conditions, one code, and `cause` names which: an empty secret, a `url` that is not a url, or a scheme that is not `http:` or `https:`. The scheme is refused by NAME rather than by a blocklist — a delivery opens an HTTP conversation, and `file:` or `data:` is a row in a table reaching the worker's filesystem. A delivery with no secret is an unsigned POST to wherever the row points | give the endpoint an `https://` url and a non-empty secret before `webhook("<name>").endpoint` returns it |
| `X_WEBHOOK_ENDPOINT_DISABLED` | the endpoint takes no deliveries | the app disabled the row — refused before the ledger and before the socket, which is the whole point of disabling one — or this delivery is the one that reached `disableAfter` (default 10 consecutive failures, roughly a day of a retrying queue against a dead receiver), where `cause` prints both numbers. In the second case this code REPLACES the attempt's own: what an operator needs to see is that deliveries have stopped, not the status of the one that tipped it over. Terminal by construction — the next attempt reads the same row | fix the receiver, then re-enable the endpoint in your own table and enqueue the deliveries it missed — the framework never re-enables one on its own, because a dead endpoint that heals itself is a retry loop with no end |
| `X_WEBHOOK_EVENT_UNKNOWN` | no event carries this id | the `event` seam answered nothing for a queued id — the delivery was enqueued outside the transaction that writes the event row, so the read raced the commit | write the event row before enqueueing its delivery, inside the same transaction, so `webhook("<name>").event` can never be asked for a row that is not committed yet |
| `X_WEBHOOK_EVENT_INVALID` | the event cannot be signed as declared | an id or a topic that would make the canonical string ambiguous: outside 1–200 characters, or carrying a `:` or a control character. Refused BEFORE the mac is taken, because a mac over an ambiguous string is a valid signature for a delivery the sender did not write — over `v1:<t>:<id>:<topic>:<body>`, id `evt:01HZ` with topic `orders.paid` and id `evt` with topic `01HZ:orders.paid` are the same bytes | change how your app mints the field `cause` names — the separator can never appear in either, so the edit is at the mint site and not at the send |
| `X_WEBHOOK_DELIVERY_FAILED` | the endpoint did not accept the delivery | a 5xx, a 408, a 425, a 429 that named no delay, or a connection that never opened. The one **retryable** code here, and the reason the split exists at all: this is the same request landing later. `cause` carries the status or `never answered`, plus origin and path | no edit here — the job retries on its declared backoff; watch the endpoint with `x jobs ls --json` and fix the receiver before it reaches `disableAfter` |
| `X_WEBHOOK_DELIVERY_THROTTLED` | the endpoint asked for the delivery later, and said when | a receiver that answered a **retryable** status AND a delay — a 403 carrying a `Retry-After` is still `X_WEBHOOK_DELIVERY_REJECTED`, because the status is what says a retry can change something. Its own code because the answer is different work: classified `retry-after`, so `statedDelayMs` reads `meta.retryAfterSeconds` and the nack waits exactly that long — clamped by the policy's `maxDelay` — instead of spending a curve against a number it was already given | no edit here — the next attempt waits the delay the receiver named; an endpoint that throttles constantly wants a higher `retry.maxDelay` or fewer events fanned out to it |
| `X_WEBHOOK_DELIVERY_REJECTED` | the endpoint refused the delivery in a way a retry cannot change | a 4xx that is not a throttle, or a redirect. Its own code rather than a per-instance flag on the row above: `classifyThrown` reads a per-instance `terminal` on an unregistered code as UNCLASSIFIED, so the distinction has to be a registered code or it does not exist | `x jobs show <id> --json` — `meta.status` is the answer; then correct the url or the secret on this endpoint row in your own table. A 401 or 403 is a secret the two sides disagree about, a 404 is a path that moved |

### Exports

`exportRows()` is a job factory too, and both its codes refuse the DECLARATION rather than the data — the same `row()` over the same page answers the same way on every attempt, so both are `terminal`.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_EXPORT_ROW_INVALID` | `row()` answered something the declared columns do not carry | a column missing, a column nobody declared, or a value no format can carry. The extra-column half is the one worth the code: a `row()` returning a key `columns` omits is silently DROPPED by both encoders, so the rest of the file looks perfectly correct and the gap is found by whoever consumes it, later — and the reverse, `row: (r) => ({ ...r })`, is how PII leaves through an export nobody reviewed, picking up every column the entity gains from then on. `cause` names the COLUMN and never the value: a cell is user data by definition, and a cause reaches the log store as a field nothing can redact | return exactly the declared columns from `row()` on `exportRows("<name>")`, each one a string, a finite number, a boolean or `null` — format a date with an explicit `timeZone` and a Money with its own currency before it gets here |
| `X_EXPORT_PART_TOO_LARGE` | one page encoded to more bytes than a part may hold | a page whose encoded size passed `maxPartBytes` (default 8 MiB). The memory bound made mechanical: accumulating a result set before writing it is the failure `exportRows()` exists to prevent, and "we hold a page, not a dataset" is only true while a page is bounded — a row that is a megabyte of JSON turns a thousand-row page into a gigabyte in one buffer | lower `batch` on `exportRows("<name>")` until a page fits (the default is 500 rows), or raise `maxPartBytes` if this deployment really can hold that much per part — the number is a heap bound, not a file-size preference |

## Realtime

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_SOCKET_UNAUTHENTICATED` | the sync upgrade carried no credential this app accepts | the app's `authenticate` hook decided this upgrade belongs to nobody. **A decision, not a fault** — it never pages anyone, because the refusal is the whole point of the hook. Until this cycle there was no way to authenticate a WebSocket at all, so realtime was single-tenant only. Distinct from `X_TOPIC_FORBIDDEN`, which is a subscriber that already has a socket and asked for something it may not have; this one never gets a socket, so the client learns about it by tearing the connection down | send the credential `createSyncNode({ authenticate })` reads on the upgrade request, or return an anonymous `Actor` from it to admit this socket |
| `X_SOCKET_AUTH_UNAVAILABLE` | the sync node could not decide who a connecting socket is | `authenticate` **raised** instead of deciding — a token service that timed out, a JWKS fetch that failed. The same rule the row gate follows: a failure is not a denial, so the client is told to come back rather than told it may not connect, and this one **does** page someone | `x doctor --json` |
| `X_TOPIC_FORBIDDEN` | the actor may not subscribe to this topic | no guard, or the guard denied | `hub.guard('<topic>', ({ actor }) => …)` |
| `X_SUBSCRIPTION_LIMIT` | socket, tenant or node hit its subscription cap | a component subscribing in a loop, or one client minting distinct `(query, input)` pairs — a `qid` derives from client-chosen input, so the node holds a matcher and a row window per value. The scope in the message says which ceiling refused | raise `maxPerSocket` / `maxPerTenant` / `maxEntries` on `new LiveQueryRegistry({…})`, or `maxTopicsPerSocket` / `maxTopicsPerNode` on `new ChannelHub({…})` — none of them is an `app.config.ts` field |
| `X_FRAME_RATE_LIMIT` | one socket sent frames faster than this node will route them | the accept budget spends a token per *upgrade*, so an open socket was unbounded: one authenticated client could drive a database read, a shared-store presence write and a fleet-wide publish per frame. A client fault: it never pages anyone | batch subscribes into one frame per subscription and retry after the delay, or raise `maxFramesPerSecond` where `createSyncNode()` is called |
| `X_SUBSCRIPTION_ID_TAKEN` | a subscribe frame reused a `sid` this socket already holds | a hand-rolled client incrementing its own subscription ids, or a remount that reuses one. | `X_PROTOCOL_VERSION` | client and sync node disagree on the wire protocol | a client from an older build | `x build` and redeploy the client; the node sends `update-available` before draining |
| `X_CURSOR_STALE` | the resume LSN is outside the change buffer | a long disconnect | pass `snapshot` to `resumeFrom()` so the fallback re-snapshots |
| `X_REBASE_CONFLICT` | a local mutation could not be rebased | server state moved incompatibly | set `conflict: 'server-wins'`, or return a row from `custom(merge)` |
| `X_TRANSPORT_UNAVAILABLE` | the fanout bus is unreachable | the nats-server `NATS_URL` names is down or misconfigured | `x doctor` — then check `NATS_URL` |
| `X_TRANSPORT_PROTOCOL` | the bus does not speak the protocol this build speaks | nats-server older than 2.11, JetStream not enabled, or something that is not NATS on the port | run `nats:2.11-alpine` or newer with `-js`; reconnecting cannot fix it, so this never retries |
| `X_REPLICATION_FAILED` | the replication connection was refused | `wal_level` not `logical`, no publication, a slot another replicator holds, wrong credentials | the message names the object; the fix is the exact `ALTER SYSTEM` / `CREATE PUBLICATION` / `pg_drop_replication_slot` statement |
| `X_REPLICATION_PROTOCOL` | the WAL stream cannot be decoded | a server or `pgoutput` version this build does not speak, or a proxy on the replication port | `x doctor db` — point the URL at postgres itself, on a server ≥ 14 |
| `X_REPLICATOR_SLOT_HELD` | another replicator already owns this database | `replicator` scaled to more than one replica, or a rolling deploy started the new replicator before the old one exited — nothing is wrong with this process, the database already has its one replicator | scale the replicator to 1 per database: `kubectl scale deploy/replicator --replicas=1` |
| `X_LIVE_CLIENT_MISSING` | a realtime hook ran in a browser with no `LiveClient` registered | `useLive` / `useConnection` / `useMutation` / `useMutationQueue` in a browser whose entry never registered one — a server render is not this: with no DOM every hook falls back to `serverRenderLiveClient()` | `setLiveClient(new LiveClient({ signal: createSignal, connect, buildId }))` in the app entry, above the first render |
| `X_LIVE_SERVER_RENDER` | a browser-only live operation ran during a server render | `mutate()` or `drain()` reached from a page body — a server render has no socket, so `@ultimat3/realtime` hands it `serverRenderLiveClient()`, which serves the first render and refuses everything that can only mean "talk to the socket"; a dropped mutation would look exactly like one that happened | call it from an island `mount()` instead of from the page, or guard it with `hasLiveClient()`, which answers `false` on the server |
| `X_QUERY_NOT_SUBSCRIBABLE` | a hook was bound to a query that is not declared live | `liveHookFor(orgPosts)` where `orgPosts` has no `live: true` — there is no subscription for the hook to read, so it could only ever answer an empty set | add `live: true` to the query declaration, or read it once through `query.client({ baseUrl })` |
| `X_LIVE_ROW_UNIDENTIFIED` | a live query returned a row with no id | a `live: true` read whose projection selects columns but not the primary key — patches, cursors and the local store all address a row by `id` | select the primary key in that query's `sql()`, or drop `live: true` from it |
| `X_LIVE_REPLICA_IDENTITY` | a replicated table sends a key-only row on delete | the table's replica identity is not `FULL`, so a delete carries the key columns only and a live query decides "did this row leave the result set" from a partial row — warned at preflight, never thrown, because an app running on the default identity would otherwise stop booting | `ALTER TABLE <t> REPLICA IDENTITY FULL;` — one per table the warning names; rows already in the WAL keep the identity they were written with |
| `X_LIVE_QUERY_UNKNOWN` | no live query is registered under the name a `subscribe` frame asked for | a misspelled name, or a query never passed to `defineApi({ queries })` — the frame parsed and the version matched, so this is not a protocol skew and a client rebuild cannot change it | `x queries list --json` |

## Cache

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_CACHE_TAG_UNKNOWN` | a tag no entity declared | typo in `invalidates: [tag.pots]` | `x manifest` to regenerate the tag graph, then fix the tag |
| `X_CACHE_TOO_LARGE` | one entry exceeds the tier's byte budget | caching a whole row set | raise `cache.<tier>.maxBytes`, or cache a projection |
| `X_CACHE_DRIVER_UNAVAILABLE` | a tier's backing store is missing | no Redis binding, or a purge driver built without `FASTLY_API_TOKEN` / `CLOUDFLARE_API_TOKEN` | provision the tier, or drop it from `app.config.ts` |
| `X_CACHE_TTL_INVALID` | a cache TTL that is not a positive number of milliseconds | `ttlMs: 0`, a negative value, `NaN` or `Infinity`. `0` used to mean "never expires" in the memory tier and "one second" in the Redis tier, so a stack holding both answered differently depending on which tier hit | pass a positive `ttlMs`, or omit it and inherit the tier's default — "do not cache" is expressed by not declaring a `cache` block |
| `X_CACHE_LIMIT_INVALID` | a tier is given a numeric limit outside the domain its option accepts, refused at **construction**. Three domains, and the refusal names which: a **capacity** (`maxEntries`, `maxBytes`) is a whole number greater than zero; a **duration** (`defaultTtlMs`, `loadDeadlineMs`, a driver's request budget) is a whole number of milliseconds greater than zero; a **similarity floor** is a number from 0 to 1. So finite zero, a negative, a fraction and an unsafe integer are all refused too — not only `NaN` and `Infinity` | `maxEntries`, `maxBytes`, `defaultTtlMs`, `loadDeadlineMs` or a similarity floor arriving as `NaN` or `Infinity` — most often `Number(process.env.CACHE_LIMIT)` on an unset variable, which is `NaN` and is **not** nullish, so `??` does not catch it and `Math.max`/`Math.min` propagate it. The failure is the dangerous direction: a comparison against `NaN` is false for **every** entry, so the limit stops being enforced rather than being enforced wrongly — an unbounded cache that reports healthy. The cause names that mechanism **only for `NaN`**: the same refusal also catches `Infinity`, `0`, a fraction and an unsafe integer, where the bound is applied as given rather than disabled — a ceiling of `Infinity` is never exceeded and a similarity floor of `Infinity` is never met, which are opposite outcomes one sentence cannot claim at once. Raised at construction rather than on the first write, where `X_CACHE_TTL_INVALID` would have named the write instead of the config | the cause names the tier and the option; set it in `app.config.ts`, and parse an environment value before passing it. Where the value is a call argument rather than a config key — `createCacheStack({ loadDeadlineMs })`, `lookup(embedding, override)` — the fix names the **argument**, because sending that caller to `app.config.ts` names a key that does not exist. `bun run finite-bounds` is the repo-wide rule |
| `X_CACHE_JITTER_INVALID` | a TTL jitter fraction outside `[0, 1)` | `cache.<tier>.jitterFraction` at `1` or above, negative, or not finite. Jitter exists because 40,000 keys warmed by one rolling restart share one TTL and therefore one expiry instant, and spreading them is the only thing that stops the herd — a fraction of `1` shaves a whole lease away, a negative one **extends** it past what the caller asked for. Both are miswiring rather than preference, refused where the TTL rule already lives | set `cache.<tier>.jitterFraction` in `app.config.ts` to a value in `[0, 1)` — `0.05` is the default, `0` disables jitter |
| `X_CACHE_PURGE_FAILED` | the CDN refused a purge | a wrong or unscoped API token, a zone without tag purge, a throttle, a key carrying whitespace or a comma | `meta.retryable === true` → the identical purge can land again; `false` → set the env key the `fix` names, then `x dev` |

## Storage

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_STORAGE_CHECKSUM_MISMATCH` | bytes do not match the declared checksum | a truncated upload, or a sha256 computed over different bytes than the ones sent | recompute the checksum over the exact bytes you send, or omit it and let the driver hash |
| `X_STORAGE_DELETE_FAILED` | the object could not be deleted | the provider **refused** — a denied `s3:DeleteObject`, a throttle, an expired credential, a read-only mount. Deleting an absent key stays idempotent and never reaches here; everything else does, because the alternative shipped for a year: a `.catch(() => undefined)` turned 200 denied deletes into 200 successes and an erasure sweep reported data gone that was still there | the `fix` is the driver's own, so it reproduces the refusal with the provider's words — a generic one is a round trip |
| `X_STORAGE_LIST_FAILED` | the objects could not be listed | the disk **refused** a listing — a denied `s3:ListBucket`, a throttle, an expired credential, a root this process cannot read. A disk nobody has written to yet is honestly empty and answers an empty page; everything else reaches here, because `sweepOrphans` walks `list()` and a swallowed refusal certifies a prefix nothing could see as having no orphans | the `fix` is the driver's own — `ls -ld <root>` on `local`, `aws s3api list-objects-v2 --bucket <bucket>` on `s3` — so it reproduces the refusal with the disk's own words |
| `X_STORAGE_QUARANTINED` | the object is still in quarantine | `promoteAttachment` reached a key still under the quarantine prefix. The framework never scans bytes — that is the app's job — so the only thing it can enforce is that nothing leaves quarantine without the app saying so | scan the bytes, then `releaseQuarantine({ disk, key: '<key>', orgId: '<orgId>' })` — promote the key it returns |
| `X_STORAGE_DISK_UNKNOWN` | no disk with that name is configured | `disk('<name>')` for a disk `storage.disks` never declared | add `"<name>"` to `storage.disks` in `app.config.ts`, or call one of the names `cause` lists |
| `X_STORAGE_NOT_FOUND` | no object at that key | a stale key, the wrong disk, or an object already deleted | list the prefix and compare: `await disk('<disk>').list({ prefix: '<dir>' })` |
| `X_STORAGE_PATH_UNSAFE` | object key escapes its prefix | an absolute key, a `..` segment, or a backslash | build the key with `scopedKey(orgId, ...parts)` — relative, forward slashes, no `..` |
| `X_STORAGE_TOO_LARGE` | payload exceeds the upload size limit | a file over the policy's `maxBytes`; `cause` carries both numbers | `uploadPolicy({ maxBytes: <bytes> })` for a higher limit, or compress the file first |
| `X_STORAGE_TYPE_REJECTED` | content type is not allowed for this upload | a type absent from `allowedContentTypes`, or magic bytes that disagree with the declared `Content-Type` — the bytes win | add the declared type to `allowedContentTypes` in the upload policy, or re-upload with the `Content-Type` `cause` sniffed |
| `X_STORAGE_URL_INVALID` | signed URL does not match its signature | an edited constraint (`x-max`, `x-ct`, the key), a URL outside the mounted base, a `PUT` grant replayed as a `GET`, or a `Content-Type` header the signature does not cover | mint a fresh one with `grantUpload({ disk, orgId, request })` and send it unedited — every constraint is inside the signature |
| `X_STORAGE_URL_UNVERIFIABLE` | nothing can check the signature — no verifier was supplied | `acceptSignedUpload` was called with no `secret:` and the disk's driver implements no `verifySigned`. **Its own code deliberately, not `X_STORAGE_URL_INVALID`:** "no verifier" and "this signature is forged" need opposite edits, and reporting the first as the second sends an operator hunting an attacker who is not there | implement `verifySigned` on the driver, or pass `secret:` explicitly — a local disk already verifies its own |
| `X_STORAGE_URL_EXPIRED` | signed URL is past its expiry | a form left open longer than the grant's window | call `grantUpload({ disk, orgId, request, expiresInMs })` again — a longer `expiresInMs` widens the window the signature grants |
| `X_STORAGE_ORG_MISMATCH` | object key belongs to another org | a key from one tenant used while the actor resolves to another; the signature can be perfectly valid and this still fires | build it with `scopedKey('<orgId>', ...parts)`, and pass the **actor's** org as `orgId` — never one read off the request |
| `X_STORAGE_UPLOAD_FAILED` | the signed upload was refused | the presigned `PUT` answered non-2xx, or never reached the disk (`status: 0`) | call `uploadFile({ file, grant })` again for a fresh grant; a 4xx here is the constraint named in the body, not a transport fault |
| `X_STORAGE_SECRET_DEV` | upload grants would be signed with the shipped development key | `STORAGE_SIGNING_SECRET` is unset or holds the constant published in `@ultimat3/storage`, in a non-local environment — anyone can then mint a `PUT` grant offline with a `maxBytes` and `contentType` of their choosing, and the signed constraints outrank the app's `uploadPolicy`. Reported by `x doctor`; the local disk driver also refuses to construct | `export STORAGE_SIGNING_SECRET="$(openssl rand -hex 32)"` |

## Flags

`X_FLAG_EXPIRED` is the only code in the framework that is **reported and never thrown**: an overdue temporary flag is a debt, not an outage, so `isEnabled()` hands it to the configured `ErrorReporter` as a `warning` (rate-limited to one report per key per hour) and still answers its targeting. Everything else here fails at declaration time.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_FLAG_DUPLICATE` | two flags were declared with the same key | a copy-pasted `defineFlag()`, so one of the two declarations decides nothing | rename one of the two `defineFlag({ key: '<key>' })` declarations |
| `X_FLAG_EXPIRED` | a temporary flag is past its expiry and is still being evaluated | scaffolding that outlived the change it was wrapping; `cause` names the owner and how overdue it is | delete the branch and its `defineFlag()` declaration, or move it to `kind: 'permanent'` if it is a real product switch |
| `X_FLAG_EXPIRY_INVALID` | a temporary flag has no usable expiry date | `expiresAt` absent or unparseable — reachable from a store snapshot or plain JS; in TypeScript the union already refuses it | set `expiresAt` to an ISO-8601 date such as `'2026-12-01'` in `defineFlag({ key: '<key>' })` |
| `X_FLAG_SUBJECT_REQUIRED` | a flag decides by a subject the evaluation context does not carry | targeting names a subject kind — an org, or an app record such as `bank` — but the actor carries no `orgId`, or the call site passed no record for that kind. Answered as an error rather than a silent default, which would decide the wrong way and never say so | mint the actor with its tenant — `userActor({ id, orgId })` — for `org`; for an app kind, pass the record at the call site: `isEnabled('<key>', actor, { <kind>: '<id>' })` |
| `X_FLAG_TARGETING_INVALID` | flag targeting is out of range or malformed | `rollout: 0.5` (a fraction read as a percentage means nobody), a rollout outside 0-100, or `default: true` beside a rollout | set `rollout` to a whole percentage 0-100 in `defineFlag({ key: '<key>' })`, and leave `default` false when a rollout decides |
| `X_FLAG_UNKNOWN` | no flag is declared under this key | a typo at the `isEnabled()` call site — answered as an error rather than a silent `false`, which would be a branch that never runs and never says so | declare it with `defineFlag({ key: '<key>', … })`, or correct the key at the call site |

| `X_BOUNDARY_APP_TO_API` | `app/` imported `api/` at runtime | a value import instead of `import type` | use `import type`, and call the typed client |

| `X_ISLAND_PROPS_INVALID` | an island was handed props it may not receive | a key not listed in `props: [...]`, a value that is not JSON (a function, `Date`, class instance, `bigint`, `symbol`, `undefined`, or a cycle), or a payload over 4096 bytes. A module that calls `hasLiveClient()` has written its own fallback and is not reported | `x g island <route-dir> --at <route-dir>`, declare it with `island({ src: './<name>.island.tsx' })` above `defineRoute`, and move the live read into its `mount()` — which is where `setLiveClient()` belongs |
| `X_PRERENDER_FAILED` | a prerendered path threw during build | `prerender()` returned an id that no longer resolves | fix the data source, or narrow `prerender()` |
| `X_STYLES_GLOBAL_MISSING` | a surface renders documents whose CSS defines no `:root` custom properties | nothing in the app's module graph imports the global layer, so every `var(--color-*)` and `var(--space-*)` a component emits resolves to nothing and the browser drops the declaration | add `apps/web/shared/global.scss` containing `@use '@ultimat3/ui/global.scss';` and `apps/web/shared/global.ts` containing `import './global.scss';` — `x new` scaffolds both |

## Notifications

`notifier()` is a job factory — one queue row and one step trace for the whole fan-out, with every recipient a durable step. Five of the six codes are the app's own DECLARATION and one is somebody else's server, which is what decides the statuses: the five are 500 and `X_NOTIFY_DELIVERY_FAILED` is **502**. That row is chosen for the day a notifier is invoked in a request rather than a job, and the asymmetry decides it — a wrong 502 costs nothing, and a wrong 500 pages the on-call for an email provider's outage, because `stages.ts` reports every `status >= 500` to the error monitor.

Three of them are raised at `notifier(...)`, while the app's modules load, so they fail the boot rather than a run: `X_NOTIFY_CHANNELS_EMPTY`, `X_NOTIFY_CHANNEL_DUPLICATE`, `X_NOTIFY_DIGEST_UNSUPPORTED`. The other three are raised inside the run.

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_NOTIFY_CHANNELS_EMPTY` | the notifier declares no channels | an empty `deliver: []`. Refused where it is written: a notifier with no channel resolves its recipients on every run and delivers to nobody | add at least one entry to `deliver: []` on `notifier("<name>")` — `inAppChannel()` is the one with no external driver |
| `X_NOTIFY_CHANNEL_DUPLICATE` | two deliveries share one channel name | two `deliver` entries naming the same channel. Refused because the delivery ledger's unique index is `(notifier, key, channel, coalesce(recipient, ''))`: the second delivery would claim a row the first already owns and be dropped as a duplicate, so one of the two would silently never send | give the second channel its own name on `notifier("<name>")` — `channel('<name>-digest', …)` — or merge the two `deliver` entries |
| `X_NOTIFY_DIGEST_UNSUPPORTED` | a digest window is declared on a bulk channel | `digest:` beside a `bulkChannel()`. Refused where it is written: a bulk send has one payload for the whole audience and a window coalesces PER RECIPIENT, so the two have no shared meaning — and inventing one would be this package deciding whose events get grouped | drop `digest` from that entry and give it a `wait` instead, or deliver it through `channel('<name>', …)` one recipient at a time |
| `X_NOTIFY_FANOUT_TOO_WIDE` | the audience is larger than one run may fan out to | the resolved audience passed `maxRecipients` (default 500). One step per recipient is what makes a provider blip re-send one address rather than all of them, and a step is a durable row — so there is a width past which this is the wrong shape entirely. Refused with both numbers rather than degraded silently | deliver through a `bulkChannel()` on `notifier("<name>")`, which sends one payload for every recipient, or page the audience with `backfill()` from `@ultimat3/jobs` |
| `X_NOTIFY_STORE_MISSING` | a channel needs a store nothing installed | an in-app channel with no inbox store, or a digest window with no digest store. The delivery ledger is deliberately NOT one of these — it has a correct-for-one-process default the way every other driver seam here does. An inbox and a digest window have none: there is nowhere to put the row, so they refuse rather than skip. Never an optional chain at the call site, because a silently skipped inbox write is a notification the user never sees and nobody logs. `cause` and `meta.store` name which of the two is absent | `setNotifyStores({ inbox: createMemoryInboxStore(), digest: createMemoryDigestStore() })` at boot — **one call**, naming every store this app wants: it is whole-object replacement and never a merge, so a second call drops what the first installed. `createPgInboxStore({ executor })` shares the inbox across replicas |
| `X_NOTIFY_DELIVERY_FAILED` | a channel did not accept the delivery | a channel's `deliver` threw. Wrapped rather than rethrown so the dead-letter row carries a stable code and names the channel — a raw provider error names only itself. The ledger row is settled `failed` first and stays re-claimable, so the job's own retry policy decides whether it goes out again. Rendered through `renderThrowable`, never `${cause}`: a provider rejection is routinely an object whose `toString` throws | `x jobs ls --json` for the run, then `x jobs show <id> --json` — the failing step is `deliver:<channel>`, and `meta.channel` names it |

| `X_EVAL_BASELINE_INVALID` | a recorded baseline cannot be read | a hand-edited or half-merged baseline file | `ULTIMATE_EVAL_RECORD=1 x test eval` to re-record it |
| `X_EVAL_MISSING` | a prompt has no eval | a `definePrompt` with no `defineEval` naming it | add `defineEval({ prompt, cases, scorers, tolerance, baseline })` beside the prompt |
| `X_EVAL_RECORDING` | the gate ran with baseline recording switched on | `ULTIMATE_EVAL_RECORD` was exported in the shell, or set on the CI job, that ran `x verify` | `env -u ULTIMATE_EVAL_RECORD x verify` — record with `ULTIMATE_EVAL_RECORD=1 x test eval` instead |
| `X_VECTOR_DIM_MISMATCH` | embedding dimensions differ from the store | the embedder model changed, or the provider returned a width the embedder was not declared with. The fix used to name `x ai reindex`, which is **planned and throws** — a fix line naming it sends an operator to a wall | use the same embedder that created the store, or re-embed every record at the new width and upsert it — for a declared/returned mismatch, set `dimension:` on the embedder to the width `cause` names first |
| `X_VECTOR_SCOPE_WIDENED` | a derived vector scope tried to leave its tenant | a handler re-scoped the store it was handed | derive from the unscoped store: `vectorStore.scoped({ tenant })` |
| `X_AI_EMBEDDER_INVALID` | an `Embedder` returned fewer vectors than texts it was given | `embedOne` got an empty batch back from `embed([text])` | return one vector per input text from `embed()`, in the order the texts arrived |

## Scraping

`@ultimat3/scraping` owns its codes in `SCRAPE_OWNED_ERROR_CODES` and borrows two (`X_NOT_IMPLEMENTED`, `X_ENV_MISSING`) — the count is not written here because nothing derives it, and a number in prose beside a list that grows is a number that goes stale; `bun run manifest` re-derives the owner of every code. Every one is classified `retryable` or `terminal` **once**, in `SCRAPE_ERROR_RETRY` ([`packages/scraping/src/errors.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/scraping/src/errors.ts)), rather than re-decided by whichever `catch` saw it — a scraper's whole operational question is "was that the site being slow, or the site being different?"

The rule, stated once: **retryable means the same code, run again, has a real chance of a different answer.** Transport, budget and liveness faults qualify. Anything that says "the page is not the page this scraper was written against" does not — attempt 5 hammers a site with a request that cannot succeed, and on an authenticated target that is how three wrong attempts lock an account.

Two sets override the table, in `failures.ts`:

| Set | Codes | Effect |
|---|---|---|
| `NEVER_RETRIED` | `X_SCRAPE_AUTH_FAILED`, `X_SCRAPE_PROMPT_UNANSWERED` | no retry policy, backoff or recovery hook can reach them |
| `BURNS_SESSION` | `X_SCRAPE_BLOCKED`, `X_SCRAPE_SESSION_EXPIRED` | the persisted identity is discarded **before** the retry — a flagged profile stays flagged, so reloading it re-trips the same block every time |

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_SCRAPE_DRIVER_UNKNOWN` | no browser driver is installed for this run | **terminal.** Nothing called `setScrapeDriver()` at boot and the definition passed no `driver:`; `cause` lists what *is* installed, or `none` | call `setScrapeDriver(localBrowser())` at boot, or pass `driver: fakeBrowser()` on the `scrape()` definition |
| `X_SCRAPE_CDP_ATTACH_FAILED` | the CDP endpoint refused the attach | **retryable.** A browser host still starting, a wrong `cdpUrl`, or an endpoint that is up and not speaking CDP. The underlying throw is rendered through core's `renderThrowable`, never interpolated | `curl "$CDP_URL/json/version"` to confirm the endpoint answers, then pass that `webSocketDebuggerUrl` to `remoteBrowser({ cdpUrl })` |
| `X_SCRAPE_BROWSER_UNREACHABLE` | the browser went away mid-run | **retryable.** The browser process or host died, or stopped answering, after the attach succeeded | raise `watchdog: { idleMs }` on the `scrape()` definition if the site is genuinely slow, otherwise re-run once the browser host is back |
| `X_SCRAPE_PROFILE_LOCKED` | another process holds this browser profile | **terminal.** Two runs pointed at one `profileDir`, or a previous browser died without clearing its lock | `rm -f <profileDir>/SingletonLock` once no browser is using it, or give this run its own `localBrowser({ profileDir })` |
| `X_SCRAPE_HOST_BLOCKED` | the page asked for a host `allowHosts` does not list | **terminal.** A third-party asset, an analytics beacon or a redirect off the allow-list. The allow-list is default deny, so silence blocks | add the host to `allowHosts` on the `scrape()` definition — `cause` names both the requested URL and the current list |
| `X_SCRAPE_SELECTOR_MISSING` | the selector never appeared inside its window | **terminal — the page changed.** The markup this scraper was written against is not what the site served. Deliberately distinct from `X_SCRAPE_NOT_ACTIONABLE`: nothing matched at all, so no wait and no retry can produce one | open the run's `page.html` artifact and re-derive the selector, or raise the timeout on this `waitFor({ timeout })` |
| `X_SCRAPE_NOT_ACTIONABLE` | the element is present and cannot be acted on | **terminal — something is in the way.** Disabled, hidden, zero-sized, or covered by an overlay; `cause` names which. The separation from `X_SCRAPE_SELECTOR_MISSING` is the point — one is a rewrite, the other is a wait or a dismiss | wait for the state that unblocks it — `page.waitFor(selector, { state: 'enabled' })` — or dismiss whatever overlays it before the click |
| `X_SCRAPE_TIMEOUT` | the step exceeded its wall-clock budget | **retryable.** A slow site, a slow network, or a pass doing too much inside one budget | raise `timeout:` on the `scrape()` definition, or split the pass so each `step.run` stays inside one budget |
| `X_SCRAPE_WEDGED` | the browser stopped answering and was killed | **retryable.** No browser activity at all for `watchdog.idleMs`, so the watchdog killed the process. The session went with it | raise `watchdog: { idleMs }` on the `scrape()` definition if the site is genuinely this slow, otherwise re-run — the browser was killed and its session is gone |
| `X_SCRAPE_WATCHDOG_STOPPED` | the wedge watchdog stopped measuring and the run was ended | the `ScrapeClock` the scrape definition supplied has a `sleep()` that **rejects**, so the guard's poll loop died and nothing was left watching for a wedged browser. Ended rather than run unwatched: a guard that stopped measuring is the first incident with nothing armed. A separate code from `X_SCRAPE_WEDGED` on purpose — that one means the page stopped answering, and sending a reader there to investigate a page that is fine is the whole cost of reusing it. **Terminal, where its sibling is retryable**: attempt 2 reaches the same clock identically, so retrying buys five browser launches that die at the first poll — and on an authenticated target, five arrivals at a login | `drop the custom clock: from the scrape() definition — systemScrapeClock is the only ScrapeClock whose sleep() cannot reject — then re-run` |
| `X_SCRAPE_PAGE_CRASHED` | the renderer process died | **terminal**, and it is the one liveness fault that is. A dead renderer takes its tab's state with it, so a re-run of a half-submitted form is the incident rather than the recovery. Out of memory far more often than a bug | lower `concurrency:` on the `scrape()` definition, or raise the container memory limit in `docker-compose.prod.yml` |
| `X_SCRAPE_OUTPUT_INVALID` | the extracted rows do not match the extract schema | **terminal.** The selectors still match and what they yield no longer parses — a column that became empty, a number that became a range, a date that changed format | align the extract schema with the page — the run's `page.html` artifact holds the markup the rows came from |
| `X_SCRAPE_YIELD_COLLAPSED` | the run succeeded and returned far too little | **terminal, and the silent-green alarm.** Two triggers: fewer rows than `expect.minRows`, or a fall past `expect.maxDrop` against the trailing median of the last `expect.window` runs (default 7, and no baseline below 3 samples). A run that succeeds and returns nothing is the worst failure a scraper has, because it stays green. **A collapsed run is deliberately not recorded** — check, then record, and record only a run that passed, or three broken runs at 2 rows make the median 2 and the alarm silences itself exactly when it was working | open the run's `page.html` artifact and compare it with the extract selectors — a collapse is the page changing far more often than the data changing |
| `X_SCRAPE_YIELD_HISTORY_MISSING` | a `maxDrop` is declared and no history store can supply its baseline | **terminal, raised at declaration time.** `expect.maxDrop` measures a fall against a trailing baseline, and with no `history:` store `expect.ts` reads `[]` forever — so `X_SCRAPE_YIELD_COLLAPSED` can never fire and the alarm is silently inert. `expect.minRows` is an absolute floor checked before the history gate and stays legal on its own | add `history: memoryYieldHistory()` for a test, or your own `YieldHistory` in production — or drop `expect.maxDrop` and keep `expect.minRows` |
| `X_SCRAPE_DOWNLOAD_TIMEOUT` | the download never landed | **retryable.** A slow file, or a trigger that is not the element that starts the download | raise the timeout on `page.download({ timeout })`, or confirm the trigger is the element that starts the download |
| `X_SCRAPE_ROBOTS_DISALLOWED` | `robots.txt` disallows this path | **terminal.** The site's own file refuses this path for the declared user agent | declare `robots: { ignore: '<the written reason this run is permitted>' }` on the `scrape()` definition, or scrape a path `robots.txt` allows |
| `X_SCRAPE_FIXTURE_MISSING` | the fixture driver has no recording for this request | **terminal.** An offline driver never reaches the network, so an unrecorded URL has no answer to give | add `<fixtureDir>/<the recording file>` holding `{ "url": "…", "html": "…" }`, or point `fixtureBrowser()` at the directory that already holds it |
| `X_SCRAPE_FIXTURE_STALE` | the recording is older than the fixture max age | **terminal.** A test passing against a year-old copy of a page proves the test still parses the copy, not the site | re-record the fixture directory, or raise `maxAge` on `fixtureBrowser({ maxAge })` with the reason an old recording still proves something |
| `X_SCRAPE_REMOTE_REQUIRED` | this driver needs a `cdpUrl` and was given none | **terminal.** `remoteBrowser()` attaches to a browser somebody else started; there is nothing to attach to | pass `remoteBrowser({ cdpUrl: env.SCRAPE_CDP_URL })`, or use `localBrowser({ launcher })` to start one in this container |
| `X_SCRAPE_RECOVER_REFUSED` | the recovery hook declined to recover this failure | **terminal.** `recover()` was declared and returned no strategy for this failure, so the original failure stands and the run ends where the hook left it | widen `recover()` to handle this failure, or drop `recover:` and let the job's retry policy own it |
| `X_SCRAPE_SECRET_EXPOSED` | an artifact would have carried a secret this run typed | **terminal.** A screenshot or a video was requested after a secret was typed into the page, and pixels cannot be redacted afterwards. Refused rather than captured-and-scrubbed | call `artifact.html()` instead — page HTML is redacted by value and password fields are blanked — or take the capture before the secret is typed |
| `X_SCRAPE_HTTP_FAILED` | the site answered the HTTP leg with a non-2xx status | **retryable by default** — 429, 5xx and a deploy window are transient far more often than not. A 4xx that `isRetryableStatus` (`@ultimat3/core`) calls permanent is thrown with a per-instance `terminal` override, because the same code is both and only the throw site knows which it saw — **408, 409, 425 and 429 keep their attempts** `As of 2026-08-23`. This row said "below 500 other than 429" until then, and a private copy of the table here called 408 and 425 terminal while the rest of the framework called them retryable; a terminal classification dead-letters the run on the attempt that failed rather than spending its declared `attempts` | confirm the endpoint the browser leg calls is the one this request names — `page.network()` lists every URL the page actually fetched |
| `X_SCRAPE_BODY_TOO_LARGE` | the HTTP leg's response body ran past `maxBytes` | **terminal.** A response's size is a property of the endpoint, so attempt 2 reads the same bytes and dies identically. The default is 32 MiB (`DEFAULT_HTTP_MAX_BYTES`) — generous for the JSON endpoint behind a paginated page, far under what OOM-kills a worker. Before this the leg did `await response.text()`, which materialises the whole body: `AbortSignal.timeout` bounds TIME, not bytes, so a 30s stream at 50 MB/s was a 1.5 GB allocation and the run persisted nothing | raise it for the one call — `page.fetch(url, { maxBytes: 64 * 1024 * 1024 })` — or narrow the endpoint so it answers a page rather than a corpus. Never raise it globally: the cap is what stops one hostile origin taking the worker down |
| `X_SCRAPE_AUTH_FAILED` | the credentials were rejected | **TERMINAL, always, and the retry table cannot be talked out of it.** It is in `NEVER_RETRIED`, so no retry policy, no backoff and no recovery hook can reach it. A site that locks an account after three wrong attempts turns a retrying framework into the thing that destroys the user's account | correct the credential in `.env.local` for the name listed in `secrets:` on the `scrape()` definition — this run will **not** be retried, deliberately: a second wrong attempt is how an account gets locked |
| `X_SCRAPE_SESSION_EXPIRED` | the restored session is no longer valid and nothing can renew it | **terminal**, and it **burns the session**: the stored state failed its `auth.validate()` probe and the definition declares no `auth.login`, so there is nothing to replace it with | add `auth: { login }` to the `scrape()` definition so an expired session can be replaced, or drop `auth.validate` and let the body handle the logged-out page |
| `X_SCRAPE_PROMPT_UNANSWERED` | a login step asked for a code and nothing answered | **terminal**, and in `NEVER_RETRIED` — an out-of-band code is not something a second attempt invents | add `prompt: async ({ label }) => await otpFor(label)` to the `scrape()` definition — a code that arrives out of band needs somewhere to come from |
| `X_SCRAPE_CAPTURE_INVALID` | the capture names a framing no picture can be taken with | **terminal** — the rectangle is the caller's own literal, so attempt 2 passes the identical one, and it is refused before any driver runs, so there is no half-done capture to resume. Three shapes: `fullPage` beside a `clip` (CDP silently ignores one, so the caller gets a picture they did not ask for), a rectangle with no area or a non-finite number, and a `clip` on `page.pdf()`, which has no crop and would answer a whole-page PDF to a caller who asked for one component. A rectangle merely BELOW THE FOLD is accepted — this package sets and reads no viewport, and refusing it would reject the component-screenshot case it exists for | drop `fullPage` or drop `clip`; measure the element with `page.query('<selector>')` and pass a rectangle with a positive width and height; a PDF has no crop — use `page.screenshot({ clip })` |
| `X_SCRAPE_BLOCKED` | the site refused this client — the identity is spent | **retryable, and it burns the session first.** Retrying a block on the *same* persisted identity re-trips it every time: the flagged cookies are the thing being refused, so the retry has to arrive as somebody else or it is arithmetic, not a retry | the session is burned and the next attempt starts a new identity — lower `rate:` on the `scrape()` definition if this repeats |

`X_NOT_IMPLEMENTED` and `X_ENV_MISSING` are `@ultimat3/core`'s and are documented above: the first is the honest stub the agent recovery seam throws, the second is what a declared secret with no value in the environment is — a missing environment variable, not a scraping concept needing its own code.

## Admin and manifest

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_ADMIN_ENTITY_UNKNOWN` | the admin references an entity that does not exist | a renamed entity | `x g entity <name>`, then `x manifest` |
| `X_ADMIN_POLICY_MISSING` | an admin-exposed subject has no policy | a screen added without authz | add `policy: can('<subject>')` to the definition |
| `X_ADMIN_FIELD_UNSUPPORTED` | a column type the admin cannot render | an exotic Postgres type | supply a custom field renderer, or hide the column |
| `X_ADMIN_ACTION_DUPLICATE` | two registered admin actions carry one `name` | the same action name declared on two entities, or on an entity and the global toolbar. Refused at `defineAdmin`, not at the first call: the name is the MCP tool name, the default label key **and** the key `callAdminTool` resolves a handler by, so a collision is a call that succeeds against the wrong action and reports nothing | rename one in `defineAdmin`'s `actions` — `name: '<entity>.<action>'` — so the bare name belongs to one of them; the cause names both holders |
| `X_ADMIN_PAGE_UNGUARDED` | a custom admin page declared no permissions | a `pages:` entry with an empty `permissions` array. Refused at **declaration** rather than at a request, because the author never writes the `defineRoute` call — `adminRouteConfig` emits it with the policy composed in, so a page cannot reach the router unguarded | add `permissions: ['<subject>:read']` to the `pages` entry for `'<path>'`; the frame's `admin:read` is prepended for you |
| `X_ADMIN_PAGE_PATH_INVALID` | a custom admin page has an unusable or already-taken path | a path that is not rooted, or one that shadows a generated resource route — the generated screen would become unreachable | give the page a rooted path that no resource already claims, e.g. `'/ops'`; the cause names the collision |
| `X_ADMIN_DENIED` | the actor may not use this admin surface | missing `admin:*` permission | grant the permission through the normal policy layer |
| `X_ADMIN_TOOL_FORBIDDEN` | an admin MCP tool was called without permission | agent acting beyond its user | nothing to fix — the policy is correct |
| `X_ADMIN_INVALID` | an admin tool's arguments failed the resource schema | the agent built a row from a stale tool schema | `x manifest`, then re-read the tool's JSON Schema from `tools/list` |
| `X_DEV_DASHBOARD_IN_PROD` | `/_x` was mounted outside dev | the dev dashboard shipped in the image | delete the `/_x` mount from the production entrypoint |
| `X_MANIFEST_DRIFT` | a committed manifest differs from the code | a primitive changed without regenerating, or the file was hand-edited so its `buildId` no longer hashes its own contents | `x manifest` — `bun run manifest` for this repo's own `framework.manifest.json` |
| `X_MANIFEST_STALE` | `openapi.json` is stale | the committed spec does not match the actions the code registers | `x manifest`, then commit |
| `X_MANIFEST_MISSING` | the app ships no `x.manifest.json` at all | nothing ever ran `x manifest`: after `x new`, `bin/setup` and every generator, the file did not exist while the gate's `manifest` step reported green — because the drift check has nothing to compare when the file is absent. Its own code because the repair differs from both neighbours: `X_MANIFEST_DRIFT` means the committed file disagrees with the code, `X_MANIFEST_STALE` means `openapi.json` does, this one means there is nothing there. Raised only at an app root — this repo emits `framework.manifest.json` and has no `x.manifest.json` to be missing | `x manifest` |
| `X_MANIFEST_BREAKING` | a published contract was removed or narrowed | a breaking change with no version bump | bump the major version, or restore the contract |
| `X_AGENTS_MD_MISSING` | no `AGENTS.md` | the human-authored file was deleted | write it by hand — short: stack, commands, conventions |
| `X_AGENTS_MD_TOO_LARGE` | `AGENTS.md` grew past its cap | generated facts pasted into it | move facts into `x.manifest.json`; keep conventions only |

## Testing

| Code | Means | Typical cause | Fix |
|---|---|---|---|
| `X_TEST_DB_UNAVAILABLE` | no Postgres for the test template | nothing listening | run `x dev` (embedded Postgres), or set `TEST_DATABASE_URL` |
| `X_TEST_FIXTURE_UNAVAILABLE` | a declared fixture has no driver in this process | destructuring `page`, `budget`, `signIn` or `deploy` with no browser installed. `subscribe` left this set in 4.2.0 — the framework builds it | `defineFixtures({ <name>: () => yourDriver() })` in the test preload — `cause` names what the fixture needs |
| `X_TEST_LIVE_NODE_UPGRADE_REFUSED` | the in-process sync node refused the connection | the `subscribe` fixture's node answered the upgrade with a response instead of taking it — its accept budget, its connection ceiling, or a node that was never started. A different failure from having nothing to serve, which is the row below | `await node.start()` before `connect()`, and keep the request path at `/_x/sync` |
| `X_TEST_LIVE_NODE_EMPTY` | the in-process sync node has no live query to serve | the `subscribe` fixture built a node and found no `query({ live: true })` registered — almost always the app's api module was never imported, so `registerQueries()` never ran. A registry with nothing in it answers every subscribe with "no live query registered", which is a working socket serving no reads | import the app's api module in the test preload, then `x queries list --json` |
| `X_TEST_FIXTURE_UNKNOWN` | a test requested a fixture nobody registered | a destructured fixture name no `defineFixtures` call declares | `defineFixtures({ <name>: () => buildIt() })` at test setup — `cause` lists the registered names |
| `X_TEST_NETWORK_OFFLINE` | the test network is offline | a request made after `network.offline()` or `network.drop()` | `network.online()` before the call — or assert the offline path instead of the request |
| `X_TEST_NETWORK_SEALED` | a test tried to reach the network | an unmocked external call | `mockFetch('<url>', …)`, or `allowHost('<host>')` if it must be real |
| `X_TEST_NONDETERMINISTIC` | a test read wall-clock time or unseeded randomness | `Date.now()` in the code under test | wrap in `frozenClock()` / `seededRandom()`, or remove the read |
| `X_TEST_EVAL_THRESHOLD` | an `evalTest()` score fell below its threshold | a prompt or output regressed against `options.threshold` | improve the prompt under test, or lower the threshold passed to `evalTest()` |
| `X_TEST_SCHEMA_EXPECTED` | a matcher expected a Standard Schema and got something else | `toRejectInput`/`toAcceptInput` called on an action instead of `action.input` | `call toRejectInput(action.input)` — the schema, not the action or the query |
| `X_TEST_LOCATOR_EXPECTED` | a matcher expected a locator and got something else | `toBeVisible` handed a page, a selector string, or the result of awaiting the locator — anything with no `isVisible()`. Thrown rather than returned as a failing result, exactly as `X_TEST_SCHEMA_EXPECTED` is: the assertion is not false, it is unanswerable, and a `pass: false` would read as "the element was hidden" | `expect(page.getByRole("heading", { name: "Feed" })).toBeVisible()` — the locator itself, unawaited |
| `X_E2E_EVALUATE_UNSUPPORTED` | a page.evaluate() closure cannot be sent into the browser | the closure is native or bound, declares a parameter, or its source is not an expression — there is nothing to send. Refused **statically**, before a round trip | rewrite as a zero-parameter closure over page globals only |
| `X_E2E_EVALUATE_CAPTURED` | a page.evaluate() closure named a binding the page does not have | raised from the page's own `ReferenceError`, naming the binding, because no static scan can catch it: measured on Bun 1.4.0, `const wanted = 3; (() => wanted === 3).toString()` is `"() => !0"` — the transpiler constant-folds a captured primitive away before `toString()` runs, so a captured value may not exist in the source at all | pass the value through the page instead of closing over it |
| `X_E2E_EVALUATE_THREW` | an expression an e2e page ran threw inside the browser | the in-page wrapper catches and answers a value, so the name and message survive the crossing instead of arriving as an opaque evaluation failure | read the reported name and message; the throw happened in the page, not in the test process |
| `X_E2E_LOCATOR_EMPTY` | an e2e locator matched no element | resolved lazily, so this is raised at the question, not at construction — the selector, role or text is quoted back as the call that was written | print what the page actually rendered: `await page.evaluate(() => document.body.innerHTML)`, then narrow or correct the locator call the cause quotes back |
| `X_E2E_LOCATOR_AMBIGUOUS` | an e2e locator matched more than one element and was asked to click | an assertion handed three matches has an answer; a click does not, so `isVisible()`/`count()` answer and `click()` refuses — the "wrong receiver throws, wrong value returns" rule | add `.first()`, or narrow the locator |
| `X_E2E_SERVICE_WORKER_ABSENT` | no service worker took control of the page within the budget | bounded **in the page** rather than by a loop in the harness, so there is exactly one retry mechanism; an unbounded wait is a test that hangs rather than fails | confirm the page registers one: `await page.evaluate(() => navigator.serviceWorker?.controller !== undefined)` — if it does, pass a longer budget to `waitForServiceWorker({ timeoutMs })` |
| `X_CDP_BROWSER_MISSING` | no Chrome or Chromium is installed for the e2e driver to launch | the driver launches a real browser over raw CDP and carries **no dependency** to do it, so what it needs is a binary on disk — `CHROME_PATH` first, then the four `/usr/bin` names GitHub-hosted `ubuntu-latest` ships. Reached only by a caller that has already decided a browser is required: `openE2eBrowserIfAvailable()` answers `undefined` instead, so a machine with no browser SKIPS rather than failing | `export CHROME_PATH=/usr/bin/google-chrome` — or leave it unset and let the browser-backed suite skip |
| `X_CDP_LAUNCH_FAILED` | the browser started and never announced a DevTools endpoint | Chrome states the port it took on **stderr**, once, and `--remote-debugging-port=0` means there is no URL to poll until it does — so no announcement is a crash, a rejected flag or a sandbox refusal, and the last lines of its own stderr are the actionable half | run the same binary by hand with `--headless=new --remote-debugging-port=0` and read its stderr; in a container add `--no-sandbox --disable-dev-shm-usage`, which the launcher already passes |
| `X_CDP_CALL_FAILED` | the browser refused a DevTools call | the call reached the browser and came back an error frame, or the connection died under it — every in-flight call is settled on close, so a dead browser reports this rather than one deadline per call | print what the page had: `await page.evaluate(() => document.body.innerHTML)` — a call that refuses the same way means the browser itself is gone, so read the launch above it |
| `X_CDP_TIMEOUT` | a DevTools call did not answer inside its deadline | its own code rather than `X_TIMEOUT`, because the actionable half is WHICH call: a hung `Page.navigate` is an app that never finishes responding, a hung `Runtime.evaluate` is an expression that never settles | raise `timeoutMs` on `installE2eDriver({ timeoutMs })`, or find the request the page is still waiting on |
| `X_TEST_JOB_EXPECTED` | a matcher expected a job declaration and got something else | `toEmitSteps`/`recordSteps` called on `job.run` or an unrelated value | `call toEmitSteps(myJob)` with the job export, not `toEmitSteps(myJob.run)` |
| `X_TEST_NETWORK_RACE` | a request raced `unsealNetwork()` and lost the patched fetch | `unsealNetwork()` called while a request from the same seal was still in flight | do not call `unsealNetwork()` while a request from the same test is still pending |
| `X_TEST_FACTORY_TRAIT_UNKNOWN` | a factory was asked for a trait it does not declare | a typo at the call site, or a trait never added — the same symptom, so `cause` lists every declared trait to tell them apart | `declare it: defineFactory(<table>, { traits: { <trait>: { /* columns */ } } })` |
| `X_TEST_ISLAND_NOT_BUILT` | the island build produced no chunk for the file the test named | `mountIsland` was given a `file` the builder never produced — a path relative to the test instead of to the app root, a typo, or an island outside `apps/*/{site,app,shared}/**/*.island.tsx`. A **string literal** key and a **null-prototype** table are recognised rather than pinned | guard the read with `Object.hasOwn(table, key)` before indexing, or make the table a `Map`; a table that is deliberately prototype-free is built with `Object.create(null)` and stops being reported |
| `X_PROTO_CHAIN_INDEX_PIN_STALE` | a package is pinned above the number of prototype-reachable reads it still has | the pin outlived the fix, so it would let that many back in | `bun run scripts/proto-index.ts --unpin <packages/name>` — it only lowers |
| `X_PROTO_CHAIN_INDEX_UNSCANNED` | the scan read no source file | same class as an empty glob: a clean answer over nothing read | `edit SOURCE_PATTERNS in scripts/boundaries.ts so it matches this repo layout, then bun run scripts/proto-index.ts` |
| `X_FLIGHT_SECOND_CURVE` | a module other than `packages/core/src/backoff.ts` computes its own backoff | it raises a factor to an attempt and clamps the result in one expression, which is a retry curve whatever it is named. Four of these shipped at once — `jobs/retry.ts`, `ai/gateway.ts`, `realtime/thundering-herd.ts`, `db/transaction.ts` — with three different jitter strategies between them, so fixing a backoff bug meant finding four files and missing three. Matched on SHAPE, never on the name: the first draft looked for a roll called `random`/`rng`/`roll` and read straight past a copy whose parameter was `r`, the same way a rule spelled `RenderMode` read past `PwaRenderMode` | `import { backoffDelay } from '@ultimat3/core'` and delegate — pass `curve` and `jitter` rather than re-deriving them |
| `X_FLIGHT_RANDOM_UNINJECTED` | a shipped source file calls `Math.random()` | nothing downstream of it can be pinned by a test, which is why `packages/ai/src/gateway.ts` was the one retry engine of four with no test at all. A **call**, never a reference: `random = Math.random` as a default parameter is the injectable seam working correctly, and `packages/core/src/backoff.ts` does exactly that | take a `random: () => number` parameter defaulting to `Math.random` and call that instead |
| `X_FINITE_BOUND_UNCHECKED` | a numeric option is defaulted with `??` and never checked for finiteness | `??` guards **nullish**, and `NaN` is not nullish — so `Number(process.env.X)` on an unset variable, a `parseInt` of a typo and an untyped config value all walk past the default and land on the bound intact. `Math.max`/`Math.min`/`Math.floor` are not validators either: all three **propagate** `NaN`, and this repo relied on all three as guards. Four measured outcomes — a comparison that reads false forever (a dead worker's job never reclaimable, an `AcceptBudget` admitting the whole herd), an `Array.from({ length: NaN })` or `slice(0, NaN)` that is `[]` (zero workers, reported as success), a `setTimeout(fn, NaN)` that is `setTimeout(fn, 0)` (a poll becomes a spin), and a loop that never terminates, synchronously, past every `AbortSignal`. Matched on the missing CHECK, never on the option's name | `assert(Number.isFinite(value), '…', '…')` where the option is read — `packages/jobs/src/limits.ts`'s `createLimiter` is the form. `bun run finite-bounds --explain --json` lists every site |
| `X_FINITE_BOUND_PIN_STALE` | a package is pinned above the number of unchecked numeric options it still has | the pin outlived the fix, so it would let that many back in | `bun run scripts/finite-bounds.ts --unpin <pkg>` |
| `X_FINITE_BOUND_UNSCANNED` | the scan read no source file | same class as an empty glob: every package reports zero and the ratchet enforces nothing | `edit SOURCE_PATTERNS in scripts/boundaries.ts so it matches this repo layout, then bun run scripts/finite-bounds.ts` |
| `X_DEAD_DOCS_HOST` | a shipped source file builds a URL on `ultimate.dev` | that host answers **HTTP 404 on every path**, and it shipped as the `docs:` line of roughly ninety error declarations plus a `docsFor(code)` helper in four packages — so the link an operator was handed at the moment of a failure went nowhere. A ratchet: the sweep was done once and nothing stopped it regrowing, because `scripts/new-package.ts` wrote the dead URL into every future package's `errors.ts` template. Only a **string literal** is reported; a comment naming the host as the thing that was removed cannot 404 (`packages/core/src/error-codes.ts:26` is the precedent) | delete the `docs:` line the finding names — `UltimateError` resolves the registered descriptor, whose default is `ERROR_DOCS_URL` from `@ultimat3/core`; if it is not an error link, import `ERROR_DOCS_URL` rather than writing a second host |
| `X_DEAD_DOCS_HOST_PIN_STALE` | a package is pinned above the number of dead-host URLs it still has | the pin outlived the fix, so it would let that many back in | `bun run scripts/dead-docs-host.ts --unpin <packages/name>` — it only lowers |
| `X_DEAD_DOCS_HOST_UNSCANNED` | the scan read no source file | same class as an empty glob: every package reports zero and the ratchet enforces nothing | `edit SOURCE_PATTERNS in scripts/boundaries.ts so it matches this repo layout, then bun run scripts/dead-docs-host.ts` |
| `X_SECRET_COMPARED_UNSAFELY` | a value whose **name** says it is a secret is compared with `===`, `!==` or `.includes()` | a short-circuiting comparison's running time depends on how many leading bytes match, so an attacker learns the value one byte at a time. It must be static and not a test: all twelve `timingSafeEqual` call sites in `@ultimat3/auth` were rewritten to `(a) === (b)` and the package still answered 432 pass · 0 fail, `session.test.ts` included — the difference between the two spellings is a timing distribution, not a return value, so no suite can hold this rule. Reads the NAME of each operand, never its type: `tokenHash === record.tokenHash` is reported, `a === b` is not | replace the comparison with `timingSafeEqual(a, b)` from `@ultimat3/core`; if the name is not a secret, pin the package in `scripts/lib/secret-compare-pins.ts` with the sentence saying what it is |
| `X_SECRET_COMPARE_PIN_STALE` | a package is pinned above the number of secret-named comparisons it still has | the pin outlived the fix, so it would let that many back in | `bun run scripts/secret-compare.ts --unpin <packages/name>` — it only lowers |
| `X_SECRET_COMPARE_UNSCANNED` | the scan read no source file | same class as an empty glob: a clean answer over nothing read | `edit SOURCE_PATTERNS in scripts/boundaries.ts so it matches this repo layout, then bun run scripts/secret-compare.ts` |
| `X_VERSION_STAMP_PIN_STALE` | a page is pinned as naming a version for a reason that is not a stamp, and the page no longer says it | the pin outlived its sentence, so it now excuses whatever lands there next — `PUBLISHING.md`'s `git tag v1.1.0` shell line is the shape the pin exists for | `bun run scripts/version-stamps.ts --unpin <path>` |
| `X_WORKSPACE_MANIFEST_UNREADABLE` | a `package.json` the workspace glob matched cannot be read as a workspace manifest | it vanished between the glob and the read, or it parses into something whose `name`/`version` are not strings — and every release tool in `scripts/` enumerates the workspaces through this one module, so an unreadable manifest silently shrinks the set each of them acts on | `bun -e "console.log(await Bun.file('<path>').json())"` prints the parse error; repair the file until it is a JSON object whose `name` and `version` are strings, then `bun run workspaces:list` |

## Reserved codes

Everything above this heading is live: `x errors explain <CODE>` answers for it today, and the `errors` step fails the build if it does not (`X_ERROR_CODE_UNREGISTERED`). Everything below is documented for a different reason and is deliberately outside that rule.

### Not thrown yet

Reserved, not registered. The name is spoken for — the design docs use it and no future code may reuse it — but nothing raises it in this build, so `x errors explain` refuses it. The right-hand column is what actually happens today.

| Reserved code | What happens today |
|---|---|
| `X_SW_HAND_EDITED` | `sw.js` carries no checksum, so a hand edit survives `x build` and is silently overwritten on the next one |
| `X_SW_UNCACHEABLE` | an `offline` strategy contradicting the route's `render` mode is accepted; `X_SW_SCOPE_INVALID` covers only the scope half |
| `X_CACHE_UNTAGGED_QUERY` | a query no tag covers is cached and never invalidated. `X_CACHE_TAG_UNKNOWN` catches the opposite mistake — a tag no entity declared |

### Names used in the design docs

Some design docs predate the implementation. `As of 2026-08` these are the mappings; the right-hand column is what the framework actually throws. The old name stays here because a code never changes meaning — a renamed concept gets a new code and the old one keeps its row.

| Design doc name | Implemented code |
|---|---|
| `X_JOB_NO_IDEMPOTENCY_KEY` | `X_IDEMPOTENCY_REQUIRED` |
| `X_JOB_DUPLICATE_STEP` | `X_STEP_DUPLICATE` |
| `X_JOB_STEP_FAILED` | `X_JOB_MAX_ATTEMPTS` (retries exhausted) or `X_JOB_TIMEOUT` |
| `X_SEO_NO_TITLE` / `X_SEO_NO_DESCRIPTION` | `X_SEO_META_MISSING` |
| `X_SEO_BUDGET_EXCEEDED` (retired 1.3.0) | `X_BUDGET_EXCEEDED` — `@ultimat3/render`'s, raised by `x verify`'s `budgets` step. `@ultimat3/seo` is tier 1 and cannot see a build's bytes, so its own code had no thrower but its own test, and its `fix:` named a report no step produces. The name is never reused |
| `X_READONLY_VIOLATION` (retired 1.3.0) | the server's own refusal inside `readOnlyQuery`'s `BEGIN READ ONLY`, or `X_MCP_QUERY_REJECTED` from `@ultimat3/mcp`'s parse guard. `@ultimat3/db`'s regex-gated `readOnly()` client is gone — it judged statement keywords only, so `select pg_sleep(60)` and `select pg_read_file('/etc/passwd')` both read as reads |
