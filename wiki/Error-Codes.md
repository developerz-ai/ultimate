# Error codes

Every framework failure is an `UltimateError` carrying a stable `X_*` code, a concrete cause, and the exact command or edit that fixes it. Same content in the terminal, the dev overlay, the HTTP body, the MCP tool result and `--json`.

```text
X_DB_DRIFT: schema differs from migrations
  cause: table "posts" has column "publish_at" not present in any migration
  fix:   x db gen "add publish_at"
```

```json
{"code":"X_DB_DRIFT","title":"schema differs from migrations","cause":"table \"posts\" has column \"publish_at\" not present in any migration","fix":"x db gen \"add publish_at\"","docs":"https://github.com/developerz-ai/ultimate/wiki/Error-Codes"}
```

The HTTP body is the same content as an RFC 9457 problem document — `type`, `title`, `status`, `detail`, plus `code`, `cause`, `fix`, `docs`, `requestId` and `retry` (`terminal`, `retryable` or `retry-after`: the class a client maps to an exception, on every document, a hidden 5xx included) as top-level extension members. Two more are carried when the error has them: `issues`, the per-field rejections of a validation failure, and `meta`, the keys of the error's own `meta` that the app declared for that code with `registerProblemMeta` (everything else in `meta` is operator-only and never leaves the process). Both are all-or-nothing and both are dropped, with `cause`, on a 5xx nobody classified.

| Rule | Detail |
|---|---|
| Lookup | `x errors explain <CODE> --json`, or the MCP `errors.explain` tool — same content as this page |
| Uniqueness | one code is owned by exactly one package; a collision throws `X_ERROR_CODE_DUPLICATE` at registration |
| Stability | codes never change meaning. A renamed concept gets a new code and the old one stays documented |
| `fix` | always runnable or editable as written. If a fix reads "do the right thing", that is a bug — [file it](https://github.com/developerz-ai/ultimate/issues) |
| Bare `Error` | never thrown by the framework. Anything caught is normalised through `toUltimateError()` |
| Registration | a code exists when its owning package calls `registerErrorCodes()`. That one call is what makes it explainable, unique and documented-or-fail — a code emitted as a `Finding` rather than thrown is registered the same way |
| App codes | an app declares each of its own codes ONCE: `defineError({ code, title, status, cause, fix })` from `@ultimat3/core/page` (`offSocket: true` in place of `status` for a code no response carries) registers the title, the HTTP status and the retry, and returns the class to throw — `throw new PostNotFound(ref)`, `PostNotFound.is(error)`. A code with no status answers 500 and hides its cause, so the call makes you choose. An app code needs no row on this page; `guards/error-declared.ts` refuses a handwritten `UltimateError` subclass, a literal-coded `new UltimateError` and a `defineError` imported from the `@ultimat3/core` barrel, which carries the framework's titles tables into every island that throws (12,019 B against 6,507 B, one declaration thrown). A framework code goes through `bun run new-error-code` instead |
| Enforcement | the `errors` step of `x verify` fails on an empty or advice-only `fix`, or one that runs the command before the edit it needs (`X_ERROR_FIX_INVALID`), on a `fix` citing a file the repo does not have (`X_ERROR_FIX_PATH_MISSING`), on a declared code with no row on this page (`X_ERROR_CODE_UNDOCUMENTED`), on a row this page presents as live that no package registers (`X_ERROR_CODE_UNREGISTERED`), and on a `code:` reached through a name nothing in its own file declares (`X_ERROR_CODE_UNRESOLVED`) |

## Reserved codes

Everything above this heading is live: `x errors explain <CODE>` answers for it today, and the `errors` step fails the build if it does not (`X_ERROR_CODE_UNREGISTERED`). Everything below is documented for a different reason and is deliberately outside that rule.

### Not thrown yet

Reserved, not registered. The name is spoken for — the design docs use it and no future code may reuse it — but nothing raises it in this build, so `x errors explain` refuses it. The right-hand column is what actually happens today.

| Reserved code | What happens today |
|---|---|
| `X_SW_HAND_EDITED` | `sw.js` carries no checksum, so a hand edit survives `x build` and is silently overwritten on the next one |
| `X_SW_UNCACHEABLE` | an `offline` strategy contradicting the route's `render` mode is accepted; `X_SW_SCOPE_INVALID` covers only the scope half |
| `X_CACHE_UNTAGGED_QUERY` | a query no tag covers is cached and never invalidated. `X_CACHE_TAG_UNKNOWN` catches the opposite mistake — a tag no entity declared |

New codes are added in the owning package's `src/errors.ts` and registered through `registerErrorCodes()`; add the row to its owner's page in the same pull request (`bun run new-error-code` writes both), or the `errors` step of `x verify` fails the build with `X_ERROR_CODE_UNDOCUMENTED` — see [Contributing](Contributing).
