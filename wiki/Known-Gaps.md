# Known gaps

Defects and unfinished seams named here rather than left to be discovered. Each row carries its own `As of` stamp.

A reference manual that hides these is lying to the reader.

**Read the section headings first.** [Open](#open) is what is wrong with the code you can install
today and is still to change, each row with its decision. [Open by decision](#open-by-decision) will not be fixed and says why, with
what to do instead. [Not built yet](#not-built-yet) is empty. [Carried backlog](#carried-backlog) is owed work with a tracking
issue each. [Deferred by plan 101](#deferred-by-plan-101) is ranked work a later plan owns. [Closed](#closed) is history — every row there carries the release
that fixed it and the workaround for anyone still pinned below it.

**Only the [footer](_Footer) stamps the installable version.** Resolve it yourself rather than reading it here:

```bash
npm view @ultimat3/core version
```

A Closed row whose release is newer than the [footer](_Footer)'s is fixed in the repository and in **no published release** yet; if you
are on an earlier version, treat those rows as open and take the workaround. `[Unreleased]` in
[`CHANGELOG.md`](https://github.com/developerz-ai/ultimate/blob/main/CHANGELOG.md) is the source of
truth for what the next release carries, and most of what it fixes was never a row here. Read that section rather than this sentence: `grep -n '^## '
CHANGELOG.md` finds its bounds, and it changes on any commit.

**Publication is not a gap.** All 31 workspaces are on the registry, every one with a provenance attestation, `As of 2026-11-10` by `bun run scripts/registry-audit.ts --json`, which `registry-audit.yml` re-runs daily;
`@ultimat3/scraping` was the last never-published package and was bootstrapped by hand at 2.0.0
([`PUBLISHING.md`](https://github.com/developerz-ai/ultimate/blob/main/PUBLISHING.md) step 1).
`bun add @ultimat3/scraping` resolves — check it with `npm view @ultimat3/scraping version`.

## Open

Every row carries its decision, `As of 2026-11-18`: **build** is owed work, a defect still to fix; **deferred** waits on the reason in the row.

| Gap | Decision | Symptom | Work around it by |
|---|---|---|---|
| A pod evaluates the framework from **source**, one module at a time — ~28 Mi of resident memory per pod that a bundle would not hold | deferred | `As of 2026-10-01`, measured on the framework serve graph alone: 1,071 modules from source settle at **80.4 Mi**; the same graph as one `bun build --target=bun` file is 5 modules and settles at **51.8 Mi** — ~34 kB of RSS per source module, the runtime's cost and not the code's. It is the largest saving left after the per-role load and the prebuilt store (a web pod of the demo app settles at 97–102 Mi, a worker at 80–85 Mi). **Not a patch**: a registry is a module instance, so the framework bundled apart from the app is two `@ultimat3/jobs`, two `@ultimat3/entity` — the app registers into one and the boot reads the other. The unit has to be the app **and** the framework as one graph, per role, built inside the image build from a generated entry that imports what `scanAppModules` would, with the `.tsx`/`.scss` loaders as build plugins. Containers only either way (axiom 7). Design note: [`docs/architecture/13-topology-runtime.md`](https://github.com/developerz-ai/ultimate/blob/main/docs/architecture/13-topology-runtime.md#not-built-one-bundle-per-role). Deferred `As of 2026-11-18`: it changes what an image contains and how a role resolves its app, so it needs a plan of its own. pin: none — a resident-memory measurement of a running pod, not a behaviour a unit test can assert | nothing to do in an app. Size a pod's memory request from `process_resident_memory_bytes` on `/metrics`, not from a guess |
| Every role evaluates all of `@ultimat3/jobs` — 96 modules (`As of 2026-10-02`, by file) — whatever it runs | deferred | `As of 2026-10-01`, read off the serve graph by the names each role's code uses: a `web` pod needs 43 of them (enqueue, the outbox relay, the purge task), a `scheduler` 46, a `worker` 62. The rest ride the barrel: `worker.ts` and its eighteen dependencies in a web pod, the `backfill()` / `exportJob()` / `webhook()` factories (17 modules, 123 kB of source) in an app that declares none, and the memory driver (3 modules) outside a test. ~1.6 Mi per web pod at the measured 34 kB a module. Closing it means subpath entries (`@ultimat3/jobs/worker`, one per factory) and every importer rewritten — a breaking move for a saving the per-role bundle above makes moot, so it waits on that decision. The operator surface is **not** in this list: `JobIntrospection` is a member of the driver, and the worker announces itself and counts settles through it pin: none — a module count read off a role's serve graph, measured rather than asserted | nothing to do in an app |
| `onSettled` for a completion that **returned a value** runs at most once across a crash | deferred | `As of 2026-11-14`. Every other ending is at least once: the write that settles the row records the debt (`x_jobs.settle_owed`) and the scheduler leader re-drives a dead worker's with `redriven: true, reason: 'lost'` — failures, dead letters, refusals, completions whose body returned `undefined`, and the rows the CLAIM settles (a final-attempt lease lapse buried `dead`, an expired row: `ClaimOptions.settleOwed`, `packages/jobs/src/claim-exhausted.ts`). A body's return value is never stored (`x_jobs` has no result column), so a re-drive could only hand `result: undefined` to a hook typed for a value; on a minor that would break every `onSettled` reading `result`. Storing the result, and so at-least-once for every completion, is planned for `next` [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/jobs/src/settle-redrive.test.ts#a%20completion%20that%20returned%20a%20value%20owes%20nothing%3A%20told%20once%2C%20at%20most%20once) | write what must be recorded for certain inside the body, in a `step.run`; or have the body return nothing and read what it wrote from there |
| A `step.run` output past 256 KiB is stored with a warning, not refused | deferred | `As of 2026-11-12`. Undeclared, `STEP_OUTPUT_MAX_BYTES` logs `jobs.step.output-too-large` (`X_STEP_OUTPUT_TOO_LARGE`) once per job and step and stores the output, because refusing by default would fail shipped jobs on a minor; every attempt still loads it. Refusal by default is planned for `next` [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/jobs/src/steps-output.test.ts#the%20default%20256%20KiB%20warns%20once%20per%20job%20and%20step%2C%20with%20the%20code%2C%20and%20still%20stores) | declare `job({ stepOutputMax: 262_144 })` to be refused now, and persist the payload, returning its key from the step |

## Open by decision

Each of these is a defect, or a target, somebody has already argued about, and the reasoning is why it stays. A target "not planned" names the extension point an app builds on instead.

| Gap | Why it stays |
|---|---|
| `x token`'s `grant` | removed from the registry `As of 2026-11-15`, where it was planned and exited `X_NOT_IMPLEMENTED`; now `X_CLI_UNKNOWN_COMMAND`, exit 1 as before. A key's scopes are fixed when it is issued (`AuthApiKeyRecord.scopes`, never widened; `ApiKeyStore` has no update), so a grant is a new key: `x token create --scopes post:read,post:write --json`, then `x token revoke <old-id>`. A second verb for that pair would be the second path axiom 1 refuses |
| `x db`'s `studio` | removed from the registry `As of 2026-11-15`, where it was planned and exited `X_NOT_IMPLEMENTED`; now `X_CLI_UNKNOWN_COMMAND`, exit 1 as before. The schema browser is the `/_x` db panel (`x dev`): schema, rows and a guarded SQL console. `X_DB_STUDIO_FAILED` stays reserved and unthrown; the old `bunx drizzle-kit studio` shell-out was a second schema engine for one subcommand |
| `x jobs`'s `drain` | removed from the registry `As of 2026-11-15`, where it was planned and exited `X_NOT_IMPLEMENTED`; now `X_CLI_UNKNOWN_COMMAND`, exit 1 as before. 25.0.0 deleted the drain body with the all-throw Redis and NATS stubs, and moving in-flight rows between drivers is a migration no command owns. To stop a queue for maintenance: `x jobs pause <queue>` (a queue the app does not serve is refused, `As of 2026-11-19`), then `x jobs list --queue <queue> --state running --json` until it is empty |
| A local write that died after its last rename is listed with no content type until the key is written again | `As of 2026-10`. `localDriver` commits in four steps (marker, sidecar, bytes, clear marker) and a marker left behind means "re-check this pair". `get()` and `stat()` do re-check against the bytes and answer correctly; `list()` never reads bytes, so it reports that object with no `contentType` and `etag: ''` — honest, and it stays that way until the next `put()` of that key. `stream()` returns bytes only and checks nothing. Two files cannot be committed in one step without changing the on-disk layout |
| A `delete_resource` preview checks only the policy's actor half | `As of 2026-10-18`. Without `live: true` the framework answers a preview without running the action, so the part of a policy that reads the input never runs; a preview can be granted for a call the commit then refuses. Running the policy would mean running the action. An action that needs an exact preview declares `live` in its input and answers its own |
| `localDriver` cannot hold a key and a key beneath it (`a` and `a/b`) | `As of 2026-10`. An object is a file at its key, and a POSIX path is a file or a directory. The second `put()` is refused by code (`X_STORAGE_KEY_CONFLICT`) where it used to be a bare `ENOTDIR`; `s3Driver` and `memoryStorageDriver` hold both. Storing objects under suffixed names would lift it, at the price of a layout migration for every existing root — and the keys `grantUpload` and `scopedKey` build never nest an object under another, so the limit is met only by hand-built keys |
| `insert({ ...row })` of a row whose **nullable** `.sealed()` column was read from the repository stores NULL, silently | a sealed property on a repository row is not enumerable, so a spread leaves it behind (`As of 2026-10`). A required one is refused by name (`X_INVARIANT_VIOLATED`, fix `{ ...row, <col>: row.<col> }`); an absent nullable column is a legal insert, and nothing tells a spread from an omission without making every omission an error. Copy a sealed column by name |
| A drift `fix:` for a table in `public` does not name its schema | `As of 2026-10-02`. A fix for a table read from any other schema carries `set search_path = "<schema>";`; one for `public` is left unqualified, so it relies on the pasting session resolving `public` first. Postgres' default path is `"$user", public`, so a schema named after the connecting role that holds a same-named table shadows it. Check `show search_path` in that session, or prefix the pasted statement with `set search_path = public;` |
| Drift never compares an index's `where` **text** | the catalog answers its own rewriting of the expression (`(deleted_at IS NULL)`) where the snapshot holds the author's spelling (`deleted_at is null`), so comparing the strings reports drift on a database that is exactly right. Normalising them means shipping an expression parser to compete with the server's. Three of the four parts of an index **are** compared now — columns, uniqueness, direction, and the predicate's **presence** — so a partial index recreated as a total one and a `desc` index rebuilt ascending are both caught ([`packages/db/src/drift.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/db/src/drift.ts), `compareIndexes`). `x db gen` compares the text, where both sides are generated. A predicate rewritten by hand into a *different* predicate of the same presence is the residue, and it is invisible: regenerate and read the diff |
| A long `backfill()` retains one step name per batch | `stepRunner`'s `claimed` Set is the authority for `X_STEP_DUPLICATE` and is deliberately unbounded: a 5M-row sweep at `batch: 250` holds 20,000 short strings (~1–2 MB) for the life of the attempt, released when it ends. `MAX_TRACE_NAMES` bounds the *reported* trace, not the membership set. Bounding the set would let a duplicate step name through after 200 batches, and silently replaying a step is the worse failure. Raise `batch` if the attempt is long enough for the retention to matter |
| The admin has no one-click select-all | `As of 2026-10`, by decision: the admin ships zero JavaScript (`hydrate: 'never'`), so every control is a link or a native form. A row checkbox joins the batch form through its `form` attribute, "all matching" is a radio whose meaning is the list's URL, and an action's input is its own page. Selecting every row on one page is one click per row. An island would buy that click and cost the admin its zero-script rule, and "all matching" already covers the whole list |

| `pdf()` prints with no session of its own | `As of 2026-11-09`. The Chrome that `pdf()` drives opens the app's route as nobody: no cookie jar is handed across, so a route behind a session answers exactly as it would a signed-out visitor — its 4xx is `X_SCRAPE_PDF_ROUTE_FAILED`, a sign-in page it renders is what gets printed. The workaround is held by `packages/scraping/src/pdf-render-fence.test.ts`, 'a same-origin request carries the headers; a cross-origin one is blocked without them'. **Why it stays** (`As of 2026-11-18`): The print runs in a browser process launched for that render (`packages/scraping/src/pdf-render.ts`), and handing it the caller's cookie would put a live session in a second process. The extension point is `pdf({ headers })`, sent to the route's origin only (`packages/scraping/src/pdf-fence.ts`), so the credential can be one scoped to the document. **Do instead:** issue a short-lived token the print route accepts and send it through `pdf({ headers })` — [Scraping](Scraping#a-route-printed-to-pdf--pdf) |
| A purge that a replica never hears is bounded by `ttl`, not by the next request | `As of 2026-10-10`. The purge reaches the other replicas through the invalidation broadcast. With the bus down, a replica with its own store answers its copy as a fresh hit until that copy's `ttl` (and tells an edge the ttl's remainder), then renders. `'purge'` therefore requires a `ttl`. **Why it stays** (`As of 2026-11-18`): A replica cannot detect a broadcast it never received, so only its own clock can bound the copy; that is why `'purge'` without a `ttl` is refused (`packages/render/src/revalidate-shape.ts`). The extension point is `runtime.isrStore` with `tagFence`. **Do instead:** choose the `ttl` as the longest a missed purge may last; or share one `runtime.isrStore` with a `tagFence`, where the delete is every replica's at once. |
| A bust purges by the **route's** tags | `As of 2026-10-10`. A stored `isr` page records no tags of its own, so `post:1` reaches every stored page of a route tagged `post` — one render too many per page, never one too few. Each bust reads the store's keys once; the route of each key is remembered, not re-matched [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/render/src/render-isr-purge.test.ts#every%20stored%20key%20of%20the%20route%20goes%3A%20both%20locales%2C%20and%20every%20keyed%20query) **Why it stays** (`As of 2026-11-18`): The error is in the safe direction: one render too many, never a page left stale. Per-page tags would add a tag set to every stored entry and to every `IsrStore` an app implements. **Do instead:** tag a route as narrowly as its data allows; a very large shared store pays one `paths()` per bust per replica. |
| A declared `isr` query parameter's **values** are unbounded | `As of 2026-10-10`. `query: ['page']` puts `page` in the key, and `?page=1` … `?page=999999` are each a key: the framework cannot know which values name a page. The store is bounded (least recently generated out first), so it thrashes rather than grows [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/render/src/render-isr-query.test.ts#only%20a%20declared%20parameter%20is%20part%20of%20the%20key%2C%20and%20of%20the%20URL%20load%20is%20given) **Why it stays** (`As of 2026-11-18`): Which values name a page is the app's knowledge. The framework bounds the cost (a bounded store), and `load` is the extension point that says a value names nothing. **Do instead:** answer `withStatus(404, …)` from `load` for a value that names nothing, and rate-limit the route at the ingress; put a small closed set in the path instead (`/blog/page/[n]` with `prerender()`) |
| A `grantUpload` with a `target` is never sniffed | `As of 2026-11-02`. A presigned PUT signs `host` and the size, so on an s3 disk the uploader chooses the stored type and the bytes. `promoteAttachment` is what checks them (`X_STORAGE_TYPE_REJECTED`), and a grant with a `target` lands straight on the row's key with no promotion step. With an `uploadScanner` installed such a grant is refused outright (`X_STORAGE_TARGET_UNSCANNED`, `As of 31.0.0`), so the gap is only an app's with no scanner. Served, it is contained: `objectResponse` sandboxes a type a browser would run, and a false `image/png` is shown under `nosniff` [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/storage/src/grant.test.ts#naming%20a%20target%20puts%20the%20key%20on%20the%20row%20instead%20of%20in%20pending) **Why it stays** (`As of 2026-11-18`): A presigned PUT goes to the bucket with no server in its path, and a targeted key has no promotion step to read the bytes afterwards. Refusing `target` outright would break the grants apps already issue; with a scanner installed it is refused, and serving is contained. **Do instead:** declare the pair with `uploadFlow()` (`@ultimat3/action`, `As of 31.11.0`), which never grants a target and sniffs at `confirm`; or by hand, grant with no `target` and call `promoteAttachment({ …, policy })`. Keeping a targeted grant: read the head yourself with `validateStoredHead(…)` before writing the key to the row → [Storage and uploads](Storage-And-Uploads) |
| Presence leaves past the lease roster cap | the sweep leader ships at most 4,096 member ids on its lease (`PRESENCE_LEASE_ROSTER_LIMIT`). When the leader's node dies, members beyond that whose TTL expired before the successor's first leading pass are never announced as left. A successor cannot diff against the shared store: the expired members are already gone from it. **Why it stays** (`As of 2026-11-18`): The cap bounds the lease row, the successor has nothing left to diff against, and the roster repairs itself on the next beat. **Do instead:** nothing to do: each client's next beat is answered with the whole roster, so it heals within one beat (10 s by default) |
| An **offline** scrape reads `/robots.txt` over the real network | every `fakeBrowser` / `fixtureBrowser` run takes the default `robots: 'obey'`, and the gate reads `https://<host>/robots.txt` with the platform `fetch` before the first navigation, so outside `bun test` one request still leaves the process. **The silent half is closed `As of 2026-10-04`**: an unreachable robots.txt (5xx, 429, network error, timeout) now refuses the origin with `X_SCRAPE_ROBOTS_DISALLOWED` (RFC 9309 §2.3.1.4 for 5xx, network error and timeout; refusing on `429` is Ultimate's stricter policy — the RFC calls a `4xx` unavailable), so under `bun test` the sealed network's refusal turns the run red instead of reading as allow-everything. **Why it stays** (`As of 2026-11-18`): `robotsGate` is built in `packages/scraping/src/scrape-run.ts` before the driver exists, and obeying robots is the default that must not have an ambient off switch. The extension point is the explicit, reasoned `robots: { ignore }`. **Do instead:** declare the policy in the definition under test — `robots: { ignore: 'fixture host, no live origin' }` — which returns a gate that reads nothing at all. There is no boolean and no ambient off switch, by design — see [Scraping](Scraping#testing-offline) |
| The cache fill fence crosses nodes for **tag busts through Redis only** | `As of 2026-10`. A read-through fill re-checks a fence before it writes. Inside one process that covers everything. Across nodes: the Redis tier keeps leased generation keys a bust writes and a fill samples before `load()` and re-reads after its `SET` ([`packages/cache/src/redis-fence.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/cache/src/redis-fence.ts)), so a tag bust on another pod withdraws the fill even when the broadcast is lost — at one extra round trip before each `load()` and one after the `SET`. Three things still do not cross. **Key busts**: `CacheStack.write` and `.drop` mark `{ key }` locally and the wire form carries tags only. **A deployment with no Redis tier**: there is no shared store to hold a generation, so the window is the broadcast's. **Another pod's LRU**: a value it cached before the bust stays until its TTL when the broadcast is lost. **Why it stays** (`As of 2026-11-18`): A generation needs a store every pod reads, and the broadcast carries tags alone (`packages/cache/src/invalidate.ts`), so a tag is the unit that crosses a process. The `ttl` is the bound on everything else. **Do instead:** give a `cache:` query a TTL you can afford to be wrong for on one pod, keep `redis` in `cache.tiers` on a multi-pod deploy, and prefer a **tag** bust over `cache.drop(key)`: only the first one is broadcast and fenced. |
| A replicated table with **no** replica identity is warned about, never refused | `As of 2026-10-02`. A **channel declared with params** does need `REPLICA IDENTITY FULL` on its `records` tables — a DELETE is routed by the old row's params, which a key-only image does not carry, so members keep the deleted record; `x db gen` grants it since 24.0.0 (one migration for an app that already declares such a channel), and the replicator warns (`replication.channel_identity_partial`) about a table that still lacks it. Live queries do **not** need `REPLICA IDENTITY FULL` on a keyed table: the shared window holds the whole row, so a row leaving the result set and a delete are decided from the window — proved on real WAL by [`pg-identity-window.live.test.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/realtime/src/pg-identity-window.live.test.ts) (out-of-filter update, into-filter update, delete with a key-only before-image, updates to rows never held). What still breaks is a table with no identity at all — `NOTHING`, or `DEFAULT` with no primary key — whose `UPDATE`/`DELETE` Postgres refuses once published. `X_LIVE_REPLICA_IDENTITY` names exactly those at preflight, and warns rather than throws; no `x verify` step reads it. The `REPLICA IDENTITY FULL` the app's declarations need is checked at the gate: since 24.0.0 the `drift` step reports a params-channel table whose FULL no migration recorded (`X_DB_SCHEMA_UNMIGRATED`) — against the migrations, never the live database. A live query's `subscribes:` tables are **not** granted FULL, `As of 2026-10` (#518): `x db gen` validates the names and emits no `ALTER`; a table already on FULL keeps it, and the drift step reads that as agreement. **Why it stays** (`As of 2026-11-18`): Logged and never thrown because a replicator that will not start is worse than the tables it names (`ReplicaIdentityError`, `packages/realtime/src/replication-errors.ts`). **Do instead:** give the table a primary key, or `ALTER TABLE <t> REPLICA IDENTITY FULL;` — the warning names every table that needs it. |
| HPAs read `<unknown>` without a metrics adapter | the chart half is done — `values.yaml` declares `metricsPort: 9090`, every role but `migrate` emits the container port, `service.yaml` publishes it and `templates/servicemonitor.yaml` ships the scrape target, rendered wherever the cluster serves the Prometheus operator's kind (`serviceMonitor.enabled: auto`, `As of 2026-11`). One thing still stands and it is not the chart's to fix: turning scraped series into the `Pods` metrics an HPA reads needs a **custom-metrics adapter**, which is the cluster's. **Why it stays** (`As of 2026-11-18`): The adapter is a cluster component, and axiom 7 keeps platform primitives out of the framework. The chart ships everything up to the scrape target. **Do instead:** install a metrics adapter (and the Prometheus operator, if the cluster has none; an app chart from before the scrape object gets it from `x g chart-alerts`); until then disable the HPAs and pin `replicas`. **Do not hand-add a metrics container port** — the chart emits one and a duplicate is rejected by the API server → [Observability](Observability) |
