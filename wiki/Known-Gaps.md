# Known gaps

Defects and unfinished seams named here rather than left to be discovered. Each row carries its own `As of` stamp.

A reference manual that hides these is lying to the reader.

**Read the section headings first.** [Open](#open) is what is wrong with the code you can install
today. [Open by decision](#open-by-decision) will not be fixed and says why. [Not built yet](#not-built-yet)
is unfinished work, not a defect. [Carried backlog](#carried-backlog) is owed work with a tracking
issue each. [Deferred by plan 101](#deferred-by-plan-101) is ranked work a later plan owns. [Closed](#closed) is history — every row there carries the release
that fixed it and the workaround for anyone still pinned below it.

**Only the [footer](_Footer) stamps the installable version.** Resolve it yourself rather than reading it here:

```bash
npm view @ultimat3/core version
```

A Closed row whose release is newer than the [footer](_Footer)'s is fixed in the repository and in **no published release** yet; if you
are on an earlier version, treat those rows as open and take the workaround. `[Unreleased]` in
[`CHANGELOG.md`](https://github.com/developerz-ai/ultimate/blob/main/CHANGELOG.md) is the source of
truth for what the next release carries, and most of what it fixes was never a row here. Read that section rather than this sentence: `grep -n '^## '
CHANGELOG.md` finds its bounds, and it changes on any commit.

**Publication is not a gap.** All 31 workspaces are on the registry `As of 2026-08-20`, checked by `scripts/registry-audit.ts` daily;
`@ultimat3/scraping` was the last never-published package and was bootstrapped by hand at 2.0.0
([`PUBLISHING.md`](https://github.com/developerz-ai/ultimate/blob/main/PUBLISHING.md) step 1).
`bun add @ultimat3/scraping` resolves — check it with `npm view @ultimat3/scraping version`.

## Open

| Gap | Symptom | Work around it by |
|---|---|---|
| A purge that a replica never hears is bounded by `ttl`, not by the next request | `As of 2026-10-10`. The purge reaches the other replicas through the invalidation broadcast. With the bus down, a replica with its own store answers its copy as a fresh hit until that copy's `ttl` (and tells an edge the ttl's remainder), then renders. `'purge'` therefore requires a `ttl` | choose the `ttl` as the longest a missed purge may last; or share one `runtime.isrStore` with a `tagFence`, where the delete is every replica's at once |
| A bust purges by the **route's** tags | `As of 2026-10-10`. A stored `isr` page records no tags of its own, so `post:1` reaches every stored page of a route tagged `post` — one render too many per page, never one too few. Each bust reads the store's keys once; the route of each key is remembered, not re-matched [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/render/src/render-isr-purge.test.ts#every%20stored%20key%20of%20the%20route%20goes%3A%20both%20locales%2C%20and%20every%20keyed%20query) | tag a route as narrowly as its data allows; a very large shared store pays one `paths()` per bust per replica |
| A declared `isr` query parameter's **values** are unbounded | `As of 2026-10-10`. `query: ['page']` puts `page` in the key, and `?page=1` … `?page=999999` are each a key: the framework cannot know which values name a page. The store is bounded (least recently generated out first), so it thrashes rather than grows [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/render/src/render-isr-query.test.ts#only%20a%20declared%20parameter%20is%20part%20of%20the%20key%2C%20and%20of%20the%20URL%20load%20is%20given) | answer `withStatus(404, …)` from `load` for a value that names nothing, and rate-limit the route at the ingress; put a small closed set in the path instead (`/blog/page/[n]` with `prerender()`) |
| A `grantUpload` with a `target` is never sniffed | `As of 2026-11-02`. A presigned PUT signs `host` and the size, so on an s3 disk the uploader chooses the stored type and the bytes. `promoteAttachment` is what checks them (`X_STORAGE_TYPE_REJECTED`), and a grant with a `target` lands straight on the row's key with no promotion step. Served, it is contained: `objectResponse` sandboxes a type a browser would run, and a false `image/png` is shown under `nosniff` [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/storage/src/grant.test.ts#naming%20a%20target%20puts%20the%20key%20on%20the%20row%20instead%20of%20in%20pending) | grant with no `target` and call `promoteAttachment({ …, policy })`; for a targeted grant, read the head yourself with `validateStoredHead(…)` before writing the key to the row → [Storage and uploads](Storage-And-Uploads) |
| A queued offline write is not bound to its principal **on the server** | `As of 2026-10`. The fence is in the page: a principal change abandons the running replay, refuses a write in flight (`X_OFFLINE_QUEUE_ABANDONED`) and wipes the queue. A second TAB whose replay is already past its store read when another tab changes the session cookie still sends its remaining entry under the new session — one entry, one in-flight pass, on a shared browser | sign out by full navigation (`signOutHeaders()` clears site data, and every boot wipes other principals' queues); do not share a browser profile between accounts with offline writes queued |
| Presence leaves past the lease roster cap | the sweep leader ships at most 4,096 member ids on its lease (`PRESENCE_LEASE_ROSTER_LIMIT`). When the leader's node dies, members beyond that whose TTL expired before the successor's first leading pass are never announced as left. A successor cannot diff against the shared store: the expired members are already gone from it | nothing to do: each client's next beat is answered with the whole roster, so it heals within one beat (10 s by default) |
| A **deployed** fresh scaffold issues no session: every policy-protected route answers 401 | `As of 2026-10-06`. `x new` installs a real session authenticator in **every** environment — `apps/web/app/auth/authenticator.ts`, a session cookie resolved by `@ultimat3/auth` over the framework's `x_users` / `x_sessions` tables (`packages/cli/src/templates/scaffold-auth.ts`) — so a container no longer logs `X_CONFIG_INVALID … no authenticator is configured`. What it still lacks is a **sign-in page**: nothing calls `login()`, so no browser ever holds a session cookie. Under `x dev` a request with no session is the development viewer (`dev-actor.ts`, a warning at boot); anywhere else it is anonymous, by design — the fallback reads its environment with `fallback: 'production'`, so a process naming neither `ULTIMATE_ENV` nor `NODE_ENV` installs no viewer | write the sign-in page: an action that calls `login(appAuth(), { email, password, ip })` and sets the `cookie` it returns on the response (`appAuth` is `apps/web/app/auth/auth.ts`; `register(appAuth(), { email, password, orgId, roles })` creates a user). Then delete `dev-actor.ts` and its fallback line in `authenticator.ts` → [Policies and authz](Policies-And-Authz) |
| An **offline** scrape reads `/robots.txt` over the real network | every `fakeBrowser` / `fixtureBrowser` run takes the default `robots: 'obey'`, and the gate reads `https://<host>/robots.txt` with the platform `fetch` before the first navigation, so outside `bun test` one request still leaves the process. **The silent half is closed `As of 2026-10-04`**: an unreachable robots.txt (5xx, 429, network error, timeout) now refuses the origin with `X_SCRAPE_ROBOTS_DISALLOWED` (RFC 9309 §2.3.1.4 for 5xx, network error and timeout; refusing on `429` is Ultimate's stricter policy — the RFC calls a `4xx` unavailable), so under `bun test` the sealed network's refusal turns the run red instead of reading as allow-everything | declare the policy in the definition under test — `robots: { ignore: 'fixture host, no live origin' }` — which returns a gate that reads nothing at all. There is no boolean and no ambient off switch, by design — see [Scraping](Scraping#testing-offline) |
| The cache fill fence crosses nodes for **tag busts through Redis only** | `As of 2026-10`. A read-through fill re-checks a fence before it writes. Inside one process that covers everything. Across nodes: the Redis tier keeps leased generation keys a bust writes and a fill samples before `load()` and re-reads after its `SET` ([`packages/cache/src/redis-fence.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/cache/src/redis-fence.ts)), so a tag bust on another pod withdraws the fill even when the broadcast is lost — at one extra round trip before each `load()` and one after the `SET`. Three things still do not cross. **Key busts**: `CacheStack.write` and `.drop` mark `{ key }` locally and the wire form carries tags only. **A deployment with no Redis tier**: there is no shared store to hold a generation, so the window is the broadcast's. **Another pod's LRU**: a value it cached before the bust stays until its TTL when the broadcast is lost | give a `cache:` query a TTL you can afford to be wrong for on one pod, keep `redis` in `cache.tiers` on a multi-pod deploy, and prefer a **tag** bust over `cache.drop(key)`: only the first one is broadcast and fenced |
| A replicated table with **no** replica identity is warned about, never refused | `As of 2026-10-02`. A **channel declared with params** does need `REPLICA IDENTITY FULL` on its `records` tables — a DELETE is routed by the old row's params, which a key-only image does not carry, so members keep the deleted record; `x db gen` grants it since 24.0.0 (one migration for an app that already declares such a channel), and the replicator warns (`replication.channel_identity_partial`) about a table that still lacks it. Live queries do **not** need `REPLICA IDENTITY FULL` on a keyed table: the shared window holds the whole row, so a row leaving the result set and a delete are decided from the window — proved on real WAL by [`pg-identity-window.live.test.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/realtime/src/pg-identity-window.live.test.ts) (out-of-filter update, into-filter update, delete with a key-only before-image, updates to rows never held). What still breaks is a table with no identity at all — `NOTHING`, or `DEFAULT` with no primary key — whose `UPDATE`/`DELETE` Postgres refuses once published. `X_LIVE_REPLICA_IDENTITY` names exactly those at preflight, and warns rather than throws; no `x verify` step reads it. The `REPLICA IDENTITY FULL` the app's declarations need is checked at the gate: since 24.0.0 the `drift` step reports a params-channel table whose FULL no migration recorded (`X_DB_SCHEMA_UNMIGRATED`) — against the migrations, never the live database. A live query's `subscribes:` tables are **not** granted FULL, `As of 2026-10` (#518): `x db gen` validates the names and emits no `ALTER`; a table already on FULL keeps it, and the drift step reads that as agreement | give the table a primary key, or `ALTER TABLE <t> REPLICA IDENTITY FULL;` — the warning names every table that needs it |
| HPAs read `<unknown>` without a metrics adapter | the chart half is done — `values.yaml` declares `metricsPort: 9090`, every role but `migrate` emits the container port, `service.yaml` publishes it and `templates/servicemonitor.yaml` ships the scrape target. Two things still stand and neither is the chart's to fix: `serviceMonitor.enabled` defaults **false**, because a cluster without the Prometheus operator has no such CRD and `helm install` fails on an unknown kind; and turning scraped series into the `Pods` metrics an HPA reads needs a **custom-metrics adapter**, which is the cluster's pin: none — what is missing is the cluster's custom-metrics adapter, outside this repository | set `serviceMonitor.enabled: true` and install a metrics adapter; until then disable the HPAs and pin `replicas`. **Do not hand-add a metrics container port** — the chart emits one and a duplicate is rejected by the API server → [Observability](Observability) |
| `--target binary` is a **launcher** for an app tree, and has never been served from a bare VM | `As of 2026-10-06`. It boots: `x build --target binary` compiles `apps/web/server.ts` with `--compile-autoload-package-json`, `--compile-autoload-tsconfig` and `@ultimat3/*` external (`binaryArgs`, `packages/cli/src/cmd-build.ts`), and the required `windows` CI job starts the result from a scaffold and gets `200` from `/healthz`; `packages/cli/e2e/binary-launch.e2e.test.ts` proves the same on Linux. **It is not a self-contained artifact**: at run time it reads the app's `package.json` and `tsconfig.json`, imports `app.config.ts` and every module under `apps/*`, and loads the framework from the app's `node_modules` — one instance, so the app's registrations reach the server. Unmeasured: a scaffold compiled, copied with its tree to a VM with no Bun, and served under systemd [pin](https://github.com/developerz-ai/ultimate/blob/main/packages/cli/e2e/binary-launch.e2e.test.ts#the%20compiled%20launcher%20resolves%20its%20app%20tree%20at%20run%20time%2C%20against%20ONE%20framework%20instance) | ship the app root, its installed `node_modules` (installed for the target OS and CPU) and the binary together, and start the binary from that root. Prove it for your own app first — `./app --version`, then `ROLE=web PORT=3000 ./app` and `curl /readyz`. Prefer `--target docker`, the self-contained artifact → [Deployment](Deployment) |

Observed once (2026-09-17, TypeScript 7.0.2): after a `git stash -u` → branch switch → `x verify` on the other branch → switch back → `stash pop` sequence, a type error that surfaces in an UNCHANGED file (a widened index signature in a file it imports) passed locally and failed CI; deleting `tsconfig.tsbuildinfo` then reproduced CI's red locally. Five faithful reproduction attempts against 7.0.2 all stayed correctly red ([#450](https://github.com/developerz-ai/ultimate/issues/450)). **[#450](https://github.com/developerz-ai/ultimate/issues/450) itself is closed `As of 2026-09-23`** — read from the shipped fix, not from the tracker: plan 101 row 14 r ("Close #450", `docs/plans/2026/09/23/101-framework-deep-sweep/14-guards-gate.md:37`; plan `status.yml` `complete`), recorded in `CHANGELOG.md` under 22.0.0 and pinned by `packages/cli/src/verify-typecheck.test.ts`. `tsc -b` decides "up to date" by **mtime**, and Bun installs a dependency as **hardlinks** carrying its cache's old mtimes, so an upgrade to an already-cached version left every input older than the buildinfo and a root without `references` — every scaffolded app — skipped the program and reported green while a cold CI was red. A scaffolded app's `typecheck` is now `tsc -p .` ([`packages/cli/src/templates/scaffold-repo.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/cli/src/templates/scaffold-repo.ts), its `"typecheck"` script), which is incremental by **content hash**, and `x verify`'s `typecheck` step picks `-p .` over `-b` for any such root ([`packages/cli/src/verify-typecheck.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/cli/src/verify-typecheck.ts)); the framework root keeps `-b`. **Still open**: a *second* `tsc` racing the same buildinfo is the one suspect not excluded, and no cause for it has been shown. `x verify` deliberately takes two flags and no `--cold` pin: none — one sighting, and five faithful reproductions stayed red, so no test can hold it | CI is always cold and is the judge of record. If a local `typecheck` disagrees with it again, capture the command, its argv and its exit code before deleting any `tsconfig.tsbuildinfo` |
| A `stream` page with a realtime island keeps every island on the page inert until its slowest hole closes | `As of 2026-11-02`. The runtime goes `async` so a shell island answers while a hole is open, but only with no realtime boot in the document: the boot (`script defer`) has to run first (`bootScript`, [`packages/cli/src/route-islands.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/cli/src/route-islands.ts)), and a deferred script waits for parsing to end. Bound by the hole's 15 s deadline | keep the slow read out of such a page's holes, or give it a short deadline of its own: `fetch(url, { signal: AbortSignal.timeout(2_000) })` |
| A soft visit waits for the slowest hole | `As of 2026-11-02`. The client router reads `response.text()` ([`packages/render/src/navigation-fetch.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/render/src/navigation-fetch.ts)) and swaps the whole answer, so holes fill through the re-run scripts and the first paint of an in-app navigation is as late as a full `ssr` render. | A pod evaluates the framework from **source**, one module at a time — ~28 Mi of resident memory per pod that a bundle would not hold | `As of 2026-10-01`, measured on the framework serve graph alone: 1,071 modules from source settle at **80.4 Mi**; the same graph as one `bun build --target=bun` file is 5 modules and settles at **51.8 Mi** — ~34 kB of RSS per source module, the runtime's cost and not the code's. The operator surface is **not** in this list: `JobIntrospection` is a member of the driver, and the worker announces itself and counts settles through it pin: none — a module count read off a role's serve graph, measured rather than asserted | nothing to do in an app |

## Open by decision

Each of these is a defect somebody has already argued about, and the reasoning is why it stays.

| Gap | Why it stays |
|---|---|
| A local write that died after its last rename is listed with no content type until the key is written again | `As of 2026-10`. `localDriver` commits in four steps (marker, sidecar, bytes, clear marker) and a marker left behind means "re-check this pair". `get()` and `stat()` do re-check against the bytes and answer correctly; `list()` never reads bytes, so it reports that object with no `contentType` and `etag: ''` — honest, and it stays that way until the next `put()` of that key. `stream()` returns bytes only and checks nothing. Two files cannot be committed in one step without changing the on-disk layout |
| A `delete_resource` preview checks only the policy's actor half | `As of 2026-10-18`. Without `live: true` the framework answers a preview without running the action, so the part of a policy that reads the input never runs; a preview can be granted for a call the commit then refuses. Running the policy would mean running the action. An action that needs an exact preview declares `live` in its input and answers its own |
| `localDriver` cannot hold a key and a key beneath it (`a` and `a/b`) | `As of 2026-10`. An object is a file at its key, and a POSIX path is a file or a directory. The second `put()` is refused by code (`X_STORAGE_KEY_CONFLICT`) where it used to be a bare `ENOTDIR`; `s3Driver` and `memoryStorageDriver` hold both. Storing objects under suffixed names would lift it, at the price of a layout migration for every existing root — and the keys `grantUpload` and `scopedKey` build never nest an object under another, so the limit is met only by hand-built keys |
| `insert({ ...row })` of a row whose **nullable** `.sealed()` column was read from the repository stores NULL, silently | a sealed property on a repository row is not enumerable, so a spread leaves it behind (`As of 2026-10`). A required one is refused by name (`X_INVARIANT_VIOLATED`, fix `{ ...row, <col>: row.<col> }`); an absent nullable column is a legal insert, and nothing tells a spread from an omission without making every omission an error. Copy a sealed column by name |
| A drift `fix:` for a table in `public` does not name its schema | `As of 2026-10-02`. A fix for a table read from any other schema carries `set search_path = "<schema>";`; one for `public` is left unqualified, so it relies on the pasting session resolving `public` first. Postgres' default path is `"$user", public`, so a schema named after the connecting role that holds a same-named table shadows it. Check `show search_path` in that session, or prefix the pasted statement with `set search_path = public;` |
| Drift never compares an index's `where` **text** | the catalog answers its own rewriting of the expression (`(deleted_at IS NULL)`) where the snapshot holds the author's spelling (`deleted_at is null`), so comparing the strings reports drift on a database that is exactly right. Normalising them means shipping an expression parser to compete with the server's. Three of the four parts of an index **are** compared now — columns, uniqueness, direction, and the predicate's **presence** — so a partial index recreated as a total one and a `desc` index rebuilt ascending are both caught ([`packages/db/src/drift.ts`](https://github.com/developerz-ai/ultimate/blob/main/packages/db/src/drift.ts), `compareIndexes`). `x db gen` compares the text, where both sides are generated. A predicate rewritten by hand into a *different* predicate of the same presence is the residue, and it is invisible: regenerate and read the diff |
| A long `backfill()` retains one step name per batch | `stepRunner`'s `claimed` Set is the authority for `X_STEP_DUPLICATE` and is deliberately unbounded: a 5M-row sweep at `batch: 250` holds 20,000 short strings (~1–2 MB) for the life of the attempt, released when it ends. `MAX_TRACE_NAMES` bounds the *reported* trace, not the membership set. Bounding the set would let a duplicate step name through after 200 batches, and silently replaying a step is the worse failure. Raise `batch` if the attempt is long enough for the retention to matter |
| The admin has no one-click select-all | `As of 2026-10`, by decision: the admin ships zero JavaScript (`hydrate: 'never'`), so every control is a link or a native form. A row checkbox joins the batch form through its `form` attribute, "all matching" is a radio whose meaning is the list's URL, and an action's input is its own page. Selecting every row on one page is one click per row. An island would buy that click and cost the admin its zero-script rule, and "all matching" already covers the whole list |
